Hive Browser Bridge — 设计、实现与使用

让 agent 驱动你正在用的那一个 Chrome，而不是每个 agent 各起一个无头浏览器：Chrome 扩展 + 本地 WebSocket 桥 + 每 agent 一个 tab group。本文覆盖设计动机、进程/端口架构、协议、代码地图、使用步骤、安全边界，以及 Go 移植的诚实现状。

00为什么需要它

一句话：agent 需要操作真实网页，而“每个 agent 启动一个 Playwright Chrome”在真实账号场景里代价太高。Browser Bridge 用扩展把自动化接进用户已有的 Chrome。

问题 1 · 登录态
真实会话
独立浏览器 = 独立 profile：SSO、Cookie、企业门户都要重新登录；很多系统还会对无头浏览器做风控。
问题 2 · 隔离与可见
Tab group / agent
多个 agent 共用一个浏览器会互相踩标签页；用户也看不到 agent 在操作什么。
问题 3 · 生命周期
桥独立存活
浏览器连接不能绑在可随时被超时杀掉的工具子进程上，否则一次慢调用会带走所有标签页。
设计选择做法解决什么
复用真实 ChromeChrome 扩展（chrome.debugger + chrome.tabs + chrome.tabGroups）连到本地桥；不启动新浏览器登录态、Cookie、扩展、企业风控全部保持原样；用户可随时接管。
每 agent 一个 tab group首个浏览器调用时 context.create 建组；组标题带零宽标记 U+200B，供清扫器识别 Hive 组并发 agent 互不串页；标签栏可见；任务结束 context.destroy 关组，Chrome 不退出。
桥独立进程gcu.bridge_host 监督进程 + 常驻 worker；gcu MCP server 只是 RPC 客户端工具调用超时/子进程重启不会断开扩展；gcu 重启后重连仍保留所有标签页。
控制面与数据面分离14829 扩展中继、14830 状态/代理 HTTP、14831 方法调用 RPC坏掉的工具调用不会和扩展帧混在一起；两套协议可独立演进。
健康可观测双向心跳（WS ping + 应用层 ping）、/status、side panel、状态徽章、blocker 规则“绿灯但实际卡死”能被识别；DevTools 抢占、特权页面、原生对话框会给出可读原因。

2.1 这是标准接口吗？

层标准性说明
传输标准RFC 6455 WebSocket，JSON 文本帧，扩展主动连 ws://127.0.0.1:14829/bridge；WS 层 ping/pong 由协议自带。
信封与命令词表Hive 私有hello{version,protocolVersion,extensionId,profileLabel}、ping/pong、{id,type,...params} → {id,result|error}、tab.*/cdp.attach/cdp、cdp_event/tab_event/tab_group_event。有版本协商（当前 protocol 6）和同 label 顶替（close 4002），但不是公开规范，没有第三方 SDK/多实现生态。
页面动作语义事实标准cdp 命令把 Chrome DevTools Protocol 的 method/params 原样透传给 chrome.debugger.sendCommand；点击/输入/截图最终都是 CDP。这层是标准的，“怎么跟桥说话”那层是私有的。

对比：W3C 的 WebDriver BiDi 是标准化浏览器自动化协议，Hive 没有实现；MCP 是更外层（agent ↔ 工具）的标准，不负责扩展 ↔ 桥；Playwright/Puppeteer 走 CDP 或自家驱动。Hive 选私有薄协议的原因是：要驱动用户已登录的真实 Chrome（不能要求用 --remote-debugging-port 重启浏览器）、要 chrome.tabGroups 这类扩展 API（CDP 没有稳定等价物）、还要 context 接管/健康/遥测等 CDP 之外的语义。

03一条命令的生命周期

以 hive-browser open https://example.com --json 为例：

  1. 身份注入：Hive runtime 在 terminal_exec 子进程环境里写入 HIVE_BROWSER_SESSION（= 该 agent 的 session id）与 HIVE_BROWSER_PROFILE_DISPLAY_NAME；CLI 把它绑成 _active_profile contextvar。没有它，所有 agent 会落到共享的 default 组，互相串页。
  2. CLI → RPC：gcu.cli 经 BridgeClient 连 14831，调 open；gcu.errors.run 负责把异常映射成 JSON envelope + 退出码。
  3. 桥 → 扩展：桥若发现该 profile 还没有组，先发 context.create（返回 groupId, tabId）；然后 tab.create → tab.activate（除非 background）→ cdp.attach → Page.enable → Page.navigate → Runtime.evaluate 轮询 readyState/url/title。
  4. 扩展 → Chrome：chrome.tabs 建标签、chrome.tabGroups 标记组、chrome.debugger 发 CDP；结果原路回传。
  5. 桥侧记账：context 注册表、active tab、action history、telemetry JSONL（opt-in）、限流钩子、stale sweep（30s）在同一进程内更新。
  6. 返回：CLI 打印 {"ok":true,"tabId":…,"url":…,"title":…,"browser_profile":…}；退出码 0。截图类命令会把 JPEG 写到 saved_to 并自动挂到 agent 下一轮。
为什么截图要“自动挂下一轮”：工具结果里只有文本和路径，图片字节要由 framework 的 _maybe_inline_browser_image 在下一轮转成多模态内容；这也是为什么 CLI 文档反复强调“不要再用 attach_file 重复挂”。

05怎么用

5.1 安装扩展

  1. Chrome Web Store（推荐）：Hive Browser Bridge。
  2. 开发者安装：打开 chrome://extensions → 开启 Developer mode → Load unpacked → 选 go_hive/browserbridge/extension（或 tools/browser-extension）。
  3. 打包分发：go_hive/browserbridge/scripts/package_extension.sh 生成 dist/hive-browser-bridge-1.7.4.zip；--check 只校验 manifest 引用文件。

5.2 启动桥

  • Hive 运行时：hive serve / 桌面端启动后，_bridge_keepalive_loop 会调用 ensure_bridge_host_running() 自动拉起 supervisor；无需手工起。
  • 手工调试：uv run --project tools python -m gcu.bridge_host --supervise（supervisor）或 python -m gcu.bridge_host（单 worker）。
  • 确认：curl -s http://127.0.0.1:14830/status | jq .；或 hive-browser setup --json 看 connected_profiles。

5.3 Agent 命令面

agent 通过 terminal_exec 跑 hive-browser <command> ... --json；先调 browser_setup 拿完整命令表。

06健康、隔离与安全

健康状态
4 态
healthy（connected 且 pong < 15s）· stale（connected 但 pong 过期）· disconnected（桥在、扩展不在）· offline（桥都不在）。
双向心跳
WS + 应用层
WS ping 查 TCP；应用层 ping 查 offscreen/Service Worker 是否还在泵消息。半开连接任一侧都能发现并重连。
隔离单位
tab group
每个 agent/session 一个组；组标题带零宽标记供清扫器识别；context.destroy 只关组内标签，Chrome 不退出。

6.1 Blocker（可读的失败原因）

  • privileged_scheme：chrome:// 等特权页，Chrome 禁止扩展自动化；
  • devtools_attached：DevTools 或别的工具占着 chrome.debugger；
  • pending_dialog：页面有原生 alert/confirm/prompt 挡住输入；
  • 其余规则在 gcu/browser/health.py，/contexts 会把组内所有标签的 blocker 去重后汇总，/status 给 system_blocker。

6.2 隔离与接管

side panel 可以 adopt 一个用户正在看的标签（把它移进 agent 的组）或 release 它（移出组、交还用户）；另一个 agent 已拥有该标签时返回 409 conflict。从用户侧发起的接管会通过 notify 帧回传到对应 agent 的 inject_event，agent 下一轮就能看到“标签被接管/释放”。

6.3 安全边界（必须知道）

它驱动的是你真实的浏览器和真实的登录态。扩展权限包括 debugger、tabs、tabGroups、scripting、offscreen、storage、alarms、sidePanel，host 权限含 <all_urls>。任何能向 agent 输入文本的人（聊天渠道、网页内容）都可能间接让 agent 在你已登录的站点上操作；Hive 文档明确提醒：bypassPermissions 或 Bash 工具下，陌生人的一句话离“在你机器上执行命令”只有几个字母。桥只监听 loopback，但这不防提示注入。
  • 桥/HTTP 全部绑 127.0.0.1，非 loopback 对端直接拒绝；
  • 导航可挂社交平台限流钩子（SocialRateLimiter），429 回到 agent；
  • 每次工具调用受 60s 预算约束；桥独立进程保证超时只杀客户端，不杀浏览器连接；
  • telemetry 默认 opt-in，写入按天 JSONL，敏感字段做脱敏。

6.4 部署边界：必须和 Chrome 同机吗？

当前设计：必须同机。Hive 运行时、bridge（bridge_host + BeelineBridge）、Chrome 扩展三者全部只走 loopback，且没有任何认证/TLS：扩展硬编码 ws://127.0.0.1:14829/bridge（legacy 9229），桥只绑 127.0.0.1，Hive 的状态探针与 CLI 的 RPC 也只拨 127.0.0.1（14830/14831）。它们是不同进程，但不是可分离的主机。

拓扑可行性说明
Hive + bridge + Chrome 同一台（推荐）开箱即用三个独立进程 + loopback；这也是唯一被测试过（协议层）的形态。
Hive 在远程服务器，Chrome 在你桌面不支持的扩展只会拨本机 loopback；远程 Hive 的 CLI/探针也拨它自己的 loopback。要拆开必须改代码（见下）。
同机 Docker（Linux，--network host）勉强可行容器与宿主共享 loopback 才能让扩展连上容器里的桥；macOS/Windows 的 Docker 不共享 loopback，不可行。
WSL2：Windows Chrome + WSL 里的 Hive不可行loopback 隔离；需要 Windows portproxy 且扩展仍只认 127.0.0.1，不被支持。
Hive 留在桌面，远程访问它的 dashboard/API可行自动化留在桌面；hive serve --host 或 SSH 隧道把 UI/API 暴露出去（注意 Hive API 的鉴权面）。
真要分离部署，需要五项改造：① 扩展的 bridge URL 可配置（不是硬编码 127.0.0.1）+ manifest host 权限；② 桥支持 wss:// + 认证令牌（现在是无鉴权的浏览器控制面）；③ Hive 侧把状态探针 / CLI RPC 的 host 做成配置（现在只有 HIVE_BRIDGE_PORT 改端口）；④ 关掉 Hive 侧的 ensure_bridge_host_running（否则它会在 Hive 所在机器本地拉起一个桥）；⑤ 隧道/VPN 承载。在此之前，把 14829/14830/14831 暴露到非 loopback 等于把你已登录的浏览器控制面交给网络——不要这么做。

07Go 移植现状（诚实版）

Go 侧 go_hive/browserbridge 是一个独立 module、零外部依赖的库（没有 cmd/ 入口），覆盖 L0/L1/L2：WS 传输、hello/多 profile、路由/错误、核心命令、context/tab-group 注册表、adopt/release、事件消费、30s 清扫、健康、telemetry、限流、side-panel HTTP。它尚未被主 go-hive module 引用（grep aden-hive/hive-go/browserbridge 在 go_hive/go-hive 下 0 命中），所以生产 Go hive 目前不会启动它。
