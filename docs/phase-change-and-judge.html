是什么 · 是否真实生效 · 对女王与 worker 的差异

一句话：phase change 是真实且对女王生效的状态迁移；judge feedback 在 Python 主路径上被短路（女王 skip_judge、worker 由 report_to_parent 先终止），Go 在 2026-11-26 已移除此前的 Go-only colony goal criteria 继承：女王 spec 固定 skip_judge=True，colony worker/overseer 不接 loop judge，自然停点与显式 report 都不注入 [Judge feedback]。两边都不是“worker 结果监督器”。

02Phase change 是什么

它不是一条消息，而是会话状态从 independent（DM）切到 colony（或反向）的迁移。女王只有一个 phase_state.phase 字段，整个运行时围绕它选择 prompt、工具和 loop 配置。

字段 / 行为说明
phase"independent" 或 "colony"；持久化到 session 的 meta.json
prompt_independent / prompt_colony创建时预先拼好的两套 phase base prompt
independent_tools / colony_tools两套工具面；get_current_tools() 按 phase 返回
loop configcolony 用更宽的 tool-call envelope（budget 50 × hard_multiple 10）

关键点：phase 不是“给模型的一句话”，而是**存储路径、工具暴露、SSE 过滤、prompt 选择**的共同判别字段。

03四条生效链路

链路实现
状态switch_to_colony() 把 self.phase 设为 colony，并 persist_phase() 写回 meta.json（tools/queen_lifecycle_tools.py:212-235）
Prompt下一迭代 dynamic_prompt_provider=phase_state.get_static_prompt 重新读取；get_static_prompt 按 phase 选 prompt_colony（:422-425）
工具dynamic_tools_provider=phase_state.get_current_tools 回到 colony 工具集（queen_orchestrator.py:1690-1706）
事件_emit_phase_event() 发 QUEEN_PHASE_CHANGED（:477-490）；前端 queen-dm.tsx:2068-2074 更新 phase badge
对话历史不变：phase change 只影响后续请求的 system prompt 和 tools，不会重写已有 messages。system 前缀因此变化，prompt cache 会失效一次，这是预期代价。

04谁触发、何时不触发

触发

  • run_worker / run_parallel_workers 在 spawn 或 resume 成功后调用 switch_to_colony()（queen_lifecycle_tools.py:1576、:1757）。
  • 会话创建时可以直接以 initial_phase=colony 启动；恢复时从 meta.json 读回 phase。多数 colony 会话不走中途切换。

不触发 / 边界

情况行为
已经是 colonyswitch_to_colony 直接 return，不重复发事件
工具触发（默认 source="tool"）不注入 [PHASE CHANGE] 消息——工具结果本身已经告诉女王；只有 frontend/auto 触发才 inject_notification
反向切换switch_to_independent() 方法存在（:525），但当前树里没有生产调用方；只在 queen-only 工具清理名单里出现（routes_execution.py:78）
worker 内部worker 没有 phase 概念，不参与这个切换

05真实性与边界

是真实有效的：状态、prompt、工具、持久化、前端事件五条链路都通，且已有测试覆盖（test_queen_tools.py 直接设置 ps.phase = "colony" 并断言工具面）。

但要注意：

  • 它不产生一条 <system-reminder>；只有 frontend/auto 触发时额外注入一条 [PHASE CHANGE] 普通事件消息。
  • 它不改变已经发出的消息，只改变下一次请求的 prompt/tools。
  • 反向切换虽然实现了，但当前没有生产路径调用，实际运行形态是“创建时选 phase + 正向 switch”。

06Judge feedback 是什么

它也不是 reminder，而是**回合结束时的质量判定**。每次自然停点（没有真实工具结果的回合）会问 judge：这一轮是否完成、是否要重试、是否要升级。

verdict含义loop 行为
ACCEPT接受当前回合结束 / 进入下一个节点
RETRY + feedback未完成，需要纠正追加 [Judge feedback]: … 用户消息，继续下一轮
RETRY + feedback=None没有真正评估（skip_judge / 有工具结果）只继续，不注入任何消息
ESCALATE判定失败或无法继续结束运行并报错

07判定流水线

judge_turn（agent_loop/internals/judge_pipeline.py:57-145）按顺序短路：

层条件结果
0mark_completeACCEPT
0ctx.agent_spec.skip_judgeRETRY，feedback=None（不是真评估）
1自定义 JudgeProtocol完全交给它；RETRY 无 feedback 时补一句默认文案
2有真实工具结果RETRY，feedback=None（让 agent 继续干活）
2缺少 output_keysRETRY + Task incomplete. Required outputs not yet produced: […]
2全 nullable 且一个都没设RETRY + 提示至少设一个
2b有 success_criteria 且 LLM 可用跑 conversation-aware 质量判定；非 ACCEPT 则带反馈 RETRY

触发频率：should_judge = (iteration+1) % judge_every_n_turns == 0 or not real_tool_results；默认 judge_every_n_turns=1，所以主要在每个自然停点判定（agent_loop.py:3310-3314）。

08RETRY 如何进入对话

if verdict.action == "RETRY":
    _retry_count += 1
    if verdict.feedback is not None:
        fb = verdict.feedback or "[Judge returned RETRY without feedback]"
        await conversation.add_user_message(f"[Judge feedback]: {fb}")
    continue

agent_loop.py:3481-3502。注意 feedback=None 时不追加消息——这正是 skip_judge 和有工具结果两种情况的路径。

所以 judge feedback 真正进入模型视野的形态只有：

[Judge feedback]: Task incomplete. Required outputs not yet produced: ['report'].
Follow your system prompt instructions to complete the work.

它是普通 user 消息，不是 <system-reminder>；下一轮 LLM 请求开头就会看到。

09女王 / worker 上是否生效：Python 与 Go 一致（Go 2026-11-26 对齐）

Python：女王 runtime 的 AgentSpec 明确设了 skip_judge=True，judge 永远返回 RETRY(feedback=None)，只当“继续”，不会追加 [Judge feedback]。colony worker 也没有 output_keys/success_criteria，正常由 report_to_parent 提前终止。
位置证据
Python runtime specqueen_orchestrator.py:1665 — skip_judge=True
Python 静态 nodeagents/queen/nodes/__init__.py:772 — skip_judge=True
设计原因女王是 forever-alive 的对话 agent；用“你没输出/没调工具”的压力反馈会打断正常对话

Python：colony worker 上实际不跑 judge feedback

  • colony worker 继承 colony 的 AgentSpec：没有 output_keys、没有 success_criteria、skip_judge 保持默认 False。
  • worker 的正常终止路径是 report_to_parent：handler 设置 _report_terminated，下一迭代在 judge 之前提前退出（agent_loop.py:1797-1805）。
  • 即使 worker 没有 report 就自然停下，judge 看到的是 tool_results 为空、missing=[]、success_criteria=None → ACCEPT；不会注入反馈。
  • judge feedback 真正生效的是经典编排节点：声明了 output_keys / success_criteria，或注入了自定义 JudgeProtocol 的 node。SubagentJudge 是扩展点，默认未接线。

Go：2026-11-26 已移除 Go-only 的 colony goal criteria 继承

  • 2026-11-19 曾引入 Go-only seam：colony/runtime_worker_lifecycle.go（worker）与 colony/runtime.go（overseer）在 spec 没有 criteria 时，把 colony goal 的 SuccessCriteria 编译进 spec 并调用 ConfigureJudge；server/chat_runtime_colony.go 在绑定 colony 时对女王做同样的继承。
  • 2026-11-26（w195）已移除：worker/overseer 不再 GoalCriteriaText 回落、不再调用 ConfigureJudge；colony bind 不再继承 criteria。server/chat_runtime.go 的女王 spec 固定 SkipJudge=true，与上游 queen_orchestrator.py / 静态 queen node 同口径。
  • 因此 Go 的 colony 路径在自然停点不再跑 criteria judge，不会追加 [Judge feedback]；通用 Judge/ConfigureJudge API 仍保留给 graph-era 与显式调用方。
  • 显式 report_to_parent 同样不经过 judge：finishToolBatchTurn 的 batchStopsTurn 先返回，runJudgeStep 根本不会被调用；这一条在移除前后都成立。
  • plain DM queen 的 implicit RETRY 事件只是 wire/parity 事件，不会注入 feedback（server/chat_implicit_judge.go）。

两边共同点：judge 不是 worker 结果的监督器

真正监督 worker 结果的是：

  1. report_to_parent 的 required 字段（status / summary）与可选 report_schema（用于特化工具参数，provider 引导生成；handle_report_to_parent 本身只做归一化，不做 schema 校验）；
  2. queen 收到 [WORKER_REPORT] 后的复核、重派、stop_worker；
  3. playbook 的 retry / dead-letter 与 tracker 行状态；
  4. worker loop 预算（max_iterations、grace、tool budget、text-only streak → 合成 failed report）。

12历史脉络：为什么它会留在主路径之外

judge 不是为 queen/colony 设计的，它比这套架构更早。从 git 历史可以直接看出顺序：

当前设计文档也把这条边界写死了：docs/architecture/README.md:81 原文是

Agents that declare success criteria are checked by a judge before a turn is
accepted; a RETRY verdict comes back as a [Judge feedback] message ...
The queen skips the judge (you are her judge); workers end when they report.
准确结论：judge feedback 是历史遗留的通用机制，不是为 colony worker 设计的结果监督器。Python 的 queen/colony 主路径上它休眠：女王显式 skip_judge，worker 由 report_to_parent 先终止。但它不是死代码——经典 graph 执行器仍会构造 Orchestrator（host/execution_manager.py:713），AgentLoader 仍会把 goal 的 success_criteria 映射进 NodeSpec；Go 曾在 2026-11-19 通过 colony goal criteria 继承重新启用它，2026-11-26 已移除该 Go-only seam，现与 Python 同口径：女王 SkipJudge=true，colony 自然停点/显式 report 都不注入反馈；通用 judge API 保留给 graph-era/显式调用方。
