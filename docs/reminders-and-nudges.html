03线：8 条生命周期链路

点回答“这条规则是什么”；线回答“它什么时候、按什么顺序、和谁一起发生”。下面 8 条不是独立流程，而是同一个 loop 在不同故障下的走法。每条线都给出时序、步骤、不变量、失败分支和代码锚点。

turn

Turn 生命周期：一次模型调用被哪些点包围

SESSION_START
  → USER_PROMPT_SUBMIT（reminder 在用户消息之前）
  → model call
  → tool batch
  → POST_TOOL_USE
  → text-only? STOP
  → context threshold? PRE_COMPACT → compact → POST_COMPACT
  → stream stall? STREAM_STALLED

步骤：每个点只做一件事：SESSION_START 定向；USER_PROMPT_SUBMIT 注入上下文；POST_TOOL_USE 根据工具结果推进；STOP 检查计划；PRE/POST_COMPACT 保连续性；STREAM_STALLED 恢复传输。

不变量：reminder 在用户消息之前；所有 body 合并成一个 <system-reminder>；observe_turn 每 turn 一次；source 异常不拖垮 loop。

失败分支：某个点没有 source 时，模型仍能工作，但退化为“无提醒”；source 注册了但 provider 为空时必须 self-skip，而不是产出空 body。

代码锚点：agent_loop.py fire points · reminders.py ReminderHub · loop.go ResetTurn

park-idle

Park → idle → nudge / escalate → resume

turn end
  → park(reason)
  → IDLE_TICK
  → idle_nudge gates:
       user_stopped / external_wait / silent_park
       broken / awaiting / between_turns / slow_ttft
  → cap / rate-limit
  → nudge body
  → drain / resume

colony queen + opt-in:
  → sentinel_escalation
  → classify(continue / needs_human / done)

步骤：park 先落 reason；idle tick 周期轮询；idle_nudge 按 substate 选预算；Sentinel 只对 colony queen + opt-in 接管；drain 后回到 loop 边界。

不变量：user_stopped 不自动恢复；external_wait / silent_park 不打扰；cap 按“用户回复周期”重置；broken park 用更短预算。

失败分支：TURN_DONE + 无 open task 应保持安静；cap 用尽后等待下一条用户消息；Sentinel 开启时 idle_nudge 让位，不能双推。

代码锚点：idle_nudge.py · chat_runtime.go:968 reset · sentinel_runtime.go · escalation_source.py

tool-result

工具结果 → 计划 / tracker / fleet

POST_TOOL_USE
  ├─ tasks: drift / untracked / stale
  ├─ colony_parallel: pilot + tracker write
  ├─ tracker_snapshot: queen table state
  ├─ worker_tracker_snapshot: worker cadence 20
  └─ searchable_tools / skills_catalog: discovery

TOOL_BUDGET_CHECKPOINT
  └─ colony_worker_snapshot: active/total fleet

步骤：工具结果回填后统一进入 POST_TOOL_USE；任务源看计划漂移；并行源看 pilot + tracker 写入；tracker 源看表状态；worker 源按工具调用节奏；fleet 源在预算检查点。

不变量：tracker 写入是 colony_parallel 的“完成一条”信号；没有表时 tracker 源 self-skip；worker cadence 不被空表消耗；fleet 快照最多 8 个 worker。

失败分支：worker 的 tasks 源已绑定 workerDir/workerID；overseer 已绑定 overseerTaskSet，生产测试覆盖；不再有“注册了但不会产出”的 tasks 缺口。

代码锚点：tracker_snapshot_reminder.py · colony_parallel_nudge.py · worker_reminders.go · tasks/reminders.go

stream-stall

Stream stall 恢复：传输故障不等于模型失败

stream open
  → TTFT > 600s 或 inter-event > 120s
  → watchdog cancels stream
  → *llm.StreamStalledError
  → injectStreamStallNudge
  → WrapReminder
  → inner--; continue（重跑同一 inner turn）

cap: ≤3 / turn
reset: ExecuteTurn 开头

步骤：看门狗只负责判定和取消；loop 负责注入 reminder 并重跑；source 只产出 body；cap 防止一个坏流烧光整回合。

不变量：不换 turn、不重跑整个任务；cap 按 turn 重置；TTFT 与 inter-event 是两个独立预算。

失败分支：worker/overseer 已接共享流式 watchdog；真实网络 worker/overseer serve E2E 仍需单独验证，不能把 fake provider 测试当生产证据。

代码锚点：stream_stall.py · streaming_completer.go · stream_wiring.go · loop.go · stream_stall_recovery.go

compaction

Compaction：上下文压缩后的再定向

context threshold
  → PRE_COMPACT（当前没有 source）
  → compact
  → POST_COMPACT
  → tasks：重读计划
  → memory_recall / memory_index：重放记忆
  → searchable_tools / skills_catalog：重放目录

步骤：压缩前 hook 已存在；压缩后由 tasks / memory / tools / skills 重新公告；past_conversations 已在 hub（dfbf65b2），不再由 runtime 外挂。

不变量：task list 从 store 重新读；memory mode 决定 index/wait；同一个 catalog 不重复公告；past 的包装/顺序与 hub 一致。

失败分支：PRE_COMPACT 没有 source；worker tasks / idle open-task 的 provider/store 缺口已关闭（w87/reminders-residual）。

代码锚点：agent_loop.py PRE/POST_COMPACT · chat_memory_wiring.go · tasks/reminders.go

user-message

用户消息 → 上下文注入 → 模型

user message
  → reset idle caps
  → active_workers
  → past_conversations
  → memory_recall / memory_index
  → turn_context
  → searchable_tools / skills_catalog
  → one <system-reminder> before user message
  → model

步骤：每条用户消息先重置 idle cap，再按 provider 注入并行工作、旧对话、记忆、时间/账号、工具/技能目录；最后合并成一个 reminder 块。

不变量：reminder 在用户消息之前；provider 为空时 self-skip；不产生用户气泡；不让 source 直接写 conversation。

失败分支：worker context 已接 OpenTasksProvider / SessionGoalProvider；worker tasks 绑定私有 store；past 已进 hub（dfbf65b2），不再是缺口。

代码锚点：chat_reminders.go · chat_memory_wiring.go · worker_reminders.go · reminders.py wrap_reminder

worker-failure

Worker 失败 / 升级：三个 stall 不是一件事

text-only turn
  → grace 2
  → parallel worker? synthesized failed report
  → legacy worker? ESCALATION_REQUESTED + park
  → stall_check? judge reminder
  → doom-loop? breaker blocks the call

步骤：worker_stall 是 turn 级策略；stall_check 是 judge；doom-loop 是 breaker；三者都在 ReminderHub 之外，不能混成 nudge。

不变量：任何工具调用都算 progress；parallel worker 不发 escalation，直接 failed report；legacy worker 才 park 等 queen；stall_check 每条用户消息最多一次。

失败分支：worker task reminder 与 worker idle open-task 已由真实 worker 路径测试证明；结构门禁全绿仍不能替代功能门禁。

代码锚点：worker_stall.go · stall_check.py · stream_stall.py · worker_escalation.go

sentinel

Sentinel：停车后的分类、升级、恢复

colony queen park
  → classify_after 300s
  → classify:
       continue  → nudge
       needs_human → escalation
       done      → close
  → channel: hive / telegram / slack
  → human reply
  → token → resume

步骤：Sentinel 只在 colony queen + opt-in 时工作；source 在 IDLE_TICK 产出分类请求；manager 负责分类、记录、投递、token 路由和 resume。

不变量：硬阻塞（认证/崩溃）在 classify 之前决定；最多 5 次 nudge 后升级；escalation 有盘上记录；人回复按 token 恢复。

失败分支：未知 channel 会报错；source 注册不等于投递可用；OSS 前端没有 escalation 历史/收件箱 UI。

代码锚点：escalation_source.py · sentinel/manager.py · sentinel/store.py · routes_sentinel.py

五种观察角度

同一个系统，不同角色看到的东西不一样；这决定了“谁应该负责什么”。

角度看到什么看不到什么含义
模型视角一条 <system-reminder> 文本；不知道是哪个 source 产出的。source 的身份、cap、provider、注册矩阵。body 必须自包含；不能依赖“模型记得这是第几次提醒”。
source 视角points / applies_to / render / observe_turn / tick_interval。loop 的内部状态，除了 ReminderContext 暴露的 signals、tool_names、user_text。source 不能直接写 conversation；只能返回 body，由 hub 统一包装。
loop 视角observe_turn / collect / fire / reset / pending drain。source 的业务细节；它只按 point 和 applies_to 调用。新增 source 不改 loop；只注册 + 实现接口。
运维视角reminder_injected、stream_*、execution_*、日志、测试。模型是否真的照做；只能看“注入了什么”。需要功能 E2E 和真实转录，不能只看事件计数。
Go 视角注册表、ticker、provider、store、真实触发面。上游 source 的隐含语义；必须逐条对照。注册 ≠ 工作；结构门禁 ≠ 功能门禁。

07不在 ReminderHub 里的守卫

下面四个经常被混进 nudge，但它们是独立机制；把它们算进 15 个 source 会导致“看起来对齐、实际职责错了”。

机制是什么为什么独立
worker_stallworker 连续 text-only turn，没有工具调用；grace 2 后：parallel worker 合成 failed report 终止，legacy worker 发 ESCALATION_REQUESTED 并 park。这是 turn 级策略，不是 ReminderHub source；它决定“这个 worker 该失败/该找人”，不是“注入一段上下文”。
stall_checkjudge 判断“说了没做”：回合宣称/承诺动作却没调用工具就收尾；概率 ≥ 0.5 时注入一次提醒。需要 judge 模型和阈值，且每条用户消息最多一次；不是 source 的 applies_to 能表达的。
doom-loop breaker相同工具 + 相同参数反复调用；breaker 阻断该调用，注入“换条路”的引导。阻断的是调用本身，不是提醒；它先于 reminder 发生，避免把坏调用继续喂给模型。
Sentinel managercolony queen park 后分类 continue / needs_human / done；escalation 记录、投递、token 路由、人回复后 resume。source 只负责在 IDLE_TICK 产出“该分类”的提醒；真正的分类、投递、恢复是 manager 的职责。

08为什么会有这些？

因为一个长生命周期 agent 有五种不同故障模式：等待恢复、上下文连续性、上下文经济、多 agent 协调、人机接管。每个 source 只覆盖一种，组合起来才是完整的注意力系统。

设计原则解释
一个 hub，按角色过滤queen DM、colony overseer、worker 共用 AgentLoop；每个 source 用 applies_to 自报“我属于谁”，避免三套 loop 各写一遍。
生命周期点，不是到处轮询source 只声明 points；loop 在 SESSION_START / USER_PROMPT_SUBMIT / POST_TOOL_USE / POST_COMPACT / STOP / IDLE_TICK / STREAM_STALLED 等已知点调用，时序可测。
cap 与 cooldown每个 source 自己限速；没有 cap 的提醒会变成 wallpaper，模型会学会忽略。
上下文经济工具 schema、skill 目录、记忆 manifest 都很大；searchable_tools / skills_catalog / memory_index 只公告“现在相关”的部分。
advisory wrapper所有 body 合并后包成一个 <system-reminder>；模型可忽略，不污染用户消息，也不假装是用户指令。
可观测 + 失败隔离reminder_injected 事件记录 source / substate / nudge 计数；source 的 applies_to / render 抛异常只跳过该 source，不拖垮 loop。
守卫与自治分开stream stall / stall check / doom loop 是三种不同守卫；worker_stall 是 turn 策略；Sentinel 是停车 supervisor。不要把它们都叫 nudge。

关键 tradeoff

选择为什么代价
拆成 15 个 source每个 source 的触发条件、状态、cap、文案都不同；拆开才能独立测试、独立调参、独立关闭。注册矩阵和角色过滤更复杂；新增 source 要补 provider、测试、文档。
nudge 推自己，escalate 找人能自己恢复的不要打扰人；真正需要人的才升级。分类错误会导致该找人时自己空转，或该自己干时过早打扰。
cap + cooldown没有限速的提醒会变成 wallpaper，模型学会忽略。极端情况下会少推一次；所以 cap 按用户回复周期重置，而不是整个会话。
一个 hub，按 applies_to 过滤queen DM、overseer、worker 共用 AgentLoop；避免三套 loop 各写一遍。source 必须正确实现 applies_to；provider 为空时要 self-skip。
部分机制放在 hub 外worker_stall 是 turn 策略；stall_check 是 judge；doom-loop 是 breaker；它们不是“注入一段上下文”。对齐时要跨文件审计，容易把“注册了”误当成“完整”。
上下文经济工具 schema、skill 目录、记忆 manifest 都很大；只公告相关部分。发现性下降；需要 searchable_tools / skills_catalog 的 phase 过滤。
fail-opensource 的 applies_to / render 抛异常时，不能静默丢掉所有提醒。坏 source 可能反复失败；需要日志和测试兜底。
结构门禁 + 功能门禁分开注册/ticker 只能证明接线；真实注入要跑会话。CI 更慢；但能避免“全绿但 worker 不工作”的假绿。
仍然要盯住的误判：“注册了”不等于“工作了”。本分支已把 worker/overseer 的 tasks 与 worker idle provider 接到真实 store/session，并用真实 worker/overseer loop 测试兜底；新增 source 时仍要补功能测试，不能只加注册断言。
