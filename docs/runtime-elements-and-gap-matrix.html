01根：只有一个执行原语

理解全部元素的关键（出自 docs/key_concepts/the_loop.md）：

Hive has exactly one execution primitive: the agent loop.
The Queen IS an agent loop. Every worker is a CLONE of that same loop.

所以元素只有两类：

  • loop 内部的器官——stall 检测、park、judge、compaction、reminder…… 每个都在治 单 loop 自身的一种失效；
  • loop 之间的底座——colony、tracker、plan、event bus、reminder hub、sentinel、trigger…… 每个都在治 多 loop 并存的一种失效。

一个一次性任务和一个长期业务看门人，是同一个 loop 配不同参数。

04为什么是这些元素

所有元素都能归到三个物理约束上。这是最有用的视角。

4.1 族一：流式 LLM 不可靠 → 五种「卡住」必须分治

「stall」在这套系统里指五件不同的事。把一个判据盖五种，要么漏报要么烧钱——因为判据的性质不同：I/O 事件（确定性、零成本）、语义（一次 LLM 调用）、文本相似度（零成本）、调用结构（零成本）、角色契约（确定性）。
#名字触发条件谁判后果
1STREAM_STALL / stream_stalled通道没字节了（TTFT / 事件间隔超时）看门狗（确定性）取消该流、重流同一轮 + 同步注入提示（不可延到下一轮）
2stall_check模型说要干、但结束回合没调任何工具LLM judge注入 REMINDER，不发布事件（node_stalled 属 doom-loop）
3is_stalled（n-gram）最近几条回复互相相似（≥ 阈值）纯函数，无模型调用发布 NODE_STALLED + continue；一条不相似就重置
4doom loop连续 N 轮工具集完全相同（turn 级指纹，顺序敏感）纯函数发布 NODE_TOOL_DOOM_LOOP；可 park（ParkReason.DOOM_LOOP）
5worker text-only stallworker 连续 N 轮只说话不调工具确定性并行 worker → 合成 report_to_parent(failed) 终止；legacy worker → ESCALATION_REQUESTED 等 Queen

Go 侧现状：1 中 stream_stall、2、3、5 均已移植；3 走 agentloop/stall_detector.go（NgramSimilarity / IsResponseStalled）并已接线 ExecuteTurn 6f；4 有，但粒度为单调用 streak（warn 3 / park 5）而非 turn 级指纹窗口，且无 replay_exempt_tools 豁免表。见 §07 P0。

4.2 族二：长会话会失忆、会漂移 → park 11 值 + reminder + compaction

单个 awaiting_input 布尔有两个盲点：分不清「正常等待」与「卡死」；分不清「用户自己按了停」与「崩了」。于是每个 _await_user_input 调用点必须声明原因，并用三个视图收敛给消费者用：

ParkReason分类含义activity 映射
ASK_USERis_external_waitagent 调了 ask_user，等你回答AWAITING_USER
CREDENTIAL_FORMis_external_wait等安全凭据表单AWAITING_USER
COLONY_SUGGESTIONis_external_wait等你确认建 colonyAWAITING_USER
AWAITING_QUEENis_external_waitworker 升级了，等 Queen 指引AWAITING_USER
TURN_DONEis_silent_park干净地结束了一轮AWAITING_USER
USER_STOPPEDis_silent_park你点了 Stop / 取消了这一轮INTERRUPTED
COLD_INTERRUPTEDis_silent_park运行时死时 Queen 正在轮中；重载后在冷态停AWAITING_USER
LLM_ERRORis_brokenLLM 调用失败INTERRUPTED
EMPTY_RESPONSESis_broken连续空轮INTERRUPTED
DOOM_LOOPis_broken工具 doom loopINTERRUPTED
UNKNOWN—没记原因的 park（出现即是 bug）INTERRUPTED

三个视图就是给不同消费者用的——例如 idle nudge 只敢碰 is_broken：碰「等你在回」没意义，碰「你自己按了停」会覆盖你的自然停顿。而 ParkReason.activity 是唯一把「原因」变成「顶层状态」的地方（避免两处各自推导）。

InterruptCause 补上非 park 的中断：STREAM_STALL（看门狗触发）、CRASHED（execute 异常退出）、STALE（超过失联窗口无事件）。

4.4 族三：多 loop 并存会互相踩 → 四个底座

没有工作流图，就必须有东西替代「边」和「共享数据缓冲」。答案是四个性质不同的底座：

底座性质不是另外三个的原因存储
Plan意图，可变计划会变；tracker 是审计面。混用 → 「计划看起来全做完了，但没人知道实际发生了什么」tasks.json
Tracker事实，持久，可查它是持久共享状态；event bus 是瞬时信令，不能当账本tracker/tracker.db
Event bus瞬时信令不持久，换不来「现在到底完成了多少」内存 + events.jsonl
Reminder hub注意力，由框架写不是事件：它不报告「发生了什么」，而是决定「现在该注意什么」注入对话，不落盘
最反直觉的一条设计主张（coordination.md 原文）：workers never message each other。它们不互相通话，只往 tracker 写行，Queen 之后读。这就是「没有图」却能协作的全部机制。配套的是 Binding：「没有 binding 的工具拒绝运行，而不是猜一个路径」——这才是两个 colony 不会写到对方账本的真正原因。
