Hive 设计与实现：一个原语 · 三个角色 · 四块基底

Hive 不是 DAG/工作流引擎，也不是“很多 agent 的聊天群”。它只有一个执行原语 AgentLoop；Queen 是它，Worker 是它的克隆，Colony 是这些 loop 的部署单位。本文从设计原则、角色、一次 turn、共享基底、长期层，到 Python 参考实现与 Go 移植，给出一张可落盘的架构地图。

先记住一句话：Hive 的设计是“一个原语，多个设置”。Queen 不是另一种程序，Worker 也不是另一种程序；它们是同一个 loop 在不同 prompt、工具子集、预算和组织位置下的实例。Colony 不画图，它提供一个目录和四块共享基底，让 loop 在运行时生长。

01设计原则：为什么长这样

这八条不是口号，而是代码里能观察到的约束。它们也解释了为什么 Hive 没有 workflow DSL、没有 worker 间消息总线、没有向量数据库。

#原则是什么为什么
1一个执行原语AgentLoop 是唯一的执行状态机；Queen 是它，Worker 是它的克隆。Worker 不需要第二套运行时。预算、工具执行、事件、持久化、提醒都在同一条 loop 语义里，行为可比较、可测试。
2运行时组织，不预设图Colony 不维护 DAG、边、节点或 data buffer；Queen 先做，发现需要并行才 spawn。真实业务流程的形状常常在开工前未知。先画图会把组织僵化在一次猜测上；Hive 把拓扑留到运行时。
3先打样，再系统化execute first, then systematize：先跑通一条路径，再固化成 skill + playbook。避免为了“平台化”先造抽象；只有被证明有效的路径才值得变成可复用程序。
4状态在文件/数据库里会话、计划、tracker、memory、soul、skills 都落盘；进程只持有执行中的临时状态。可审计、可迁移、可跨语言复刻，也能在进程崩溃或长时间停车后恢复。
5角色能力故意不对称Queen 拥有对话、计划、记忆和人的回路；Worker 没有记忆、没有人设、没有 escalation。Worker 要短命、可替换、失败快；需要判断和等人时交回 Queen，避免每个 worker 都变成一个小组织。
6信号与账本分离EventBus 是神经，Tracker 是账本；事件可以重放/丢弃，tracker 行是业务真相。把实时通知和持久事实混在一起，故障恢复时就不知道信谁。
7失败快、可恢复Worker 有 grace iteration 和 report_to_parent；Queen 提问会 park 落盘；写盘走原子 rename。长任务一定会遇到失败和等待；设计目标是“失败可见、状态可恢复”，不是“永不失败”。
8双实现、行为对等Python 1.0.15 是参考实现；Go 是移植，文件格式、prompt、错误文案尽量逐字一致。同一棵 HIVE_HOME 应能被两边读取；`// Parity:` 测试把“像”变成可审计的映射。
非目标：不是通用 BPMN/DAG 引擎；不是“全自动无人组织”；不是用向量库替代可读文件；不是为了跨平台而引入 cgo。把这些非目标记住，很多“为什么没有 X”就有答案。

02三个角色：Queen / Worker / Colony

角色不是三个进程，而是同一个 loop 的三种组织位置。Queen 是持久的主管，Worker 是短命的克隆，Colony 是容纳它们的目录与共享基底。

角色是什么拥有什么故意没有什么代码锚点
Queen有身份的主管，也是 colony 唯一对外对话面。对话、持久计划、tracker 读写、需要人拍板的问题、memory/soul、12 个生命周期工具。不直接替 worker 执行所有任务；不把 colony 拓扑写死。core/framework/agent_loop/agent_loop.py · agents/queen/queen_profiles.py · tools/queen_lifecycle_tools.py
WorkerQueen loop 的克隆，注入一个任务和 worker prompt。一个任务、一个工作区、一个 report_to_parent；可写 tracker 行、可加载 colony skills。无记忆、无人设、无 escalation、不能派发自己的 worker；终止必须汇报 success/partial/failed。core/framework/host/worker.py · agents/queen/worker_definition.py
Colony一个目录 = 一个部署单位，也是一台“多 loop 组织”。共享 tracker.db、任务计划、event bus、reminder hub、skills、triggers、worker 绑定。没有图、没有边、没有节点、没有 data buffer；worker 之间不直接通信。core/framework/host/colony_runtime.py · colony_binding.py · tracker_db.py
关键不对称：Queen 拥有“人的回路”（提问、park、Sentinel、memory/soul）；Worker 故意没有这些。Worker 的终止动作是 `report_to_parent`，不是继续扩展组织。Fan-out 属于 Queen，不属于 Worker。

03一次 turn 是怎么走的

同一个 AgentLoop，在 Queen 和 Worker 上走同一条主链；差别在 prompt、工具子集、预算和“停车后谁来接”。

步骤发生什么写到哪里失败边界
1. 接收用户消息进入 session；冷会话从 parts/state 恢复，colony 会话绑定 colony。session state、conversation parts、binding未知会话 404；colony_spawned 的 DM 会话被锁，必须新开。
2. 组装静态前缀identity → soul → phase base prompt；soul 只在启用且非空时渲染。queen profile、soul.json、phasesoul 关闭/损坏读作空；identity 永远优先于 soul。
3. 注入提醒ReminderHub 在当前 point 收集 source 产出；合并成一个 `<system-reminder>`。tasks、memory manifest、skills catalog、worker/tracker snapshot单个 source 失败不应阻塞主对话；注入内容未变不重复。
4. 模型LLM 读取 prompt + 工具 schema，返回文本或 tool calls。Completion（内容、tool calls、usage）流卡住由 stream stall 看门狗处理；模型失败走 loop 的错误/停车路径。
5. 工具批执行 tool calls，结果回填；工具预算、超时、沙箱边界在这里生效。tool results、tracker 行、文件、浏览器状态工具错误作为结果回给模型；结构性失败要修，不可修要停。
6. 事件与落盘发布事件；transcript、state、checkpoint、memory 反思按策略写盘。events.jsonl、state.json、parts、memory logEventBus 不是账本；写盘失败必须暴露，不能静默假装成功。
7. 停车或继续text-only 回合可 STOP；提问则 park；静默由 idle nudge；无人值守由 Sentinel。park reason、idle state、Sentinel 决策park 要能等数天；没有 Sentinel 时，问题会一直等人。
注意：EventBus 发布成功不等于业务成功；真正的验收在 tracker/SQL。一次 turn 的“完成”是状态机事件，不是模型说“done”。

04四块共享基底：神经、账本、意图、注意力

Colony 里所有 loop 共享这四块，但它们回答的问题不同。把它们混在一起，是理解 Hive 最常见的错误。

基底回答什么问题谁写 / 谁读失败边界代码锚点
Tracker什么做了、什么没做；一行一个工作单元。Worker 写行；Queen 用 SQL 验收/读取。缺 binding 时工具拒绝执行，不猜路径；避免两个 colony 写错账本。core/framework/host/tracker_db.py · go_hive/go-hive/internal/tracker
Task plan接下来要做什么；持久任务表，跨 compaction 存活。Queen/agent 的任务工具；worker 有私有 task store。计划漂移要由 reminder 拉回；task 工具不是 tracker 的替代品。core/framework/tasks · go_hive/go-hive/internal/tasks
EventBus发生了什么；实时信号、worker 报告、UI 流。AgentLoop/worker/colony 发布；handler、SSE、events.jsonl 消费。事件不是账本；丢失不能作为业务真相丢失的理由，tracker 仍要能查。core/framework/host/event_bus.py · go_hive/go-hive/internal/eventbus
ReminderHub现在该把什么注意力拉回来；在生命周期点注入 source 的产出。各 reminder source 按角色/phase 注册；hub 合并成 system-reminder。结构注册不等于功能注入；需要真实链路测试，尤其是 worker/overseer。core/framework/agent_loop/reminders.py · go_hive/go-hive/internal/agentloop/*reminder*
不要把 EventBus 当账本：事件是“发生了什么”的实时信号，可以重放、可以丢；tracker 行才是“什么做了、什么没做”的唯一真相。恢复时先查 tracker，再看事件。

05长期层：Memory / Soul / Skills

这三层让 Queen 跨会话保持连续，但它们都不是模型权重：都是文件 + prompt 注入。Worker 完全不参与。

层是什么怎么实现边界代码锚点
Memory跨会话的事实层：纯 `.md` 文件，按 global/colony/queen/worker 分作用域。反思写入；recall 以 `<system-reminder>` 注入；index/wait/background 三模式；每作用域 200 文件、单文件 4 KB。不是向量库；只有 global + 本 queen 自动召回；worker 不参与。core/framework/agents/queen/queen_memory_v2.py · go_hive/go-hive/internal/memory
SoulQueen 对自己的第一人称叙事，注入静态 system prompt 的 `<soul>`。每天从聊天反思；默认 review，提案需批准；evidence 必须逐字来自读过的对话；有 history/rollback。identity 在 soul 之前；soul 不能覆盖身份。Go-only sediment 会把 memory 结论写进 soul，绕过 review。core/framework/agents/queen/soul.py · soul_reflection.py · go_hive/go-hive/internal/soul
Skills打样后固化的方法：`SKILL.md` + 作用域发现 + 信任/覆写。Queen 先做 pilot，再 `write_skill`；worker 可加载 colony skills；热重载。skill 不是任务状态；tracker 才是断点，playbook 重跑靠 tracker 续跑。core/framework/skills · go_hive/go-hive/internal/skills
一句话区分：Memory 是“事实”，Soul 是“自我叙事”，Skills 是“方法”。Memory 可以被 owner 编辑/删除/恢复；Soul 默认 review，有 evidence 和 history；Skills 是打样后固化的程序性知识。

深挖：Memory & Soul（存储/召回/反思/故障） · Skill Discovery（扫描面）。

06质量与自治：Judge / Stall / Sentinel / Park

这些机制不增加“智能”，它们负责在合适的时候说“不对”“还没做”“该找人了”。

机制做什么何时失败边界代码锚点
Judge成功标准判定：ACCEPT / RETRY / ESCALATE。worker/agent 输出后，按 judge cadence。judge 槽不可用时不能伪造通过；按配置/调用方策略降级。core/framework/server/judge.py · internals/judge_pipeline.py
Stall check抓“说了没做”：Queen 声称完成但实际没有工具/状态支持时提醒一次。用户消息回合；每条用户消息最多一次。这是提醒，不是自动改状态；真正验收仍看 tracker/SQL。core/framework/server/stall_check.py
Sentinelcolony 无人值守时的 supervisor：continue / needs_human / done。park/idle 后，按 colony 开关和间隔。没有配置通道时只能停在本地；升级通道是另一条投递链。core/framework/sentinel · go_hive/go-hive/internal/sentinel
Park / idle提问即停车，状态落盘；静默时 idle nudge 推一下；流卡住时 stream stall 重跑同一 inner turn。STOP / IDLE_TICK / STREAM_STALLED。park 是持久等待，不是 sleep；没有唤醒源就永远等人。core/framework/agent_loop/idle_nudge.py · stream_stall.py
Park 不是 sleep：park 会把状态落盘，可以等数天；唤醒来自用户回复、trigger、Sentinel 或 worker report。没有唤醒源，park 就是永久等待。

08Go 移植：不是重写设计，是对等实现

Go 侧的目标是“同一棵 HIVE_HOME 两边可读、同一行为两边可测”。外部行为优先于 Go 惯用法；核心处严格，边界处宽松。

层Go 包对应/说明
执行原语go_hive/go-hive/internal/agentloopAgentLoop/LoopConfig/park/reminder/judge 接线；Go 侧唯一执行原语
Colony / Workergo_hive/go-hive/internal/colonyColonyRuntime、worker spawn、overseer、playbook、binding
Memory / Soulgo_hive/go-hive/internal/memory · internal/soul文件记忆、反思、召回、timeline；soul 反思/sediment
事件go_hive/go-hive/internal/eventbus进程内 pub/sub；事件类型、持久化、handler 扇出
账本 / 计划go_hive/go-hive/internal/tracker · internal/tasksSQLite tracker、任务表、工具
服务 / CLIgo_hive/go-hive/internal/server · cmd/hiveHTTP/SSE、ChatRuntime、CLI、embedded UI
LLM / 工具go_hive/go-hive/internal/llm · internal/toolsprovider 纯逻辑/传输、工具注册与执行

Go 侧四条实现约束

  • 纯 Go / 无 cgo：六个平台可交叉编译；SQLite 用 modernc.org/sqlite，不依赖系统库。
  • 单写者 + 原子写：文件走同目录 temp + fsync + rename；SQLite 连接池单写者，换可预测的 WAL 行为。
  • 宽松读、严格写：损坏的缓存/索引读作空或跳过，不因缓存丢主数据；写出去的数据必须满足 schema。
  • Parity 是门禁：每个测试用 // Parity: 指向 Python 测试；没有对应物时用 // Parity-exempt: 写明理由。
边界：Go 不是逐行翻译。Python 的 duck typing/dict 保序/str() 语义会用 Go 结构体、有序 map、兼容助手显式实现；差异必须可观测、可测试。

09设计 trade-off：为什么不是另一种架构

每个“没有”都有代价。下表把收益和代价放在一起，避免只讲优点。

选择得到什么付出什么
不预设 DAG组织可以按真实流程生长；Queen 先打样，再决定 fan-out。协调是隐式的：没有静态边可检查，必须靠 tracker/任务/事件和真实 E2E。
Worker 无记忆/无 escalationworker 短命、可替换、失败快；不会把错误人设/记忆扩散到所有执行单元。worker 没有跨任务连续性；上下文必须由 Queen 在任务里重新给。
文件式 memory可读、可审计、可迁移、可跨语言复刻；不需要向量库。没有语义检索；陈旧/错误事实会占位，质量靠反思和 owner 审计。
EventBus 只做信号解耦实时消费者；UI/worker/reminder 可以各自订阅。不能把事件当账本；业务真相必须落到 tracker/SQL。
prompt + 工具驱动行为灵活，新增能力主要是加 prompt/工具，不是改状态机。行为依赖模型；结构测试不能代替真实模型 E2E。
Python 参考 + Go 移植同一棵 HIVE_HOME 两边可读；行为有可审计的 parity 映射。Go 受纯 Go/离线/无 cgo 约束；某些 Python 语义要手写兼容助手。

10故障边界：出问题时信谁

架构的可靠性不取决于“永不失败”，而取决于失败时状态是否可见、是否可恢复。

故障机制边界/恢复
Worker 失败Worker 有 grace iteration；即使预算耗尽，最后仍放开 report_to_parent/task_update/tracker_upsert 收尾。report 三态：success / partial / failed；Queen 不用猜。
Queen 提问提问即 park，状态落盘，可等数天；用户回复后恢复。没有 Sentinel/唤醒源时，问题会一直等人。
Colony 绑定缺失tracker 工具拒绝执行，要求显式 colony_id 或 tracker_db_path。绝不猜路径；避免写错账本。
事件丢失事件不是账本；tracker/state 才是恢复依据。关键业务结果必须落行，不能只发事件。
上下文压缩压缩会丢旧消息；memory 不参与摘要，压缩后 long reflection 尝试沉淀。反思失败时可能丢学习；需要 pending/retry 设计。
Memory/Soul 漂移memory 有 owner guard/log/restore；soul 有 review/evidence/history。auto/sediment 会绕过人工 review；见 memory-and-soul 的故障分析。
Go 行为漂移`// Parity:` 注解 + parity 门禁 + 双跑。结构注册通过不等于真实链路通过。
最容易被忽略的边界：结构注册（source/tool 已注册）不等于功能链路（真的注入/真的执行）。验证必须走到真实模型或真实 worker，而不是只数注册表。
