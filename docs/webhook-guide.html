Webhook 使用手册

目标读者：想在 Hive 里用“外部事件叫醒 queen”的用户。本页只讲怎么用；字段类型、状态码逐字文案见 triggers-webhook.html。

01先搞清楚：触发器归属于谁？

  • 归属 = 会话（session）：触发器定义保存在该会话的 worker 目录 triggers.json，不是独立全局对象，也不存在“绑定到某个 colony 的触发器库”。
  • 运行条件 = 该会话已加载 colony：webhook 事件到达时，若 session.colony_id 为空（上游）/ Session.ColonyID == ""（Go）→ 事件被静默丢弃；queen 节点不存在同样丢弃。
  • 注入目标 = 该会话的 queen；若该 colony 有常驻 overseer，同一 trigger 会再转发一份给 overseer（第二负责人），避免 queen 无输入源。
  • 创建入口 = queen 的工具 set_trigger（在会话内由 queen 调用）。REST 创建接口与 Dashboard “Create schedule”只支持 timer（上游逐字：Only 'timer' schedules can be created here.）；没有 hive session trigger 这类 CLI 子命令。

02使用前提

  1. hive serve 正在运行（默认 127.0.0.1:8788）。
  2. 打开（或已存在）一个加载了 colony 的会话——从 Dashboard 打开、能与 queen 正常对话的会话即满足。
  3. 知道 session_id（Dashboard URL 或 GET /api/sessions），后续查询/运维要用。

03创建 webhook 触发器（唯一正确姿势）

在该会话的聊天框里对 queen 说（让它调用工具）：

请调用 set_trigger 创建一个 webhook 触发器：
- trigger_id: ci-fix
- trigger_type: webhook
- trigger_config: {"path": "/hooks/ci", "methods": ["POST"]}
- task: "CI 失败时：读取 payload.run_id 与 payload.repo，拉取失败日志，定位并尝试修复，最后在会话里汇报结论。"
参数类型必填说明 / 错误语义
trigger_idstring是会话内唯一；已激活时返回 Trigger '<id>' is already active.
trigger_type"webhook"新建时必填已有同 id 定义时可省略（沿用原类型）
trigger_config.pathstring是必须以 / 开头，否则 Webhook trigger requires 'path' starting with '/' in trigger_config (e.g. '/hooks/github').
trigger_config.methodsarray<string>否默认 ["POST"]；合法集合 GET/POST/PUT/PATCH/DELETE/HEAD/OPTIONS
trigger_config.portinteger否默认 8090；host 固定 127.0.0.1（多会话需配不同端口）
taskstring激活前必须非空为空返回 Trigger '<id>' has no task configured…；激活成功即写盘并开始监听

创建成功后：定义写入会话 triggers.json（enabled=true），本会话的 webhook 服务在 127.0.0.1:8090 惰性启动并注册 path → (trigger_id, methods)。

04确认与观察

  • 列表：GET /api/sessions/<sid>/triggers → 返回 trigger_id / trigger_type / trigger_config / enabled / last_fired_at / next_due_at 等。
  • UI：Colony 面板触发器区块（webhook 用闪电图标）；触发后聊天里出现 banner「Webhook fired」+ 以 [TRIGGER: webhook/<id>] 开头的用户消息。
  • 事件：成功后发布 trigger_fired（含 trigger_id / trigger_type / name / task / last_fired_at / fire_count，timer 另有 next_fire_in / next_fire_at）；SSE 订阅者可见。

05发送一条测试请求（端到端）

curl -i -X POST http://127.0.0.1:8090/hooks/ci \
  -H 'Content-Type: application/json' \
  -d '{"run_id":123,"repo":"myapp","status":"failed"}'

期望：

  1. HTTP 202 {"status":"accepted"}（只表示已接收，不代表任务成功）；
  2. 几秒内该会话出现触发消息（banner + [TRIGGER: webhook/ci-fix]…），queen 开始一轮工作；
  3. 列表接口 last_fired_at 更新、fire_count +1，并收到 trigger_fired 事件。

调试时也可不走 HTTP：POST /api/sessions/<sid>/triggers/<tid>/run → {"status":"fired"}（payload 为 {task, trigger_config, forced:true}）。

06运维操作（REST）

操作请求返回
列表GET /api/sessions/<sid>/triggers触发器数组
激活POST …/triggers/<tid>/activate{"status":"activated"| "already_active","trigger_id":…}
停用POST …/triggers/<tid>/deactivate{"status":"deactivated"| "already_inactive",…}
手动触发一次POST …/triggers/<tid>/run{"status":"fired"}
更新 taskPATCH …/triggers/<tid>更新后的 task/trigger_config
timer 错过决策POST …/colony/resolve_missedfire_latest / skip / reschedule

细节：停用只取消订阅（webhook 路由仍注册）——之后请求仍回 202，但不会触发 queen；重新激活会重新订阅。会话重开时，enabled 的定义会恢复并重新注册 webhook route（timer 则把错过的 tick 标为 missed，不自动补跑）。

07task 怎么写（决定成败的一半）

  • 明确引用 payload：写清用哪些字段（如 payload.run_id），queen 会在消息里看到完整 JSON。
  • 给出处理顺序与验收：例如「拉日志 → 定位 → 修复 → 跑测试 → 汇报」。
  • 幂等与去重：同一事件可能重复投递（无去重），task 里要求按 run_id 判重或只处理最新一次。
  • 不假设有回复通道：调用方只拿到 202；结果写回会话/需要时由 queen 调外部 API。

08部署与安全（重要）

  • 服务只监听 127.0.0.1：同机进程可直接 POST；GitHub 云端等外部服务需经 self-hosted runner 或隧道/反代（Cloudflare Tunnel、nginx）。
  • 内置 HMAC 鉴权未接线（secret 代码存在但 set_trigger 不设置）→ 不要直接裸露到公网；在反代层加认证/来源限制，或加签名校验。
  • 多会话默认都用 8090 会冲突：每个会话显式配不同 port。
  • 事件不落盘、不重放、无重试：调用方失败需自己重发。

09排障速查

现象原因处理

202 但 queen 没反应会话未加载 colony / queen 节点不可用 / 已停用（订阅已取消）/ inject 失败查 session colony、重新激活、看 serve 日志 Webhook trigger '<id>' injection failed
重复执行无去重，发送方重试task 侧按事件 id 判重

10边界（完整清单见契约页 §09）

  • 无毫秒、无“延迟队列/一次性 after-N”（timer 仅 cron/interval）；webhook 是事件入口不是定时器。
  • 多触发器注入形态与上游不同（上游合并一条，Go 每事件一轮）；非 object JSON body 的 payload 保留差异正在修复（lane webhook-payload）。
  • secret 未接线、无鉴权、无重放、无去重；只本机监听。
