00结论与边界卡片

上游把 channels 做成进程内 Python 插件：hive.channels entry point 返回一个带 start/stop 的对象，该对象持有 ChannelHost，通过它打开 queen 会话、收发消息、订阅输出。Go 端口不能加载 Python entry point，也不能把 Python 对象塞进 Go 进程；本方案把同一条分界线改成进程边界 + stdio JSON-line。

先看结论：宿主负责发现/启动/停止、会话、输出提取、顺序与背压；插件负责平台连接、消息映射、渲染与重试。协议固定为 hive-channel/1，11 个方法、5 个错误码 + 6 个 data.kind、每订阅 256 条有界队列。Go 宿主已合并（internal/channels + adapters_channels*.go，commit 7c6104bf）；serve 会启动插件，GET /api/channels 返回真实 states。

01需求来源：为什么需要 channel 宿主

需求不是“再加一个 webhook”，而是让外部聊天应用的每个对话成为一个可恢复的 queen 会话，并把 queen 的输出按顺序送回聊天应用；同时任何插件故障都不能拖垮 hive serve。下表把需求、代码证据和验收条件分开写。

需求来源代码/文档证据验收条件
长会话会话是磁盘目录，可 resume；open_session 沿 superseded_by 找后继；dashboard 不抢通道会话。重启后继续；fork 后仍收到输出。
外部 chatchannels.py docstring：聊天应用从 dashboard 外到达 queen；每个群聊/私聊是一个 queen 会话。插件收到 ChannelHost 并能 start/stop。
entry-point 插件hive.channels 组；工厂 entry_point.load()(host)；配置 channels.<name>.enabled。安装即发现；未安装为空列表。
故障隔离load/start 异常记日志；30s 超时；failed 不拖垮 serve。坏插件不影响 HTTP 和其他通道。
人类监看message/question/error/files/idle；set_title；dashboard 同一会话。输出有序；问题不重复；标题可读。

02概念与分界线：Host vs 插件

分界线只有一句话：宿主拥有 queen 会话，插件拥有聊天平台。两者之间不共享对象、不共享数据库，只有 hive-channel/1 帧。

事项宿主（Go / hive serve）插件（独立进程）
发现与生命周期读 channels.<name>；spawn/hello/start/stop；超时、崩溃、状态不发现、不重启宿主；只响应 hello/start/stop
配置读取 configuration.json 的 channels.<name>，原样放进 hello只读自己认识的键；不写回 configuration.json
状态目录创建 $HIVE_HOME/channels/<name>（MkdirAll 0755）并传入拥有目录内容；自行迁移/清理
queen 会话open/resume/send/subscribe/unsubscribe/set_title；fork 跟随；colony 锁定只持有 session_id/subscription_id，不直接读写会话文件
输出提取从事件总线提取 message/question/error/files/idle；保序、有界队列逐条消费 output；用 seq 缺口判断丢帧
平台连接不接触平台 SDK、token 刷新、重连拥有平台连接、鉴权、重连、心跳
消息格式不解析 @、thread、附件 URL把平台消息转成文本/图片；把 output 转成平台消息
平台限流/重试不做平台级重试自己处理平台限流、退避、幂等
图片解码 base64、按内容类型嗅探、跳过非图；4 MiB/张、最多 8 张提供 base64 字符串；渲染 output.files 路径
错误分类会话错误映射成 JSON-RPC error.data.kind平台错误留在插件内；协议错误按 code 处理
人类监看暴露 GET /api/channels；dashboard 可打开会话set_title；可选择不实现
安全隔离超时、帧上限、进程终止；无沙箱、无进程组隔离同 uid、同文件系统/网络；必须自担平台凭据安全
接口就这些：宿主→插件 hello / start / stop / output；插件→宿主 open_session / send / subscribe / unsubscribe / set_title / judge。没有“插件直接 import Go 包”或“宿主直接调用平台 SDK”的旁路。

3.5 会话语义

  • 一个外部对话 = 一个 queen 会话；open_session 恢复旧会话，找不到/被 colony 锁定时新建。
  • fork 跟随：queen 把对话移到新 session 时，SESSION_FORKED 让订阅改挂新 id；后续 output 带新 id，插件下次 send 要用它。
  • colony 锁定：会话 spawn 了 colony 后不能再作为通道会话发送，返回 ChannelError。
  • dashboard 隔离：通道会话被 claim（session.channel + meta.json），dashboard 新建会话不会抢走它。

3.6 图片与附件

  • send(images=[bytes]) 把图片交给与 dashboard 相同的输入管线。
  • Pillow：最长边 > 2048 或字节 > 2097152 时缩放并转 JPEG(q=85)；不可识别图片跳过。
  • attach_file 成功后，从工具结果 JSON 的 attached[].resolved 找到会话附件副本，发 files output。

4.4 关键帧字段

hello（宿主 → 插件）

字段类型必填说明
protocolconst hive-channel/1是协议版本；插件按自己支持的版本处理。宿主不回读 welcome.protocol。
namestring是通道名，等于 configuration.json 的 channels.<name> 键。
configobject是channels.<name> 配置段原样传递（含 enabled、command 等 Go 宿主键）；插件只读取自己认识的键。可能含密钥，禁止写日志。
state_dirstring是宿主创建并交给插件的目录：$HIVE_HOME/channels/<name>；实际权限来自 MkdirAll(0755) 与 umask。

welcome（插件 → 宿主，hello 的 result）

字段类型必填说明
plugin_versionstring是插件版本；宿主只校验它非空，空或缺失会让 handshake failed。
capabilitiesarray&lt;string&gt;否咨询性能力列表；未知字符串保留，宿主不据此裁剪 output。

output（宿主 → 插件，notification）

字段类型必填说明
subscription_idstring是subscribe 返回的订阅 id。
session_idstring是输出所属会话；queen 迁移后变为新 id，插件下次 send 应使用它。

textstring是message/error 的文本；其它 kind 为空字符串。

filesarray&lt;string&gt;否files kind 的附件路径列表；其它 kind 省略。

字段类型必填说明

4.6 错误模型

错误帧是 JSON-RPC 的 error 对象（code/message/data）；data.kind 是唯一可编程字段，没有 retryable/detail。会话错误统一用 -32000，参数错误用 -32602，未知方法用 -32601（但 data.kind 仍是 invalid_params）。

codenamedata.kind含义
-32600invalid_request—保留的 JSON-RPC 错误码；当前宿主对参数错误统一用 -32602。
-32601method_not_foundinvalid_params插件调用了宿主不支持的 method；data.kind 仍是 invalid_params。
-32602invalid_paramsinvalid_params参数字段缺失、类型错误、图片超限或 base64 非法的统一错误。
-32603internal_errorinternal宿主内部异常、panic 恢复或通道停止中收到的请求。
-32000channel_errorno_queen, no_session, session_locked, queen_unavailable会话/queen 相关失败；具体条件看 data.kind。宿主使用 CodeChannelError 作为统一 code。

data.kind 明细

kind触发条件消息形态
no_queenqueen 档案 id 不存在。No queen '<id>': check the queen id in the '<channel>' channel's settings
no_session会话不存在、无法恢复，或标题写入目标不存在。No session '<id>' / Session '<id>' can't be resumed
session_locked会话已 spawn colony，不能再作为通道会话发送。Session '<id>' is locked because it spawned a colony; open a new one
queen_unavailablequeen 无法启动或会话创建未接线。The queen of session '<id>' can't be started
invalid_params参数错误、图片超限/非法 base64、method 不存在，或 Nothing to send。method ... is not supported / Nothing to send: ...
internal宿主内部异常或 panic 恢复。channel host panic: ... / channel host is stopping

4.7 图片

项规则
编码send.images[] 是 base64 字符串；可带 data:...;base64, 前缀，也容忍省略 padding
解码上限4,194,304 bytes / 张；最多 8 张
尺寸不缩放、不转码；按 http.DetectContentType 嗅探，只接受 image/*
不可读跳过并记日志；全部跳过且无文本 → invalid_params（Nothing to send）
base64 开销约 4/3；4 MiB 原图约 5.6 MiB 文本，仍低于 16 MiB 帧上限
output 文件传运行时绝对路径字符串数组，不传 base64；插件从磁盘读
与上游差异上游 Pillow 的 2048px / 2 MiB 缩放未移植；Go 只做 4 MiB 解码上限

4.8 顺序与背压

机制规则
每订阅顺序严格 FIFO；同一订阅一个 goroutine 串行写 output
seq必填，从 1 单调递增；缺口表示队列满丢帧，不要求回执
同会话 send宿主按请求并发处理；不额外串行。插件要顺序必须自己排队
请求/响应响应可按 id 乱序；没有 max pending 限制
再次订阅同一通道对同一会话 subscribe 会替换旧订阅，旧 id 失效
队列每订阅 256 条；绝不阻塞事件总线
溢出丢弃最旧的一条，保留最新；只记 drops 日志，不发 error，不关闭订阅
慢插件只拖慢自己的订阅，不拖 queen、其他通道
背压不是可靠消息队列。output 没有 ack；队列满时旧帧被静默丢弃，唯一信号是 seq 缺口。插件必须自己补偿，不能假设每条 message 都会到达。

4.9 安全边界

边界事实
信任模型channels.<name>.command 是 configuration.json 里的本地命令，等同用户主动执行代码
隔离无沙箱、无 seccomp、无独立用户；插件与宿主同 uid
可见资源同一文件系统、网络、HIVE_HOME、已导出的凭据环境

配置密钥hello.config 可能含 token；不得写日志；插件能看到

建议不可信插件放到独立用户/容器/VM；协议本身不提供权限隔离

5.2 设计决策（为什么这样切）

#决策理由放弃的方案/代价
D1新定义跨语言 ABI，而不是复刻 Python 对象调用Go 与 Python 没有共享对象模型；stdio 帧是可测试、可跨语言的最小边界。放弃直接调用 in-process；接受插件需要适配或重写。
D2宿主先说 helloconfig/state_dir 由宿主持有；插件在 hello 前没有可信配置。插件先说 hello 会迫使宿主等待未知状态。
D3JSON-RPC 2.0 风格 + 一行一个 JSON请求/响应/通知语义现成；调试可见；无需 HTTP 端口。自定义二进制帧更快但难调试；HTTP 增加端口与生命周期。
D4start/stop 30s，与上游一致保持可观察行为；超时即失败并回收进程。无超时会让 serve 卡死；更短会误杀慢平台。
D5保留五种 output kind插件迁移成本最低；语义与上游 QueenOutput 一致。合并成 text/event 会丢 question/files 的结构。
D6每订阅有界队列 + 丢最旧 + seq 缺口进程间没有可靠背压；有界内存必须定义丢帧策略；seq 让插件知道丢了。没有 overflow error/关闭订阅；插件需自己补偿，不能假设可靠。
D7图片用 base64 字符串内嵌保持单连接、单帧、无临时文件协议；与 JSON 兼容；容忍 data: 前缀。二进制帧更省 33%，但需要第二套 framing；大图占帧。
D8错误用 code + data.kind插件可按类别重试/提示；日志保留细节。只回字符串无法程序化处理。
D9不自动重启与上游失败隔离语义一致；避免崩溃循环。自动重启会掩盖插件 bug，且需要退避策略。
D10每通道一个插件进程隔离崩溃与内存；配置/状态目录天然分开。单进程多通道更省内存，但故障域更大。
D11Python entry point 用 adapter 桥接原插件代码可复用；Go 不引入 cgo。原生 Go 插件长期更优，但要重写平台 SDK。
D12state_dir 固定 $HIVE_HOME/channels/<name>与上游一致；备份/清理有确定位置。允许插件自选目录会让运维失控；实际 0755 而非 0700。
D13不移植 Pillow 缩放，按 4 MiB/8 张透传Go 标准库没有等价缩放/EXIF 管线；先保证协议与传输可用。大图直接进模型，成本和上下文占用高于上游；需要后续补缩放。

07entry-point 兼容性：为什么 Go 不能直接加载，以及 adapter 桥

7.1 为什么 Go 不能直接加载 Python entry point

障碍具体原因
运行时/对象模型entry point 返回的是 Python 对象；ChannelHost、QueenOutput、datetime/Path 都没有 Go 对等物
cgo 约束CGO_ENABLED=0 是本仓硬约束；嵌入 CPython 必须 cgo，直接违反硬约束
并发模型插件是 asyncio 协程；Go 的 goroutine 不能 await Python Future，GIL 也会让调用串行
发现机制importlib.metadata 读 Python 环境；Go 进程没有这个环境
打包/部署需要 Python 解释器、hive 包、插件依赖与版本；单二进制发布被破坏
宿主对象ChannelHost 是活对象；插件期望拿到实例，而不是 RPC 客户端；语义要靠 adapter 模拟

7.2 三种路线

路线做法优点代价结论
A. Python adapter 桥Go host spawn 一个 Python 进程；adapter 发现 entry point、构造代理 ChannelHost、在插件与 Go 之间转发 JSON-line原插件代码基本不改；复用 Python 生态；Go 不引入 cgo多一个进程与 Python 依赖；base64 拷贝；版本偏移；adapter 要维护两套语义短期推荐
B. 原生 Go 插件每个聊天平台用 Go 实现 stdio 插件，直接说 hive-channel/1单二进制、性能好、无 Python要重写平台 SDK/鉴权/重连；生态从零长期方向
C. embed CPython用 cgo 在 Go 进程里跑 Python看似无进程边界违反 CGO_ENABLED=0；GIL/崩溃/部署都更糟拒绝

lane 的 Host.startOne 对 enabled 但没有 command 的通道直接记 failed，错误文本就是：no command configured (Go host uses stdio plugins; Python hive.channels entry points need the Python adapter)。这不是文档建议，而是当前 Go 代码的明确边界。

7.3 Python adapter 桥怎么工作

adapter 的职责：发现并加载 entry point；把 hello 的 config/state_dir 映射成 Python 属性；把 subscribe 的 handler 注册在本地；把 output 的 questions/files 还原成 Python dict/Path；把 Python 异常映射成 JSON-RPC error；把 send.images base64 解码成 bytes；把 files 路径原样交给插件。

7.4 代价与兼容性

代价说明缓解
进程数每通道 1 个 Python adapter 进程；hive serve 是共享宿主（不是每通道一个）按通道隔离；不需要的通道 enabled=false
Python 依赖需要 Python、hive 包、entry point 元数据、插件依赖adapter 启动自检；失败显示 failed；固定版本矩阵
延迟多一次 JSON 序列化 + 管道 + base64；图片尤其明显限制图片数量；大文件走路径（output 已如此）
语义差异Python 对象/异常/traceback 过线后变成 code/kind/messagestderr 日志；没有 detail 字段，插件按 kind 分类
版本漂移Go 协议版本、adapter 版本、插件版本三者可能不一致welcome 只报 plugin_version；adapter/插件自检
维护面adapter 是第二套 ChannelHost 实现conformance 测试共用 golden frames；协议单一真值
隔离Python 插件崩溃会带走 adapter（但不带走 serve）每通道独立进程；不自动重启
兼容性结论：adapter 能让“原插件代码不改”成为目标，但不是零成本：它要求插件只通过公开的 ChannelHost 接口工作，且接受异步/错误/图片路径的细微差异。直接依赖 Python 私有字段的插件仍然要改。

09已知差异与风险

这一节是“不要自欺”清单：协议能解决跨语言调用，但不解决沙箱、可靠投递、平台 SDK 兼容和插件生态。

风险影响缓解状态
新 ABI 不是上游协议现有 Python 插件不能直接接 Go host；文档若称“兼容”会误导。adapter 桥或原生 Go 插件；协议版本显式。未决
4 MiB / 8 张图片 + base64单张 4 MiB 变 ~5.6 MiB 文本；多图可能顶满 16 MiB 帧。限制每消息图片数；客户端先压缩；必要时调大帧上限。设计已定
不缩放图片上游 2048px/2 MiB 缩放未移植，大图直接进模型，成本和上下文占用更高。插件侧先缩放；后续补 Go 图像管线。未决
错误信息有损只有 code + data.kind；没有 retryable/detail，traceback 只在 stderr 日志。插件按 kind 分类；日志关联通道名；不要依赖错误文本。设计已定
无沙箱配置里的 command 等同用户代码；插件可读 HIVE_HOME、密钥、网络。只安装可信插件；独立用户/容器；未来 capability token。已接受
无进程组回收只 Kill 直接子进程；插件的孙进程可能残留（尤其平台 SDK 起子进程）。插件自己管理子进程；必要时外部 supervisor。未决

9.1 新 ABI 的边界

  • 本协议不是上游 Python 协议的序列化版本；它是新协议。方法名接近，不代表 wire 兼容。
  • 上游插件拿的是活对象；Go 插件拿的是 JSON 请求/响应。任何依赖对象身份、属性回写、同步返回的插件都要改。
  • 版本策略：同 major 只加可选字段；改字段含义/必填性必须升 major。未知方法 -32601，未知字段忽略。

9.2 能力协商

welcome.capabilities 是咨询性的：宿主不据此裁剪 output，也不会提前拒绝图片；插件应忽略不支持的 kind，而不是断开。

9.3 未决问题

  • 是否给 output 加 ack/重放窗口？当前队列满只丢最旧，唯一信号是 seq 缺口。
  • 是否把 judge 调用做成可取消请求？当前无 cancel 方法；插件只能超时放弃。
  • 是否限制插件可访问的 queen/session 集合？当前同 uid 全可见；未来可加 capability token。
  • 是否补进程组/Job Object 回收？当前只 Process.Kill 直接子进程，孙进程可能残留。
  • 是否补 2048px / 2 MiB 图片缩放？当前 4 MiB/8 张直接透传，模型成本更高。
