go_hive · Requirements Spec v0.1

ACP Queen 需求说明书（详细版）

把任意 ACP（Agent Client Protocol）兼容 agent——Claude Code（claude-acp）、Codex（codex-acp）、Gemini（原生）、OpenCode（原生）、Hermes（原生）、pi（pi-acp）——注册成 Hive 的 queen：像 Claude Code queen 一样在 queen mail 里收信/回信，但驱动面从"每 CLI 一套适配"变成"一套 ACP client"。

版本：v0.1 草案撰写：2026-11-21 19:40 CST状态：需求说明书（未实现）归属：go_hive 扩展（上游无此概念）
定位与结论需求来源与参照物目标 / 非目标角色与场景功能需求 FR协议与接口规范配置 Schema磁盘契约与状态交互流程非功能需求验收标准里程碑风险与开放问题

00定位与结论

是什么
ACP queen
一位 queen 身份 + 一个外部 ACP agent 运行时；在邮局里与其他 queen 平权，在 colony 之外。
为什么
N 个 agent，一套协议
Claude Code queen 是"一 CLI 一适配器"；ACP 把"初始化/会话/回合/权限/MCP 注入"标准化，Hive 只做 client。
边界
不是 colony 成员
不派 worker、不读写 tracker、没有 Hive 记忆；与 colony 的桥梁仍然只有信件（queen mail）。
合规声明（必须先读）：本项上游 Hive 没有——`queen_mail` 只有 `claude_code` 一种外部运行时。按项目现行"只对齐、不新增"的约束，ACP queen 属于声明式扩展，落地前需要产品决策；本说明书只定义"若要做，做成什么样"，不代表已批准或已实现。

02目标 / 非目标

目标

  • G1 一协议多 agent：新增一位 ACP queen = 加一段配置；不需要为每个 CLI 改 Hive 代码。
  • G2 语义对齐：在 queen mail 层与 Claude Code queen 行为一致——收信/回信、日限/链深/审计、每 (queen, peer) 会话、回合中到达的信合并下一回合、六类失败对写信人可见。
  • G3 可观测：dashboard 能看到会话与归一化转录；每次信件/回合有审计行。
  • G4 安全默认：无人值守下权限默认拒绝；env 白名单；token 只对该会话有效；进程树可杀。

非目标（本版明确不做）

  • 不实现 ACP 远程传输（Streamable HTTP/WebSocket 仍是 RFD）：agent 进程必须本机可启动；跨机只能用 ssh 包装 stdio。
  • 不改上游：configure.json 的 queen_mail.claude_code 保持原样；ACP 用新的配置段。
  • 不把 ACP queen 变成 colony 成员：不派 worker、不落 tracker、不进 colony 组织图（组织图上按"外部 queen"虚线卡片处理，与 CC queen 一致）。
  • 不做进程常驻：与 CC queen 一致，每回合拉起一次 agent 进程（进程池是后续优化，见 §11 M3）。
  • 不替 agent 做记忆：与 CC queen 一致，没有 Hive memory/soul/recall 注入。

03角色与场景

角色职责交互面
用户配置 ACP queen；读 dashboard；通过 Hive queen 给她写信configuration.json / 组织图虚线卡片 / 只读转录
Hive queen（写信人/收信人）用 message_queen 与她互相写信；可把外部活外包给她女王的 list_queens/message_queen 工具
ACP queen（本项）收到信 → 起 ACP agent 回合 → 最终文本回信；可用 message_queen 主动写信ACP stdio 协议 + 注入的 hive MCP server
ACP agent（外部运行时）真正干活：claude-acp / codex-acp / gemini / opencode / hermes / pi-acp由 Hive 作为 ACP client 驱动

核心场景

  1. S1 外包任务：colony queen 写信"It looks like…" → ACP queen 用她自己的工具链干活 → 最终文本回到 colony queen 会话。
  2. S2 双向信件：ACP queen 在回合里调 message_queen 主动写信给第三位 queen；对方回信进入她的收件箱。
  3. S3 多 queen 分工：同时配置 queen_reviewer（codex-acp）与 queen_coder（claude-acp），各自独立配置/目录/账号，互相能写信。
  4. S4 无人值守权限：回合中 agent 请求执行一个需要批准的工具 → 按策略拒绝/放行，并留审计；写作者不被打断。

04功能需求（FR）

FR-1配置与注册

  • 新增配置段：queen_mail.runners.acp.<id>（替代命名：queen_mail.acp.<id>，二选一在实现前拍板）。字段见 §06；未配置 = 不存在。
  • 每位 queen 的 id 是 map 键；name/title 进入 list_queens。
  • 参与规则与 CC queen 相同：只要配置了且 queen_mail.enabled=true 就参与（不受 queens 列表限制）。
  • Go 侧配置读取沿用现约定：hive serve 启动时读取一次（与 CC queen 一致；热重载列为后续可选增强，需与上游差异一起登记）。

FR-2身份与会话模型

  • 会话按 (queen, peer) 建立：ref 形如 acp:<queen id>:<uuid>；conversations.json 结构与 CC queen 相同（peer/reply_to/started/provider_session_id）。
  • ACP 会话 id 来自 agent 的 session/new 返回；恢复优先用 session/resume（v1 若 agent 未声明 sessionCapabilities.resume，则用 session/load + loadSession 能力；两者都不可用 → 退回新会话并在审计里记 resume_unavailable）。
  • ACP 连接是一次的：每回合 spawn → initialize → new/resume → prompt → close；同一会话的并发回合必须串行（队列深度 ≥32，满载行为与 CC queen 一致：等下一轮）。

FR-3回合驱动

  • 收到信件 → 取该会话当前收件箱批次 → 组 prompt：[[Name(id)]: text, …]（与 CC queen 同一渲染函数，含 ]: 转义规则）。
  • 经 session/prompt 发送；期间收到的 session/update 归一为统一事件（§05.3）并写入本会话转录。
  • 回合结束取"最终文本"：agent 的最后一个完整 assistant 消息（按 ACP update 流拼装）；为空则按失败处理（与 CC 一致：空文本不产生回复）。
  • 回写路径复用现有 Mail.DeliverReply：写信人是 Hive queen → 注入其会话；是 ACP/CC queen → 进其收件箱；深度/关闭/不可达 → dropped 审计行。

FR-4MCP 注入（信件通道）

  • 在 session/new|resume 的 mcpServers 中注入与 CC queen 完全相同的 hive server：command=<hive 二进制>、args=["queen-mail-mcp"]、env = HIVE_QUEEN_MAIL_URL/TOKEN/FROM。
  • token 仍为 HMAC(secret, ref)（secret 每进程随机），只对该会话有效；工具仍只有 list_queens/message_queen 两个，schema 与文案不改（沿用 queen-mail-mcp 的字段级对齐成果）。
  • 若 agent 声明 mcpCapabilities 不含 stdio → 配置校验期直接报错（该 agent 不能成为 ACP queen），错误写入启动日志与 dashboard。

FR-5权限策略

  • 响应 session/request_permission：按 permission_policy 三档——deny（默认，拒绝一切请求）/ allow_allowlist（命中 allowed_tools 的批准，其余拒绝）/ allow_all（全批准，等同 bypass，配置需显式 opt-in 并在启动日志警告一次）。
  • 每次裁决写一条审计（会话、工具名、裁决、策略档）；不允许"静默不回"导致 agent 卡死（超时无响应按 deny 回复）。
  • 与 CC queen 的差异：CC 用 CLI 参数（--permission-mode/--allowedTools）；ACP 是协议内消息。需求上要求语义等价：无人值守默认拒绝；显式白名单自动放行。

FR-6失败与超时

  • 六类对外文案与 CC queen 逐字一致（无凭据/超时/无法启动/agent 报错/非零退出/她被移除），其中 provider 名替换为 "ACP agent"；内部保留 agent 原始错误供排查。
  • 超时（默认 timeout_minutes=30）：先 session/cancel，宽限 N 秒后杀整个进程树（Unix：进程组 SIGKILL；Windows：已知差异，仅杀直接进程——与 CC queen 同缺口）。
  • 握手失败（initialize 超时或协议版本不匹配）→ 明确错误，不计入"已尝试回合"的假成功。

FR-7并发

  • 同会话串行；跨会话并行；全局上限沿用 queen_mail.max_parallel_turns（默认 2），并且该上限同时统计 claude_code 与 acp 两类的在跑回合（"所有外部 queen 的回合总数"语义）。
  • 回合中到达的信合并进下一回合（与 CC 一致）。

FR-8Dashboard 与转录

  • 新增只读路由（命名二选一）：GET /api/acp-queens + GET /api/acp-queens/{id}/conversations/{session_id}，字段沿用现有 CC dashboard 形状并加 provider（如 codex-acp）。
  • 转录由 Hive 自建：把 session/update 归一写入 runners/acp/<id>/transcripts/<session>.jsonl（letter/text/tool/result 四类），dashboard 读它——不依赖 agent 私有文件格式（CC 是读 Claude 的 JSONL；ACP 生态无统一转录文件）。
  • 组织架构图把 ACP queen 按"外部 queen"虚线卡片展示（与 CC queen 同一视觉语言，只读）。

FR-9多 queen

  • map 配置，无数量上限；每位独立 home：HIVE_HOME/acp/<id>/（或 runners/acp/<id>/）含 conversations.json/inbox//transcripts//logs/。
  • 共享项：enabled/daily_limit/max_depth/max_parallel_turns、同一个 Mail 服务与 queens/mail.jsonl 审计。
  • ACP queen 之间、与 CC queen 之间、与 Hive queen 之间都可互相写信。

05协议与接口规范

5.1 传输与版本

  • 传输：stdio（JSON-RPC 2.0，LF 分隔，无内嵌换行；stderr 仅日志）。不实现远程 transport（RFD 未定）。
  • 版本：MVP 锁定 ACP v1，initialize 发 protocolVersion: 1；agent 回不同版本 → 明确报错不降级。v2 支持列入 M2+（需整体切 prompt 生命周期，禁止半 v1 半 v2）。
  • 能力协商必须读回并记录：loadSession / sessionCapabilities.resume / promptCapabilities / mcpCapabilities；能力缺失时走 FR-2 的降级路径。

5.2 方法集（Hive 作为 client 调用）

方法用途关键参数/返回
initialize握手与能力协商→ {protocolVersion, clientCapabilities, clientInfo}；← {agentCapabilities, agentInfo, authMethods}
session/new为 (queen, peer) 建会话→ {cwd, mcpServers}；← {sessionId}
session/resume（优先）/ session/load（备选）恢复既有会话→ {sessionId, cwd, mcpServers}
session/prompt发送信件批次→ {sessionId, prompt:[{type:"text",text}]}；v1 响应带 stopReason
session/update（agent→client 通知）流式输出message/tool/plan/state 等 update；归一入 §5.3
session/request_permission（agent→client 请求）权限裁决按 FR-5 策略回答；裁决入审计
session/cancel超时/关闭随后按 FR-6 杀进程树

5.3 统一事件（归一）

{"kind":"started","provider":"codex-acp","session_id":"sess_…"}
{"kind":"text","text":"…","final":false}
{"kind":"tool","name":"Bash","input":{…},"status":"running|ok|error"}
{"kind":"usage","input_tokens":0,"output_tokens":0,"cost_usd":0.0}   // 有则填，无则省略
{"kind":"done","text":"final answer","stop_reason":"end_turn|timeout|error","error":null}

5.4 MCP 注入（协议内）

session/new {
  "cwd": "…",
  "mcpServers": [
    {"name":"hive", "command":"<hive binary>", "args":["queen-mail-mcp"],
     "env":[{"name":"HIVE_QUEEN_MAIL_URL","value":"…"},
            {"name":"HIVE_QUEEN_MAIL_TOKEN","value":"…"},
            {"name":"HIVE_QUEEN_MAIL_FROM","value":"acp:<queen>:<sid>"}]}
  ]
}

注：field 形状以 ACP v1 schema 为准（env 为 name/value 数组的具体形态在实现时按 schema 校正）；这与 CC queen 的"临时 MCP 配置文件 + --mcp-config"形成对照——ACP 不需要文件。

06配置 Schema

"queen_mail": {
  "enabled": true,
  "runners": {
    "acp": {
      "queen_reviewer": {
        "name": "Reviewer",
        "title": "Code Review",
        "command": ["npx", "@agentclientprotocol/codex-acp"],
        "cwd": "/Users/me/work/review",
        "auth": "env_api_key",
        "api_key_env": "OPENAI_API_KEY",
        "permission_policy": "allow_allowlist",
        "allowed_tools": [],
        "timeout_minutes": 30,
        "system_prompt": "",
        "env": {}
      }
    }
  },
  "max_parallel_turns": 2
}
键必填语义 / 默认
command是agent 或适配器命令（数组或字符串）；如 ["hermes","acp"]、["npx","@agentclientprotocol/codex-acp"]、["claude","--acp"]（适配器名以各项目文档为准）
name/title否默认 id / "ACP Agent"；只影响 list_queens 显示
cwd否默认 HIVE_HOME/acp/<id>/workspace；作 session/new 的 cwd
auth/api_key_env否env_api_key（从环境变量注入到子进程）/ login（用 agent 自己的登录态，如 ~/.codex、hermes portal）/ none；默认 login
permission_policy否deny（默认）/ allow_allowlist / allow_all（需显式；启动警告一次）
allowed_tools否allow_allowlist 下自动批准的工具名列表
timeout_minutes否默认 30；超时取消+杀进程树
system_prompt否追加到 session/new 的 systemPrompt（仅当 agent 声明支持时）；默认使用 Hive 的"信件说明"文本（与 CC 同一份）
env否额外环境变量（白名单基础上叠加；不允许覆盖 Hive 保留项）

07磁盘契约与状态

HIVE_HOME/runners/acp/<id>/
├── conversations.json      # {"conversations": {"<peer>": {peer, reply_to, started, provider_session_id}}}
├── inbox/                  # 等待中的信（跨重启保留；取走即移出）
├── transcripts/<session>.jsonl   # Hive 自建归一转录（letter/text/tool/result）
└── logs/                   # 回合日志（含 agent stderr 尾部，凭据已清洗）
  • 兼容性：conversations.json 的字段与 CC queen 版本同形（多一个 provider_session_id，CC 侧已有该语义）；迁移工具可把 CC 记录映射过来（可选）。
  • 审计：每次 hop 仍写共享 queens/mail.jsonl（kind、from、to、depth、dropped 原因），ACP 相关行加 runtime:"acp"。
  • 清理：session_retention 类策略（默认 7 天）作用于 transcripts/inbox；删除前不打断在跑回合。

08交互流程

失败路径：agent 无法启动 / initialize 超时 / 协议版本不符 / prompt 报错 / 超时 / 权限全拒导致无产出 —— 六类统一映射到 FR-6 的对外文案。

09非功能需求

类别要求
安全env 白名单（不继承 HIVE_CREDENTIAL_KEY 与任何 provider key，除非 api_key_env 显式指定）；token 只对会话有效；权限默认拒绝；进程树可杀；日志清洗凭据
隔离每位 queen 独立 home/cwd；不共享 config_dir（默认）；agent 进程 cwd 即其工作目录
可观测启动/回合/权限裁决/失败均有结构化日志；running 状态可查；dashboard 只读视图
性能冷启动（spawn→initialize）目标 ≤ 10s（本地 agent）；事件到 dashboard 的转发延迟 ≤ 1s；转录写入不阻塞回合
可靠性agent 崩溃/握手失败不挂起队列；重试语义与 CC 一致（记录修正重试一次）；队列满时报明确错误，不静默丢信
兼容ACP v1 全量；v2/远程 transport 以能力探测预留，不做半支持
发布无新增二进制（Hive 当 client）；不改 claude_code 现有行为（回归测试不变）

10验收标准

10.1 单元/集成（fake ACP agent 夹具）

  • 夹具：可脚本化的 stdio JSON-RPC agent（按序回 initialize/new/prompt/update/permission；可产出超时、错误、能力缺失、无法启动）。
  • 用例：首轮 new / 次轮 resume（含 resume 不可用降级 load/new）；批次合并；最终文本回写；六类失败文案逐字；权限三档裁决与审计；env 白名单（注入 key 与不注入 key 两例）；token 只对会话有效；超时杀进程树；并发上限（跨 claude_code+acp 的全局计数）。

10.2 真实 agent 冒烟（本机可跑）

  • hermes acp（本机 0.21.5）：单 queen 一条真实回合（信件→回复）落盘证据。
  • codex-acp（npx @agentclientprotocol/codex-acp，需网络）：同一条证据链；网络不可用则 skip-with-reason（不得假通过）。
  • 可选：claude-acp（与现有 CC queen 并存对照，验证两套运行时同一 queen mail 服务内共存）。

10.3 逐字对齐点（沿用现有纪律）

  • list_queens/message_queen 工具 schema 与描述 = queen-mail-mcp 现存版本（不为 ACP 另写一份）。
  • 六类失败文案、HTTP 回调合同（/api/queen-mail/*）、日限/链深错误文案与既有实现逐字一致。
  • 审计行字段与 CC 行同形（多 runtime:"acp" 标记）。

10.4 反例（必须失败得清楚）

  • agent 不支持 stdio MCP → 配置校验期报错，不启动回合。
  • agent 返回不同协议版本 → 明确错误，不降级、不假装成功。
  • permission_policy=deny 下 agent 全程被拒 → 回合结束时的空产出按失败处理并告知写信人。

12风险与开放问题

风险/问题说明处置
上游无此概念属于"只对齐、不新增"之外的扩展产品决策后立项；未决前只保留本说明书
