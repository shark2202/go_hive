GO_HIVE · LAN PEERS · POST-1.0 REQUIREMENTS → DESIGN

LAN Pipes → go_hive LAN 发现 + 联邦 queen mail

把 LAN Pipes 的发现模式移植到 go_hive，做成可选的局域网 queen mail 联邦：UDP 组播发现、组密钥自动配对、HTTPS/JSON 投递；复用现有 queen mail 引擎，不做远程会话控制。默认关闭，单跳私有 LAN，post-1.0；配置只保留五个键。

状态：design需求：12设计项：10验收：12范围：Same private LAN, flat peer group; queen-initiated mail chains bounded to 4 hops; post-1.0 optional extension

00可行性判断

结论：发现和信件传输可移植；远程会话控制不在本设计范围。
原因：UDP multicast and HTTPS/JSON are standard-library work in Go. The hard part is identity and admission, not the socket: queen mail is already asynchronous and owns thread sessions, reply watchers, depth, daily limits and audit. The peer layer must feed that engine without bypassing participant checks, and a shared group key must not become an internet-wide bearer secret.
可复用
  • UDP multicast discovery and announce freshness are transport patterns that port to Go without cgo.
  • HTTPS/JSON request-response, TLS pinning, retries and expiry are standard library work.
  • Queen mail already has thread sessions, reply delivery, wake-up, max_depth, daily_limit and mail.jsonl audit; the peer layer only supplies remote correspondents and a remote deliverer.
  • The existing queen mail tools already give queens list_queens and message_queen; remote addresses can be added without a new model tool.
不能直接搬
  • The unauthenticated TCP/NDJSON transport and main/sub/master/slave roles from LAN Pipes do not fit Hive.
  • Raw prompt routing and remote session control would bypass queen/colony runtime, permission boundaries and audit.
  • Multicast cannot cross the public internet, and a group key is not a public-network identity.
  • Static peer rosters and manual per-peer tokens are intentionally removed from this design; they are not a fallback.
目标之外：Let queens on two Hive instances on the same private LAN write to each other with zero peer configuration beyond a shared group id and group key, while preserving local thread sessions, asynchronous replies, mail limits and audit. The peer layer is a transport and admission adapter for queen mail, not a second orchestration model.

Queen mail is process-local today: list_queens reads local queens, message_queen delivers into a local thread session, and the reply watcher writes back to a local writer. Two Hive instances on the same LAN have no discovery, no peer identity and no way to address a remote queen without custom HTTP calls.

用户价值
  • A node joins a LAN group with only group_id and a group key env var; existing nodes need no edit.
  • Remote queens appear automatically as queen_b@hive-office-b@office-lan and are writable with message_queen.
  • Replies use the existing asynchronous queen mail path: the remote queen answers in her thread session, and the adapter sends the reply back.
  • The surface stays mail-only: no remote session create/chat/events, no colony or worker control, no new model tool.
  • The feature is opt-in and disabled by default; when disabled it opens no UDP or TCP socket.
为什么不是当前 parity
This is an additive Go-only capability for a private LAN, not an upstream Hive feature. It remains design-only until the five-key schema, group auto-pair, the queenmail resolver boundary and a real two-process LAN E2E are accepted.

非目标

  • Do not add remote session create/chat/events/delete or any /peer/v1/sessions route.
  • Do not expose colony workers, task queues or tool permissions to a peer.
  • Do not copy the opcteam main/sub/master/slave role model.
  • Do not support WAN, public discovery, automatic forwarding/relay trees or unbounded multi-hop cascading.
  • Do not add federation, expose, peers, auto_connect, targets, tls, identity or discovery tuning keys.
  • Do not add a new default model tool or a colony-specific UI.
  • Do not reuse HIVE_DESKTOP_TOKEN as a peer credential.

前提

  • Both peers run hive serve on the same private LAN and can reach each other on a private IPv4 address.
  • Both peers set the same group_id and provide the same group key through group_key_env.
  • The LAN forwards UDP multicast 239.255.71.67:7101; if it does not, peer discovery is unavailable in v1.
  • Each node can generate and persist an instance_id and ed25519 keypair under HIVE_HOME/lan_peers.
  • Queen mail is already enabled locally; lan_peers only federates it.
  • A real multi-machine run is required before calling the transport production-ready.

O4Static peer roster with per-peer tokensrejectedThe user removed peers, tokens and targets; the fixed group_id + group_key pair is the only admission model.

选择：Port only the LAN Pipes discovery pattern into go_hive as an optional LAN queen-mail federation. Two Hive instances on the same private LAN announce themselves over signed UDP multicast, auto-pair when they share group_id and the group key from group_key_env, and exchange queen mail over HTTPS/JSON. The existing queen mail engine remains the only mail engine: thread sessions, reply watcher, max_depth, daily_limit and mail.jsonl audit are reused. There is no remote session control, no raw prompt path, no second role model and no public/WAN discovery. The schema exposes only five keys; federation, expose, peers, auto_connect, targets and the rest are deliberately absent, not left at defaults.

03设计链

D1

Opt-in and mail-only surface

lan_peers.enabled gates the UDP discovery socket and the peer routes. When it is false or absent, no socket or route exists. The feature requires queen_mail.enabled; there is no peer session route, no /peer/v1/sessions, no remote chat/events/delete and no colony or worker control.

D2

Fixed group discovery

Discovery is UDP multicast on 239.255.71.67:7101, TTL 1, announce every 5 seconds and expire after 15 seconds. The announce carries instance_id, name, url, public_key, group_id, capabilities, ts, a group proof and a node signature. There is no peers list, no auto_connect key, no discovery.enabled key and no static fallback; the only discovery configuration is group_id and group_key_env.

D3

Identity and group admission

On first run, generate an instance_id and an ed25519 keypair under HIVE_HOME/lan_peers. The display name defaults to the hostname; it is not an address key and not a trust source. The announce includes group_proof = HMAC(group_key, instance_id || public_key || ts) and a node signature. A receiver checks group_id, proof, signature and timestamp, then pins the public key. A changed key is quarantined, not silently accepted. If group_key_env is missing while lan_peers.enabled is true, startup fails closed.

D4

HTTPS transport

Handshake, mail and health use HTTPS over TCP on the peer's advertised private address. The self-signed certificate uses the node's ed25519 identity; the peer pins the public key from the signed announce, not the leaf bytes. Non-loopback peers must use TLS. Bodies are bounded JSON; there is no raw TCP, no NDJSON and no WebSocket/SSE. The peer listener only serves /peer/v1/handshake, /peer/v1/qmail and /peer/v1/health.

D5

Connection lifecycle

A peer moves through discovered, paired and connected states. A valid announce auto-pairs; a successful handshake connects; a missed announce or health probe marks it offline. A changed IP is accepted only from a signed announce. Group-key rotation requires updating the env var and restarting all nodes; there is no online rotation in v1.

D6

Reuse the queen mail engine

Mail.Send, Mail.DeliverReply, thread session lookup/creation, reply watcher, max_depth, daily_limit and mail.jsonl audit stay authoritative. The peer layer does not create a second queue, reply watcher or session store. A remote letter enters the same thread-session and reply path as a local letter.

D7

Correspondence resolver

Add a resolver at the edge of queen mail: local queens come from queen_mail.queens and the queens directory; remote queens come from paired peers and expire with the peer roster. list_queens merges both and returns exactly the existing {id, name, title} shape; a remote id is the full three-level address queen_name@peer_node_id@group_id. The resolver checks ref types in this order: (1) the existing claude_code: prefix via ConversationPrefix/IsConversationRef, which stays unchanged and is handled first; (2) exactly three @-separated segments for a remote queen, with group_id equal to the local discovery.group_id; (3) a local queen id from the roster; (4) a local session or reply ref. ConversationPrefix and QueenIDOfRef are not changed; remote addresses never use that prefix. message_queen parses exactly three @-separated segments: queen_name (the queen id), peer_node_id (the peer's stable instance_id, not its display name) and group_id (must equal the local discovery.group_id). One, two or four segments, an @ inside a segment, or a group mismatch is a typed error. A remote thread's meta records the full writer address so replies route back. Mail.Send target checks and DeliverReply writer checks use the resolver instead of a local-only queens map.

D8

Letter envelope and loops

The wire letter carries letter_id, trace_id, hops, group_id, from_peer, from_queen, to_peer, to_queen, text, reply_to, ts and signature. letter_id is idempotent for 24 hours. max_hops is fixed at 4 across instances; local max_depth remains independent. A letter beyond max_hops is rejected and audited, never silently delivered. A hop is a deliberate queen message_queen or reply, never automatic forwarding; there is no store-and-forward relay. max_hops only bounds the queen-initiated chain.

D9

Exposure and security

Only queens listed by queen_mail.queens (or all local queens when omitted) are advertised and writable. The advertised roster carries only the existing id, name and title fields; private profile sections are never exposed. Inbound mail is always enabled when lan_peers is enabled; there is no expose or federation key. The group key is admission only; each node has its own ed25519 identity. Private LAN only, TLS pinned, bounded bodies, per-peer rate limits, and no group key, token or letter body in logs or announce.

D10

Package boundary and verification

Put discovery, identity, transport and the qmail client/server in internal/lanpeer; keep the server adapter thin; add only a correspondent resolver and remote deliverer interface to internal/queenmail. Do not import internal/server, internal/cli or internal/tools/builtin from internal/lanpeer. No new model tool or UI. Verify with fake peers and a real two-process loopback/LAN E2E; keep CGO_ENABLED=0 and generator --check.

包边界：discovery/identity/transport/qmail client-server 放在 internal/lanpeer；server 只做薄适配器；internal/queenmail 只加 correspondent/remote deliverer 接口；不得从核心 import internal/server、internal/cli 或 internal/tools/builtin；不增加默认模型工具。

04通讯与信封

发现

Fixed UDP multicast 239.255.71.67:7101; no static peer roster

UDP 组播只产生候选和准入证明，不传信件。

投递

HTTPS/JSON over TCP for handshake, mail and health; UDP multicast only for discovery

握手、发信、回信、健康检查；没有长连接。

信任

Group key admission plus per-node ed25519 identity; TLS certificate pinned

组密钥准入 + 节点身份；announce 不携带 token。

操作顺序

  1. Both nodes start with lan_peers.enabled and the same group_id plus group_key_env value; each generates instance_id and ed25519 identity.
  2. Each node sends a signed UDP announce; the receiver verifies group proof, signature and timestamp, then auto-pairs and pins the public key.
  3. The peer client posts /peer/v1/handshake over HTTPS; a challenge-response confirms both node keys and returns the peer queen roster with the same id, name and title fields as local queens.
  4. The ref resolver checks the existing claude_code: prefix first, then the three-level remote address, then a local queen id or session ref.
  5. list_queens merges local and remote entries; the queen writes to queen_b@hive-office-b@office-lan with message_queen.
  6. The sender posts the letter to /peer/v1/qmail; the receiver returns 202 accepted and injects it into the local thread session.
  7. The remote queen answers in her thread session; the reply watcher posts a separate letter back to the writer's /peer/v1/qmail.
  8. A queen may reply to the sender or deliberately write to another peer; each leg increments hops, and nothing is forwarded automatically.
  9. An offline peer queues the letter for up to 24 hours; expiry, duplicate suppression and hop limits are audited.

peer 路由

  • POST /peer/v1/handshake
  • POST /peer/v1/qmail
  • GET /peer/v1/health

09风险、待拍板与来源

风险影响缓解
Group key compromiseany holder can join the LAN groupkeep the key in env only, rotate by restarting all nodes, never log or announce it; use a VPN for untrusted networks.
Multicast blocked or interfaces ambiguousno peers are discovereddocument the limitation; v1 has no static peer fallback; use a VPN/overlay that carries multicast or a separate design.
No per-peer revocationa member cannot be removed individuallyrotate the group key; per-node identity prevents impersonation but not admission.
Changed node keya legitimate node is quarantinedremove its runtime peer record and restart, or rotate the group key; log a clear operator message.
Asynchronous mail latencyno immediate reply; offline peers delay deliverykeep the 24h queue, retry policy and explicit offline/expired errors.
Duplicate or looping lettersduplicate replies or endless A-B chainsletter_id idempotency, trace_id and fixed max_hops=4.
Scope creep into session controlreintroduces targets, SSE, permissions and a second surfacemail-only requirement R2, no /peer/v1/sessions, no expose/targets keys.
No real multi-machine runLAN behavior differs on real networkstwo-process test is required; record multi-machine as an external gap, not PASS.

待拍板

  • Group-key rotation is restart-only in v1; is an online rotation endpoint needed later, or is restart acceptable?
  • A changed node public key is quarantined; should recovery be deleting its runtime peer record, rotating the group key, or both?
  • Remote attachments remain path text only in v1; is cross-instance file transfer required, or explicitly out of scope?
  • Inbound letters do not count against queen_mail.daily_limit; should they consume a separate per-peer quota?
  • When queen_mail.queens is omitted, all local queens are advertised; should an explicit list be required for safer defaults?
  • If the separate WAN design (docs/wan-peers-design.html) is adopted, should LAN and WAN share the ed25519 key/fingerprint storage, or keep separate identities?
