judge 槽与 stall check

补上 Hive 目前缺的那页文档：judge 是一个只回答概率的模型槽，stall check 是它的第一个消费者——抓 queen「嘴上说要做、回合结束却没调用工具」的情况。本页写清怎么配、怎么判定、影响什么、怎么排障；机制以代码为准（Python 与 Go 同语义）。

00是什么（两个东西，一个目的）

judge 槽
概率裁判
不是聊天模型。给它一段现场 + 一个问题 + true/false 标准，它返回「是」的概率（0–1）。协议目前只有 typesafe（POST /systemone，读 noul）。
stall check
说到没做 → 提醒一次
queen 回合结束、开始等用户时，把这一轮现场交给 judge；概率过阈值就注入一条系统提醒让她补做。
边界
只提醒，不代做
不阻塞、不改回复、不碰工具权限；每条用户消息最多判定一次、最多提醒一次，误判不会循环。
它解决的具体问题：有些模型会说「马上做 / 正在画」，然后结束回合却没调用任何工具；或者用户指出「手指画错了」，它只描述应该怎么改，却不动手。stall check 就是抓这种「talk ≠ work」。

01怎么配置

1.1 judge 槽（必须）

"judge": {
  "protocol": "typesafe",
  "api_base": "https://<typesafe-endpoint>",
  "model": "<model>",
  "api_key": "***",
  "threshold": 0.5
}
  • 可用条件：api_base 与 api_key 都存在；缺一个 → judge.slot() 返回 None，stall check 静默不工作。
  • 协议：typesafe → POST {api_base}/systemone，body 含 state、model、questions.answer = {type:"noul", instructions, criteria}，取 answers.answer.noul。超时 20s；失败只记日志。
  • 阈值：threshold（默认 0.5）；概率 ≥ 阈值才提醒。误报多就调高（如 0.7）。
  • 注意：judge 的 api_key 必须直接写在槽里（不像 vision_fallback 有 api_key_env_var 回退）；通常通过 Settings → AI Model → Judge 或 Advanced 原始 JSON 配置。

1.2 stall_check 开关

入口行为
Settings → Developer → Stall check写入 configuration.json 的 stall_check；没有 judge 时开关置灰并提示 "Needs a judge: set up AI Model → Judge"
HIVE_STALL_CHECK=true|false环境变量优先于配置文件
configuration.json 顶层 "stall_check": true持久化开关（features 端点写的就是它）

开关与 judge 槽都是每回合读取：改完对运行中的会话立即生效，不用重启。默认关（Developer 选项）。

02判定流程

queen 事件流
  ├─ CLIENT_INPUT_RECEIVED     记录用户消息；把上一轮存为 previous_turn
  ├─ CLIENT_REASONING          记录推理（尾部）
  ├─ CLIENT_OUTPUT_DELTA       记录回复快照
  ├─ TOOL_CALL_STARTED         记录本轮工具；清空当前段 reasoning/reply
  └─ CLIENT_INPUT_REQUESTED    park_reason == "turn_done" 才继续
        │
        ├─ 跳过：已判过 / 没有用户 / 回复为空 / 回复是可见错误
        ├─ 组装 state：user ≤2000 · reasoning 尾 ≤1500 · reply ≤1500
        │              · tools_called_this_turn · previous_turn{reply≤600, tools}
        ├─ 问 judge：这一轮有没有把该做的工作留着没做？（带 true/false 标准）
        ├─ p < threshold → 记 debug，结束
        └─ p ≥ threshold → inject_event(REMINDER, is_client_input=False)
              └─ 内容：你刚才说要做但没调用工具；如果该做就现在做；不要提这条提醒

2.1 判定标准（judge 的 criteria 摘要）

判定含义
true回复在谈"现在就该做的工作"（宣布、承诺、或同意修正并说明要改什么），而本轮没有任何工具调用去做它
false只是聊天 / 回答问题 / 反问需要的信息 / 拒绝或反驳（即使承认错误、给了替代方案）/ 回应用户的解释而非新任务 / 本轮工具已经做了（即使结果有瑕疵且回复列出了问题）

2.2 防抖

  • 每条用户消息最多一次判定、最多一次提醒（judged 标记）。
  • 判定是后台任务；judge 超时/失败/未配置 → no-op，不影响回合。
  • 提醒以 is_client_input=False 注入：模型知道它不是用户原话，UI 也不会把它当用户消息。

03影响面

方面影响
触发范围只对 queen 回合（stream_id == "queen"），且只在 turn_done 停泊时；不碰 worker、不碰非 queen 流
会话类型所有 queen 会话（DM、colony overseer）；与渠道无关（Telegram/Slack/Inbox 只是传输）
动作过阈值 → 注入一条提醒；queen 若照做，会多一轮模型调用 + 工具调用
成本每个合格回合 1 次 judge 调用（≤20s 超时）；被提醒后额外 token/延迟/工具副作用
时延judge 在后台跑，用户看到的回复已经流出；补做表现为 queen 又发消息/又调工具
输出/转录不改已发出的回复；提醒是系统提醒、不算用户原话；失败不写任何东西
安全/权限不绕过审批、不扩大工具权限；只是"再推一次"，是否执行仍由模型决定
隐私用户消息、回复、推理片段会发给 judge 端点——judge 是外部服务时要按数据边界选型
不生效的条件开关关、judge 缺 api_base/api_key、协议不支持、judge 调用失败、回复是可见错误、没有用户消息、已判过
不要当成"质量门禁"：它是启发式提醒，不是正确性保证；误判的代价被限制在"每条用户消息一次提醒"，但调高阈值/关掉是合法手段。

04启用、验证与排障

  1. 确认开关状态：curl /api/config/features 里 stall_check；Go 侧同名字段。
  2. 确认 judge 槽：Settings → AI Model → Judge 能看到已保存的 section；或 /api/config/llm-sections 的 judge 非空。
  3. 日志：命中 stall check: p=0.xx >= 0.50, reminding the queen…；未命中 p=… < …, turn is fine；judge 不可用 judge: unavailable (…)。
  4. 人为复现：让 queen 说"好的，我马上改"但停住不动（或临时把 threshold 降到 0.1 放大触发），观察是否多出一轮补做。
  5. 开关灰掉：先配 judge（需要 api_base + api_key）；环境变量强开不会绕过这个可用性检查，只会 no-op。

4.1 真实 judge 实测（2026-11-21）

本机 startlux-decide 上已跑通双实现对照：同一脚本化女王回合下，Python 与 Go 的 judge 请求体逐字段相等、p 逐位相等（stall=0.936458、阈值间回复=0.672394、工具回合=0.020912）；提醒注入、第二轮补做、开关关闭、judge 不可达 no-op、无用户消息不判定均一致；同一回复阈值为 0.5 时触发提醒、0.7 时不触发。差异：Go 原先的 state 键序会让真实 judge 输出不同 p（0.9233 vs 0.9365），已按上游插入序修复并加单测。用例与证据见 stall-check-parity.md 与 e2e-assets/judge-stall-real/。
