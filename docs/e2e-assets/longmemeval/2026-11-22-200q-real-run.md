# LongMemEval S，n=200 大样本真实跑 — Go/Py × 有/无 notes（2026-11-22）

> 结论先行：在 200 题（六类均衡配额：五类各 34 + preference 全部 30）上，四组全部 200/200 逐题落盘，
> error / judge_error 均为 0：
>
> | 组 | overall | 95% CI | task-averaged |
> |---|---|---|---|
> | Go 无 notes | **175/200 = 87.5%** | 82.2–91.4 | 86.8% |
> | Py 无 notes | **183/200 = 91.5%** | 86.8–94.6 | 91.0% |
> | Go 有 notes | **181/200 = 90.5%** | 85.6–93.8 | 90.0% |
> | Py 有 notes | **185/200 = 92.5%** | 88.0–95.4 | 92.2% |
>
> 任何配对差异都不显著：Go−Py 无 notes −8 题（McNemar p=0.115）、有 notes −4 题（p=0.524）；
> notes 效应 Go +6（p=0.238）、Py +2（p=0.832）。**n=200 上仍没有实现级差异的证据。**
> 更关键的是同题重跑一致性：n=60 的那 60 题在本轮重跑中 **Go 52→49、Py 51→57**（同题 5 小时前的结果被翻转，
> Py 6 题全部向上、0 题向下）；而在**本轮新增的 140 题上两侧无 notes 都是 126/140，完全相同**。
> 也就是说，本轮无 notes 的 −8 题差距全部来自那 60 道旧题，而旧题结果本身不可复现——**n=60 的 ±1 题差值不是实现差异：
> 同一批题、同一代码、同一模型名，5 小时后的重跑同题漂移 Go −3 / Py +6，两侧差距从 +1 摆到 −8（60 题内）**。
> 次判（0.8B judge 槽）下 Go/Py 无 notes 为 79.0% vs 84.0%
> （同向），但 notes 组间排序反转（89.0% vs 83.0%）；judge 选择足以改写 notes 结论，不能改写「两侧不可区分」。

- 主判：`deepseek-v4-pro`（与 n=20 / n=60 基线同一 judge）；官方 `gpt-4o-2024-08-06` 本机不可得 → 自建基线，
  不与发布分（88.4/82.0）比较。
- 答题模型：`deepseek-flash-1017` @ `https://token.tokenbroad.com/v1`（真实主槽，key 取自 `~/.hive-go/env`，未打印）。
- 数据：`longmemeval_s_cleaned.json`（277,383,467 B，sha256 `d6f21ea9…c3a442`）拆分的 `s_cleaned/`（500 题）。
- 代码：worktree `/Users/mac/hive/.wt/lm-200`，分支 `lm-200`，基线 `982af601`（main，已含 notes runner 支持）；
  Go 二进制 `/tmp/hive-longmemeval-lm200`（sha256 `9dda1005…4e1ec`）。
- 证据目录：`go_hive/docs/e2e-assets/longmemeval/200q/`（样本、脚本、四组 raw rows、逐题 JSON、summary、次判归档）。

## 1. 方法

### 1.1 样本（确定种子，均衡配额，n=200）

`200q/sample-n200.json` 记录完整清单与算法；`200q/sample_lme_200.py` 可复算：

- seed 0，单个 CPython `random.Random(0)`；按报告用的六类固定顺序
  （SSU → SSA → MS → TR → KU → SP）逐类 `ids = sorted(ids); rng.shuffle(ids); 取前 quota`，
  quota = min(ceil(200/6)=34, 该类供给)。
- 结果：**SSU 34 / SSA 34 / MS 34 / TR 34 / KU 34 / SP 30 = 200**。single-session-preference 全集只有 30 题，
  所以取满 30，其余五类各 34；这是数据集允许的最均衡配额（严格 200/6=33.33 不可整除，按比例配额会让
  MS/TR 各占 ~53 题，失去均衡性）。
- id 列表 sha256（换行连接）：`697330b90e61fe45766ee0a41e76208acaff8cd01d8117c10c38632219e8669a`；
  样本文件 sha256：`6ce0abda…e3574`；`_abs` 弃权题 8 道。
- **与 n=60 的关系（已机械验证）**：本脚本对 n=60 的抽样结果与 `60q/sample-n60.json` **逐 id 完全一致**
  （脚本 `--verify` 输出 `per_type_prefix_ok=True`）。因此 n=200 的样本包含 n=60 的全部 60 题（按类前缀），
  本轮可以直接做「同题重跑」一致性对比，不需要重新映射。
- 复现记录：`60q/sample-n60.json` 的 `selection.method` 文字写「sorted by type name」，但按字母序无法复现该文件；
  能逐 id 复现的是报告用的固定六类顺序（也已在本脚本注释中注明）。这是上一份样本元数据的一处文字偏差，
  样本本身有效。
- 配额对题型难度的影响：60q 时每类 10 题；本轮 preference 从 10 扩到 30（该类型旧样本 6/10 正确），
  MS/TR/KU 从 10 扩到 34。总体分是「六类等权」的估计，不是 500 题的按比例估计。

### 1.2 四组运行（同一份显式 id 列表传给两侧）

| 组 | 命令 | 运行目录 | 并发 | 墙钟 |
|---|---|---|---|---|
| Go 无 notes | `bash 200q/run-go-200.sh` | `runs/go-200` | 1（单进程顺序） | 59m03s（12:17:42→13:16:45） |
| Py 无 notes | `bash 200q/run-py-200.sh`（`PYTEST_WORKERS=4`） | `runs/py-200` | 4 | 13m08s（pytest 786.74s） |
| Go 有 notes | `HIVE_LME_NOTES_CONCURRENCY=24 bash 200q/run-go-200-notes.sh` | `runs/go-200-notes` | 预建 24 → 发问 1 | 3h10m53s（预建 2h08m08s + 发问 1h02m45s） |
| Py 有 notes | `PYTEST_WORKERS=14 bash 200q/run-py-200-notes.sh` | `runs/py-200-notes` | 14（逐题内联建 notes） | 3h16m31s（pytest 11788.63s） |

脚本都在 `200q/` 内，逻辑与 60q 的 `run-*.sh` 相同：`set +x` 后 `source ~/.hive-go/env`，只用
`BROADTOKEN_API_KEY` 派生 `HIVE_LME_*` / `HIVE_LIVE_*`，不打印 key；每个题仍使用隔离 `HIVE_HOME` + 冻结时钟 +
官方 judge prompt（字节级一致性沿用 2026-11-21 证据）。

- notes 语义与上游一致：Go `hive-longmemeval run --notes` / `notes` 预建；Py `HIVE_LME_NOTES=1` + `build_notes`。
  两侧 notes 缓存各自生成（Go `notes_cache/deepseek-flash-1017/feb123fc447c/`，Py `…/c77ef7180f69/`），
  均命中 n=60 的 60 题（每题 60 条缓存复用），其余 140 题各自新建。
- 并发上限：启动阶段 Go 预建 24 + Py base 4 + Go base 1 ≈ 29 并发；Py base 结束后 Py notes 14 + Go 预建 24 +
  Go base 1 ≈ **39 并发峰值**（与 2026-11-22 60q-notes 轮次的 38–40 并发同量级）。

### 1.3 judge 与次判

- 主判：`deepseek-v4-pro` @ tokenbroad（同 60q）。judge 调用独立计费/重试，题目行里记录 judge_model。
- 次判（敏感性对照）：本机 judge 槽 TypeSafe `127.0.0.1:18099/v1`（`0.8B-Instant-MLX-4bit`），
  经 `200q/longmem_typesafe_judge_proxy.py`（60q 的同款桥，阈值 0.5）转成 OpenAI chat；
  用 `hive-longmemeval rejudge` 对四组 800 条答案全部重判，原始日志 801 次调用（含 1 次健康检查）。
  桥接日志在 `/tmp/typesafe-200/judge-log.jsonl`（不入库），重判结果归档在 `200q/typesafe/`。

### 1.4 失败重试 / 限流 / 环境事件（如实记录）

- **失败重试未触发**：四组 200/200 行、unique 200、`error`=0、`judge_error`=0、ungraded=0。
  脚本内的 `RETRY_IDS` 路径（`prune_failed.py` 剪行 + 单题重跑）本轮没有用上。
- **未观察到 HTTP 限流**：四份日志中没有 429 / rate limit / Too Many Requests / 5xx 记录
  （Py 日志里 `timeout` 字样全部来自 pytest traceback 的源码行，不是运行事件；无 judge 超时）。
- 但**吞吐在并发升高时明显变慢**：同样的笔记构建，60q 轮次 24 并发约 17 分钟/题，本轮 24+14 并发下约 24–25 分钟/题；
  Go 无 notes 的 200 题单进程耗时 59m（60q 折合约 52m）。这是「共享端点吞吐被占满」而不是报错限流，
  对分数影响不可直接测量，记录在案。
- 唯一一次单题超时：Py notes 的 `gpt4_fa19884d`（TR）queen 轮次跑到 420s 上限，仍产出了被判错的答案行
  （无 error 字段；工具轨迹显示 20+ 次 `terminal_exec` 循环）。按「有答案、已判分」计入 200/200；
  该题若重跑至多影响 1 题（0.5pt）。Go 四组最大单题耗时 115s，无超时。
- Go notes 预建中 `70b3e69b` 有 1 个会话的反思失败（上游语义：单会话失败容忍，该题仍生成 38 条笔记），
  其余 139 题 failed reflections=0。
- 环境：机器 load ≈ 2（10 核 / 16 GB），跑前无孤儿进程；四组共享同一 tokenbroad 端点。

notes 在两侧都是正向但不显著（Go +6、Py +2），与 60q 时「Go +2 / Py −1」方向不同——这正是单次运行噪声的量级。

### 2.5 次判敏感性（0.8B TypeSafe judge 槽，重判同 800 条答案）

| | Go 无 notes | Py 无 notes | Go 有 notes | Py 有 notes |
|---|---|---|---|---|
| 0.8B overall | 158 = 79.0% | 168 = 84.0% | 178 = 89.0% | 166 = 83.0% |
| 95% CI | 72.8–84.1 | 78.3–88.4 | 83.9–92.6 | 77.2–87.6 |
| 与主判一致率 | 77.5% | 80.5% | 83.5% | 81.5% |

- 无 notes 组：两种 judge 都是 Py 领先（主判 −8、次判 −10，p=0.12），方向稳健；但绝对分整体下移/上移 8–9pt。
- notes 组：主判 Py 领先 4 题；次判 **Go 反超 12 题（p=0.0501）**，且次判下 Go 的 notes 增益 +20 题（p=0.0022）、
  Py 的 notes 增益 −2。judge 选择足以改变 notes 组间结论 → notes 的效应在本数据上不是稳健信号。
- 与 60q 的 81.7% 一致率同量级（0.8B 偏严且欠校准，仅作方向对照）。

### 2.6 与 n=60 的一致性（同 60 题重跑；本样本是 60q 的按类超集）

| 组 | 60q 旧结果 | 本轮 60 题子集 | 逐题一致率 | 翻对 / 翻错 |
|---|:--:|:--:|:--:|:--:|
| Go 无 notes | 52/60 | **49/60** | 91.7% (55/60) | +1 / −4 |
| Py 无 notes | 51/60 | **57/60** | 90.0% (54/60) | +6 / −0 |
| Go 有 notes | 54/60 | **53/60** | 85.0% (51/60) | +4 / −5 |
| Py 有 notes | 50/60 | **53/60** | 88.3% (53/60) | +5 / −2 |

- 旧结论「Go 无 notes 领先 1 题、Go notes 领先 4 题」在本轮同题上**方向反转**（Py 无 notes 领先 8 题；notes 两组打平 53:53）。
- 把 n=200 拆成「旧 60 题」与「新增 140 题」：

| 组 | 旧 60 题 | 新增 140 题 | n=200 合计 |
|---|:--:|:--:|:--:|
| Go 无 notes | 49/60 | **126/140** | 175/200 |
| Py 无 notes | 57/60 | **126/140** | 183/200 |
| Go 有 notes | 53/60 | 128/140 | 181/200 |
| Py 有 notes | 53/60 | 132/140 | 185/200 |

**无 notes 组在 140 道首次运行的新题上完全打平（126:126）**；n=200 的 −8 题差距全部落在旧 60 题上，
而旧 60 题的结果本身在 5 小时内从「Go +1」翻成「Py +8」。这是本轮最重要的证据：
**同一 60 题、同一代码、同一模型名的两次运行可以差 6–8 题，n=60 的 ±1 题结论没有可复现性。**

### 3.2 失败模式（抽查 + 自动统计）

1. **preference 的档案复用仍是主因（20 个无 notes 分歧中 13 个）**，且双向发生——谁这一轮检索/复用了用户档案，谁就赢：
   - `07b6f563`（Go 错）：Py 以「you're on an iPhone 13 Pro」开场并据此推荐配件；Go 给通用配件清单，
     未复用档案事实。与 60q 同一题同一模式。
   - `1a1907b4`（Go 错）：Py 复用「Hendrick's kick / Pimm's Cup」的既有口味偏好；Go 先反问三个问题再给方案。
   - `d24813b1`（Py 错）：Go 复用用户做过的 lemon poppyseed cake 并据此给两个烘焙方案；Py 走通用「批量烘焙」建议。
   - `0a34ad58`（Py 错）：Go 用用户已有的 Suica + 新宿住宿信息组织东京交通建议；Py 给通用东京新手提示。
   → 与 60q 报告一致：偏好题的 rubric 要求复用档案，检索到的会话内容是否被写进答案决定成败。
2. **multi-session 价格/计数题**：`91b15a6e`（Go 错）——两侧都给出 $5,000 + $150 = $5,150，Go 写成
   「figuring it's worth at least that」，Py 以「Short answer: $5,150」开头；judge 只判 Py 对。
   `88432d0a_abs`、`edced276` 也是 Py 对 Go 错，属于多会话下钻深度的老问题。
3. **judge 措辞敏感（噪声）**：除 `91b15a6e` 外，`e61a7584`（KU）两侧答案都含「nine months」，
   Go 的表述被判错、Py 被判对；60q 的 `3a704032` 是同类（两答案实质相同、判定相反）。
   0.8B 次判与主判 77.5–83.5% 的一致率也说明单次 judge 判定有 1–2 成噪声。

本轮没有出现新的失败类别；60q 报告归纳的「偏好个性化缺失 / 多会话聚合不完整 / 弃权不彻底 / 时间窗口径 /
judge 措辞噪声」在本轮 200 题上仍可覆盖观察到的样本。弃权题 8 题：Go 7/8、Py 7/8（无 notes），Py notes 6/8，
说明弃权仍是最容易受措辞影响的一类。

## 5. 限制与结论

- **结论**：n=200 上四组两两配对全部不显著（最小 p=0.0525，且是跨条件对比）；notes 对两侧都是正向
  但不显著（Go +6 / Py +2）。**没有实现级差异的证据。** 方向性排序（Py ≥ Go）在本轮出现，但同题重跑显示
  单次运行可翻转 6–8 题的量级，不足以支持「Py 优于 Go」的结论。
- **n=60 → n=200 的一致性**：旧 60 题本轮 Go 52→49、Py 51→57；新增 140 题两侧无 notes **126:126 完全打平**。
  这直接说明：n=60 的 ±1 题差值来自运行噪声（端点/判分/检索路径），不是实现差异；也解释了为什么 n=20 与
  n=60 的领先方向会来回摆。若后续要宣称实现差异，必须报告同题重复运行的方差，而不只是单次配对检验。
- **judge 不是官方 judge**：`deepseek-v4-pro` 与 0.8B 槽的一致率 77.5–83.5%，后者会改写 notes 组间排序
  （主判 Py 领先 4 题，次判 Go 领先 12 题）。发布分 88.4/82.0 不可直接比较。
- **单次运行**：四组各跑一次；没有对同组做 N 次重复来直接估计方差（用同 60 题跨 5 小时的两次运行做了替代估计）。
- **样本口径**：六类等权（34×5+30），不是 500 题按比例估计；SP 只有 30 题，该型 Wilson 区间仍较宽（±17pt）。
- **环境**：并发峰值 ~39 个进行中的 LLM 调用时，notes 构建吞吐明显下降（无 429）；Py notes 有 1 题触到
  420s 单题上限并判错；Go notes 预建有 1 个会话反思失败（容忍语义）。这些都如实记录，未发现对两侧的系统性偏向。
- 数据/代码可复算：见 §4 命令；样本与 n=60 的包含关系有脚本级验证。
