01会话能活多久

会话本身没有 TTL、最大轮数或最大寿命：会话是磁盘目录（meta/state/events/conversations/parts/checkpoints），进程退出后可以 resume；Go/Python 都支持跨重启、跨版本迁移。真正的上限发生在“单轮迭代、上下文窗口、记忆容量、存储保留”四层。

会话类型能活多久单轮上限额外增长点
Queen DM无期限；重启用 resume999,999 次迭代（HIVE_MAX_ITER 可压低）conversations/parts、events、日志
Colony queen无期限；与 DM 同机制999,999 次迭代tracker.db、worker 工位、playbook 运行记录
Worker短生命周期（被派生的任务）3 + 1 收尾（可被 queen 按次覆盖）工位转录/data，默认 14 天后可被 janitor 深清
“几十年”在代码层可行，但进程必须重启后 resume 会话；触发器、webhook HTTP 服务、timer goroutine 都在会话进程内，机器重启后要重新加载会话才恢复。

03压缩流水线：能继续聊，但不是无损

保真度边界：压缩不是“无损归档”。旧对话会变成摘要，逐字细节只对最近 40 条用户消息（可用 HIVE_MAX_VERBATIM_CLIENT_MSGS 调整）和最近 6 条可重取工具结果保留。要长期保留的事实必须写入 memory / skill / 文档，而不是指望聊天记录。

07“连续运行几十年”的前提

  1. 进程可恢复：机器重启后 hive serve 重新加载会话；否则会话只是磁盘上的静止数据，触发器/timer/webhook 都不会跑。
  2. 定期跑 janitor + 自己归档：queen parts、tracker.db、worker 工位不会自动瘦身；events 重写也只在 janitor 跑时发生。
  3. 接受摘要化：几十年对话不可能逐字保留；长期事实要写 memory/skill/文档。
  4. 模型/协议演进：换模型、换 provider、schema 升级都要迁移验证（v1→v3 home 已有双跑证据）。
  5. 成本：每次压缩、每 6 回合反思、每轮系统提示都在烧 token；长跑是持续成本。
  6. 触发器/队列：timer 是会话内 sleep-until-due，missed ticks 上限 100；webhook 队列无界、无背压，长跑要自己控流量。
