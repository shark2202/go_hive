00设计动机：三个失败模式

一句话：Reminder 解决“失忆”，Budget 解决“失控”，Park 解决“失联”；nudge / stall / sentinel 是停车后的看门狗。核心分工是 reminder 是内容，budget 是策略，park 是状态，supervisor 是恢复。
失忆
每轮重新定向
模型调用之间没有状态；压缩会丢工具结果；注意力会漂移
失控
确定性上限
自主循环可能无限重试、狂调工具、烧上下文与成本
失联
显式停车
等用户/凭据/queen/worker 是合法状态，不是空转或失败
被遗忘
看门狗
停下后需要有限次唤醒、故障恢复与人工升级
问题根因机制 / 为什么不能靠提示词
计划/约束被遗忘每次调用都是新 prompt；压缩丢结果；注意力漂移tasks / turn_context / skills_catalog / searchable_tools / memory_* 在生命周期点重新注入。提示词是静态的，这些信息每轮变化。
工具越调越多模型没有可靠的“已花多少”计数与成本感每 turn 软/硬工具预算、lifetime 预算、自适应 colony 预算。模型不能自证会停，必须由 loop 强制。
迭代/上下文失控自主循环可无限重试；窗口会被撑爆max_iterations + grace、compaction buffer、工具结果 spillover。这些是运行时资源，不是语义。
该等人却继续跑ask_user、凭据、colony 建议、等待 queen/workerParkReason 显式建模；等待是控制流，不是一句“请停下”。
正常结束被误判为故障干净 turn 结束、等用户下一条消息是合法的TURN_DONE / USER_STOPPED / COLD_INTERRUPTED 归为 silent_park，不自动唤醒。
真故障被静默吞掉LLM 报错、空回复、doom loop、流卡住归为 broken；stream stall 取消后重跑同一 inner turn。

01机制分界：内容 / 策略 / 状态 / 恢复

机制回答的问题是什么 / 不是什么
Reminder这一轮它该知道什么source 在生命周期点产出 body，合并成一个 <system-reminder>。不是系统提示（会变、不该进缓存前缀），不是用户消息（会可见、会触发 turn）。
Nudge该不该催它行动reminder 中“带行动推力”的子集；不是独立类型。有 caps、cooldown、energize 语义。
Budget还能花多少确定性策略：软检查点负责 steer，硬上限负责停止，grace 负责收尾。不是模型可自行放宽的建议。
Park为什么停下、等谁持久状态（reason + activity + pending_input），不是一条消息。决定 supervisor 是否打扰、能否 resume。
Supervisor停下后谁来管idle_nudge / sentinel / stream_stall / stall_check / worker_stall / doom loop；各自独立，互不替代。
先记住：reminder 是机制；nudge 是其中“催行动”的子集；worker_stall / stall_check / doom loop 是独立守卫；Sentinel 是停车后的 supervisor。stall 与 Sentinel 不能混为一谈。

03生命周期

3.1 Turn 生命周期

3.2 Reminder source 生命周期

  1. register：注册顺序就是合并顺序；上游 15 个 source 在每个 AgentLoop 上都注册，再由 applies_to 按角色/provider 过滤。
  2. bind：会话开始解析 active 子集；applies_to 抛错时 fail-open（保留 source）。
  3. observe_turn：每 turn 一次，tasks 等据此计数。
  4. collect(point)：source 在声明的 point 上 render；空 body 丢弃；异常隔离；ticker source 收集到 pending。
  5. drain：loop 在迭代边界 take_pending，由 loop 单写者写入对话，避免竞争。
  6. reset：用户消息到达时 idle_nudge / sentinel 的 caps 重挂，按“用户回复周期”而非整会话计。

3.3 Budget 生命周期

预算重置点耗尽行为
每 turn 工具调用每个 turn-loop 开始每 N 次发 TOOL_BUDGET_CHECKPOINT 软提醒（可带 fleet/tracker 快照）；到 hard 停止派发剩余调用，退出本 turn
lifetime整个 execute / 恢复累计进入 grace wind-down，限制终态工具，要求 report_to_parent 后结束
迭代每个 execute超出后进入 grace；worker 默认 3 工作 + 1 收尾
上下文每次构建 prompt到触发点压缩；POST_COMPACT 重新公告计划/记忆/工具/技能
自适应 colony单调不升按成功 worker 的 median/p90/max 收紧 nominal，clamp 在跑 worker；floor / max-guard / dispersion guard
流每个 turnTTFT / inter-event 超时 → 取消流 → 重试同一 inner turn，≤3/turn

05设计不变量与权衡

不变量 1–4
① Reminder 在用户消息之前，所有 body 合并成一个块；没有 source 时安静退化。
② Source 异常隔离：render/applies_to 抛错只跳过该 source。
③ 单写者：ticker/post 只进 pending，loop 在迭代边界 drain。
④ 每用户回复周期重置 caps；user_stopped 优先级最高；external_wait / silent_park 永不打扰。
不变量 5–8
⑤ Park 是持久状态，不是内存 flag；pending_input 是冷启动的唯一真相。
⑥ 先软后硬：软 checkpoint 用于 steer，hard 才停；lifetime 给 grace 收尾。
⑦ 自适应预算只降不升，且有 floor / max-guard / dispersion guard。
⑧ 看门狗分层：stream stall 恢复传输；stall_check 抓“说了没做”；worker_stall 抓纯文本；doom loop 抓重复指纹；sentinel 负责升级。
为什么不是另一种做法原因
塞进 system prompt信息每轮变化；进缓存前缀会破坏缓存；压缩后仍需重发。
作为普通用户消息用户可见、会触发新 turn、污染对话历史；reminder 是非唤醒的上下文。
Busy-wait / 轮询模型烧 token；无法跨重启；park 用持久状态 + 事件唤醒。
只设一个硬超时合法等待可能很久；需要区分 external_wait / silent_park。
让模型自己记预算模型无法可靠自计数；soft steer + 确定性 hard cap 才可测。
一个大 reminder source触发条件、caps、文案不同；拆开才能独立测试/调参/关闭。
代价：reminder 可能吵；预算可能误杀长任务；park 可能死等；ticker 可能双唤醒。缓解手段就是 caps、分类、grace、单 ticker、持久化与 golden/对位测试——这些机制必须显式建模，不能塞进一句提示词。
