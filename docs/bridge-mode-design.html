GO_HIVE · BRIDGE MODE · POST-1.0 REQUIREMENTS → DESIGN

BRIDGE_MODE → go_hive 远程控制面适配器 需求—设计链

把“本地 CLI 注册为远程执行器”的 Bridge 模式移植为 go_hive 的可选出站适配器：注册环境、长轮询取任务、ack/心跳/停止、映射真实 queen session、权限回到宿主审批。默认关闭，出站 only，post-1.0；不声称兼容 claude.ai / ByteBroad，直到控制面合同和 OAuth 访问被确认。

状态：design需求：14设计项：12验收：17范围：one private workspace, one active work per environment in v1, post-1.0 optional

00可行性判断

结论：传输可移植；控制面兼容性有条件；产品语义不能照搬。
原因：Bridge Mode is an outbound long-poll worker protocol, so Go can implement the HTTP client, environment registration, lease, heartbeat, cancellation, session mapping and permission relay with the standard library. The hard dependency is the external control plane: its endpoints, OAuth provider, work result contract and trusted-device semantics are not part of go_hive. A local design can pin a product-owned contract, but cannot honestly claim claude.ai or ByteBroad compatibility without that server contract.
可复用
  • HTTPS long-poll, bounded backoff and outbound-only networking are straightforward in Go.
  • hive serve already exposes a real session API: POST /api/sessions, chat, events and DELETE.
  • hive-cred and the credential store already provide a place for provider credentials; bridge must not invent a plaintext token file.
  • Sentinel's outbound long-poll listeners are a useful lifecycle and backoff reference, not the bridge protocol itself.
  • The event bus already carries ask-user and client-input events that can be relayed to a host approval surface.
不能直接搬
  • The control-plane endpoints, OAuth refresh and trusted-device rules are external; they cannot be fabricated locally.
  • A remote work id is not a Hive session id; a mapping and ownership check must be designed, not assumed.
  • Bridge must not expose an inbound port or reuse HIVE_DESKTOP_TOKEN.
  • Bridge is not LAN Pipes: it has no multicast discovery and no peer-to-peer prompt routing.
  • The feature is outside upstream Hive 1.0 and outside the current alignment scope.
目标之外：Turn a local go_hive installation into a remotely controlled executor without exposing an inbound port. The remote control plane chooses work; the local process retains ownership of session creation, tool execution, permission decisions and audit. The model never receives a raw remote prompt that bypasses the queen/colony runtime.

go_hive already has a local session API and a queen/colony runtime, but no outbound control-plane client. An operator who wants to use a web control plane must open an inbound port, copy a desktop token and manually manage sessions. Bridge Mode describes the missing pattern: register once, poll work behind NAT, run a real session, relay approval, and release the lease.

用户价值
  • A local installation can be driven from a control plane without an inbound port.
  • Remote work maps to a real Hive session, so queen/colony tools and audit still apply.
  • Permission and ask-user prompts stay human-approved on the host side.
  • A crashed or stopped worker does not silently duplicate work or leak a lease.
  • Operators can see environment, work, session and last error in one status surface.
为什么不是当前 parity
This is an additive remote-control capability, not an upstream Hive feature. It must remain design-only until the control-plane owner, credential model, workspace isolation and permission relay are accepted. A complete-looking page is not implementation evidence.

非目标

  • Do not copy claude.ai or ByteBroad's proprietary control plane or claim compatibility without its contract and OAuth access.
  • Do not expose an inbound bridge port or reuse HIVE_DESKTOP_TOKEN as the bridge credential.
  • Do not add a raw remote prompt path that bypasses SessionManager, queen/colony runtime, permissions or audit.
  • Do not add LAN discovery, multicast, peer-to-peer control or multi-hop federation; that is the separate LAN Pipes design.
  • Do not add a model-facing bridge_* tool or a new default tool surface.
  • Do not add multi-tenant isolation, public internet exposure or a hosted SaaS control plane in v1.
  • Do not make bridge mode a Hive 1.0 parity item or a commercial release gate without explicit approval.
  • Do not log environment secrets, OAuth tokens, trusted-device tokens or full message bodies.

前提

  • The control plane owner provides a pinned HTTP contract, OAuth provider and environment registration policy.
  • The local process has a dedicated workspace and can run without a shared HIVE_HOME containing unrelated sessions.
  • A remote work is represented by a stable work id and an explicit session reference; unknown types fail closed.
  • The host UI or CLI is the permission authority; the remote model is never an approval authority.
  • The control plane can tolerate a 10s long poll, bounded backoff and duplicate deliveries.
  • A real control-plane run requires credentials not present in this repository and must be recorded separately.
  • Bridge is single-hop; multi-hop and LAN P2P are separate designs.

操作序列

  1. register environment with OAuth bearer
  2. persist environment id/secret; start outbound poll
  3. poll work; validate environment id and work type
  4. persist work-to-session mapping; ack work
  5. create or resume the local Hive session; run the turn
  6. heartbeat the lease while running
  7. relay ask-user/tool permission event; host approves or denies
  8. post result/status through the pinned control-plane channel
  9. stop on cancel/lease loss; archive; deregister on shutdown

控制面操作

  • POST /v1/environments/bridge
  • GET /v1/environments/{id}/work/poll
  • POST /v1/environments/{id}/work/{workId}/ack
  • POST /v1/environments/{id}/work/{workId}/stop
  • POST /v1/environments/{id}/work/{workId}/heartbeat
  • DELETE /v1/environments/bridge/{id}
  • POST /v1/sessions/{id}/archive
  • POST /v1/sessions/{id}/events
  • POST /v1/environments/{id}/bridge/reconnect

03方案决策

ID方案结论理由
O1Outbound bridge adapter over the existing Hive session APIchosenKeeps session creation, queen/colony semantics, permissions and audit local; works behind NAT; maps cleanly to a v2-style environment and lease.
O2Expose the existing hive serve API directly to the control planerejectedRequires an inbound port and broad desktop-token access; the control plane could reach unrelated APIs. It also ignores environment registration, lease and permission relay.
O3Reuse LAN Pipes multicast/TCP as the remote control transportrejectedBridge is a control-plane-to-executor direction, not peer discovery. LAN Pipes has no environment registration, lease or remote approval model.
O4SSH reverse tunnel or static reverse proxy to hive servedeferredUseful as an emergency deployment, but it provides no environment lifecycle, work queue or remote approval UX and still exposes a broad local API.
O5Direct claude.ai / ByteBroad bridge compatibilityrejected for v1The endpoints, OAuth, trusted-device and result contract are external and unpinned; claiming compatibility without them would be fabricated.
O6In-process delegate_task onlyrejectedIt solves local fan-out, not remote control behind NAT. It has no environment, lease, cancellation or control-plane permission semantics.
选择：Implement BRIDGE_MODE as an optional outbound bridge adapter for go_hive. The local process registers an environment with a control plane, long-polls work, acknowledges and heartbeats a lease, maps the work to a real local Hive session, relays permission events, and archives the session. It is v2-style env-less, outbound-only, default off, and post-1.0. It is not a LAN peer transport and it does not claim compatibility with claude.ai or ByteBroad's proprietary bridge until their control-plane contract and OAuth access are provided.

04设计链

D1

Opt-in scope and deployment

Bridge routes and the poller mount only when bridge.enabled is true. Default serve remains loopback; the bridge client is outbound and opens no inbound port. The feature is post-1.0, not part of the frozen route or tool surface, and can be killed without affecting local sessions.

D2

Control-plane client contract

A single client owns the pinned base URL, API version, OAuth registration, work poll, ack, heartbeat, stop, deregister, archive, permission event and reconnect. It validates server ids with a small allowlist, rejects path traversal, uses bounded timeouts and never reads a per-request URL from work data.

D3

Identity and credentials

Environment id and secret are issued by registration; OAuth and trusted-device material live in the credential store. Config names a credential handle or env var, never a literal secret. The desktop token is a different principal and is rejected. Logs redact headers, tokens and message bodies.

D4

Environment lifecycle

Register is idempotent by reuse id; the id/secret pair is persisted atomically before polling. Deregister revokes the lease and stops polling. A restart reuses the persisted environment and does not create an orphan. A failed deregister is reported, not silently ignored.

D5

Work lifecycle and idempotency

Poll returns one work; the client validates type and required ids, persists a work-to-session mapping, then acks. A redelivered work id reuses that mapping and never starts a second turn. Unknown work types, mismatched environment ids and malformed payloads fail closed before ack.

D6

Session mapping and ownership

A remote work maps to a local queen session created through the existing SessionManager. The mapping stores environment id, work id, local session id and workspace/profile; it never accepts an arbitrary local session id from the control plane. Colony spawning is allowed through the session's normal runtime and locks the session as usual.

D7

Permission relay

ask-user and tool-permission events are published to a host approval surface and forwarded as a control-plane event with work, session and request ids. Only a host decision is accepted; request ids expire on cancel, timeout, close or lease loss. A remote model cannot approve its own request.

D8

Lease, heartbeat and cancellation

A live work renews its lease with heartbeat. Soft timeout asks the session to stop; hard timeout and lease loss cancel the turn. Stop is idempotent and late heartbeats cannot resurrect a lost lease. Process crash recovery either resumes the same session or reports a typed lost-lease error.

D9

Events, results and archive

Session events are bounded and ordered; the control-plane result channel is pinned before implementation. Archive is idempotent (409 = already archived) and does not delete local audit. An event gap is reported, never silently reset. Local session history remains the durable source.

D10

Security and isolation

Outbound HTTPS only; control-plane host allowlist; dedicated workspace; no shared HIVE_HOME; no desktop API exposure; no auto-approval; no shell interpolation from remote text; body/event caps; per-environment rate limits; kill switch. The bridge is a remote code-execution surface and is treated as such.

D11

Operator surface and audit

hive bridge status/register/deregister and GET /api/bridge/status expose enabled, environment id, control-plane URL, lease, work, local session, last error and stop reason. Audit records environment/work/session and permission outcome; tokens and message bodies are redacted.

D12

Package, tool and dependency boundary

internal/bridge owns transport, protocol, store, lease, runner and policy; internal/server/bridge_adapter.go is the only SessionManager wiring; internal/cli/bridge.go is the operator entry. internal/bridge must not import internal/server, internal/cli or internal/tools/builtin. No model-facing bridge tool is registered; no bundled peer runtime; CGO_ENABLED=0.

包边界：internal/bridge 负责 transport/protocol/store/lease/runner/policy；internal/server/bridge_adapter.go 只做 SessionManager 接线；internal/cli/bridge.go 只做 operator entry。核心不得 import internal/server、internal/cli 或 internal/tools/builtin；不注册 model-facing bridge 工具。

Limits
  • max_sessions: v1 default 1; hard cap configurable, never unbounded
  • poll_timeout: 10s documented; client timeout includes margin
  • heartbeat: must be strictly below the control-plane lease
  • work_payload: bounded JSON; unknown fields preserved only where the contract says so

  • retry: bounded backoff; 401 refresh once; 403/404/410 fatal; no infinite loop

  • 是否进入 1.0 发布；本设计建议 post-1.0。

待拍板

  • Who owns the control plane, and what is the exact pinned API/OAuth/result contract? Without this, implementation is blocked.
  • Should v1 support only one active work per environment, or a bounded pool? The proposal is one.
  • Should the remote work map to a queen session or a colony session? The proposal creates a queen session and lets normal colony semantics apply.
  • What is the result/status channel? The attached document names nine operations but not a result upload; this must be pinned.
  • Should trusted-device v2 be required, or is environment-secret + TLS sufficient for v1? The proposal prefers v2 when available.
  • Should bridge mode be in the 1.0 release at all? The proposal keeps it post-1.0 and out of parity.
