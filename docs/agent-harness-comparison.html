Agent Runtime Comparison

三种 agent 运行时对照：hive · oh-my-hermes · prime-agent

01三方定位（决定了它们只能怎么解）

hive
自己拥有 loop
一个 agent loop；Queen 与 worker 是同一段代码的两组参数；无人值守跑 colony
oh-my-hermes
没有自己的 loop
Hermes Agent 之上的一层："It never patches or replaces Hermes"。它决定"往 loop 里放什么、谁干、什么算 done"
prime-agent
自己的 loop + daemon
RLM（context 即变量 / 子 agent 即函数调用，跑在持久 Python REPL）+ Continual Harness（可编辑的持久 harness 状态）
这个差异决定了后面每一行。OMH 只能在"编排与证据"上加杠杆（loop 不是它的）；hive 必须把"人在场"的每项职能翻译成 loop 内的机制；prime-agent 则可以同时改 loop、改 daemon、改资产层。

02逐机制对照

2.1 多 agent 编排

prime-agent 的 Continual Harness 具体长什么样（代码级）

// HARNESS_STATE_DIR_NAME = "harness"
// REFINEMENT_HISTORY_FILE_NAME = "refinement_history.jsonl"
// DEFAULT_OVERVIEW_ENTRY_LIMIT = 3 · DEFAULT_OVERVIEW_CONTENT_LIMIT = 140 · DEFAULT_OVERVIEW_REFINEMENT_LIMIT = 10

/refine 的系统提示词自己把定位讲得很清楚：

"This is similar in spirit to context compaction, but instead of summarizing the conversation you emit precise Create, Update, or Delete edits to reusable state."
"The base system prompt is immutable and MUST NOT be rewritten."
"Prefer small evidence-backed edits. If prior refinements caused issues, rollback or replace the faulty editable entries."

还有一条独立的自动复核提示词（AUTO_REFINE_REVIEW_SYSTEM_PROMPT）：

"Decide whether this checkpoint should run /refine … Reject one-off noise, unsupported hypotheses, and transient tool outputs. Ask for global refinement only for durable cross-session lessons or explicitly project-qualified lessons likely to be reused."

而 skill 类条目必须是真可调用的，不是散文：

reference: {"type":"python", "import":"pkg.module", "callable":"fn", "call_pattern":"await fn(...)"}
arguments: {"name": {"type":"string","required":true,"description":"..."}}
这就是我前面判定 hive「有变异、有遗传、没有选择 → 漂变」时缺的那块，而且补法比"加评分系统"便宜得多：
  1. 不是自由重写，是受约束的编辑提案：JSON 定形 → 可校验、可审计、可回放。
  2. 选择不是打分，是"再判一次要不要动手"：一次便宜调用拒掉一次性噪声。
  3. 回滚是一等公民：history + snapshot。
  4. 隔离用规则而非纪律：默认 local；想影响别的会话必须显式命名项目；local 期间 global 只读。
  5. 不可变底线：基础提示词永不被改写 —— 这是"允许自改"能安全存在的前提。

还有一个反问

OMH 的 /dag-ulw（图 + 写作用域不相交 + 独立验证节点）与 prime 的 factory（DAG 编译成状态机、写入时校验语义）都说明："有图"是可以工程化落地的。hive 的设计声明是「没有图，靠 tracker 与 binding」。这不是谁对谁错——

hive 的 tracker（行级事实、事后记账）与 OMH 的 node 写作用域不相交（事前分区）解决的是同一个问题：并行写冲突。而 hive 的 binding「没有绑定就拒绝运行」其实已经是分区思想的一个特例。

05公平起见：hive 领先的地方

项为什么另外两家没有

06三种设计哲学

hiveoh-my-hermesprime-agent
一句话一个 loop + 共享账本 + 大量运行期检测器不改 loop，在编排与证据上加杠杆唯一正面实现自改进的一家
怎么替代"人在场"检测器（stall/doom/judge/reminder）状态可信度（两段式证据 + 硬措辞）受约束的自编辑（提案 + 复核 + 回滚）
并行正确性靠事后记账（tracker）+ 绑定事前分区（写作用域不相交）+ 独立验证节点显式消息 + 状态机 validator
知识怎么长记住并复用（明确否认 evolution）只在 benchmark 说有用时保留小步、可审计、可回滚的编辑
主要风险库只增不减、无选择压力、覆盖无痕证据链必须整条配合（展示层即契约）自编辑的爆炸半径（用 scope 规则 + 不可变底线压）
