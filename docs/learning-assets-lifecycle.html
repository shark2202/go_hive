01为什么 hive 的 loop 需要"资产"这一层

先把坐标定住：pi-agent 的 loop 里没有 skill / playbook / reminder / stall check 这些东西。不是因为没想到，是因为它不需要——它有一个坐在终端前的人。

两者共享同一副骨架

步pi 1.5.2 runLoophive
1流式响应（text_delta/thinking_delta/toolcall_delta）同
2取 message.content.filter(c => c.type === "toolCall")同
3严格顺序：for (toolCall of toolCalls) { await runToolCall(...) }只读工具并行，其余按序
4结果 push 回 context.messages同
5finishTurn → {action:"end"|"continue"}judge → ACCEPT / RETRY / ESCALATE
6for(;;) 继续同

分野在哪：pi 把复杂度外包给"人"，hive 必须把人的职能翻译成机制

pi 里由人承担hive 的替代机制为什么不能省
盯着屏幕，发现它在复读n-gram 相似度停滞检测无人值守；判据是零成本纯函数，可以每轮查
发现它反复调同一个工具doom loop 检测 + replay breaker + 豁免表重复调用产生 N 倍副作用
发现流卡住，手动重发stream watchdog + STREAM_STALLED 同步注入通道问题，与模型无关
判断"这活干完了吗"judge（criteria / output_keys / 会话质量）需要语义判据，只能花 LLM 调用
提醒它"还有 3 个 worker 在跑"reminder hub（14 源 × 9 个已知时点）防重复派工、防压缩后失忆
崩溃后重开、重述任务游标落盘 + park/resume（ParkReason 11 值）parked 状态必须能被机器读懂，才能决定推一把/升级/续跑
调度多个助手并汇总colony + run_worker + tracker + bindingworker 之间不对话，只写账本
记得上次怎么做的skill / playbook / memory / soul上下文一压缩就没了；这是本文的主题
手动重复一整套步骤playbook（可重跑的收敛流程）逐行手工派工不可靠且活不过压缩
一句话：pi 的 loop 复杂度上限 = 一个人能理解的；hive 的复杂度上限 = 一个无人值守的 colony 需要的。资产层（skill / playbook）存在的唯一理由是：Queen 的调度意图和方法必须活过上下文压缩与进程重启。

03playbook 专章

3.1 它是程序吗 —— 是，但准确的说法是「被宿主收编的脚本」

判据证据
有文件 + manifest + 入口保存为 playbooks/<sanitized-name>.play.py；必须定义 meta（name/description/可选 concurrency，默认 8、上限 32）和 async def run(args)，缺一个即 PlaybookScriptError
真的被执行上游在进程内 exec 命名空间；Go 起 外部 python3 子进程 + stdio 行式 JSON-RPC
API 是注入的，且刻意很窄只有 2 个跨进程：dispatch_one（派一个 worker 并等终态报告）、query_rows（tracker SELECT）。其余 converge / retry / backoff / lane / deadletter / log / phase 都是 runner 的纯函数
宿主收编了它的 I/Osys.stdout = sys.stderr，因为 stdout 是 RPC 通道——print() 不许污染协议

形制上类似 CGI / Lambda handler / 插件：程序 + 声明式入口 + 宿主注入的窄 API。

三条限定（否则会误用）

  1. 不是通用程序：没有工具、没有 LLM、没有 MCP、没有网络客户端。只能"派 worker + 读账本"。
  2. 必须幂等可重入（硬约束）：runner 原话——"It owns no durable state: the tracker is the source of truth, so 'what's done / what's left' is always a fresh query, and re-running a playbook is resume by construction."
  3. 格式在 Go 里异构：上游只有 .play.py（程序）；Go 还认 .play.json（rows.go:194 候选顺序 base+".play.json" 优先），而上游对 .play.json 零引用。

3.2 谁产生它 —— Queen 自己，被一条 reminder 在特定条件下催出来

信号判据含义
pilot 做过本会话调用过 browser_* 或 web_scrape她真的亲手做了一单 ⚠️ 见 L1
落账了刚写过 tracker（tracker_upsert / tracker_sql）"我完成了一单并记下了"

两个信号都到才响。代码注释原话：

"a queen who runs the first unit herself discovers the real selectors/edge-cases, validates the protocol, and seeds the tracker — so the playbook she writes next is correct. Nudging before the pilot would push her to fan out a guess."

配套开关：一旦调了 run_playbook → 立即静音；冷却 4 轮（HIVE_COLONY_PARALLEL_COOLDOWN）；每会话最多 4 次（HIVE_COLONY_PARALLEL_MAX）——防它变成壁纸。

产生的机制：「保存不是动作，是 run_playbook 的副作用」

if source_path:                       # 从路径/名字来的 → 它本来就在库里
    saved_path = source_path
else:                                 # 内联脚本 → 顺手落盘
    _persist_script(binding.dir, meta.get("name") or run_id, script)
    # → <colony>/playbooks/<sanitize(name)>.play.py   （playbooks/ 目录在这里懒建）

没有"新建 playbook"这个动作：写一个 playbook = 跑一个内联脚本。Queen 的实际循环是 写内联 → 跑 → 自动存 → 按名重跑 → 改了再跑（注释叫 *the edit-and-re-run iteration loop*）。

命名 _sanitize_name：小写 → 非 [alnum-_] 换 - → 去首尾 - → 截 64 字符 → 空则 playbook。同名 = 直接 write_text 覆盖：无版本、无备份、无锁。

3.3 怎么用 —— 三选一入口 + 四个工具

_resolve_script 入口来源校验
playbook内联脚本字符串（跑完自动存进库）—
playbook_path磁盘任意路径（expanduser 后 is_file）只验存在
playbook_name库（<colony>/playbooks/）后缀探测 + 失败时列出库内容

执行链：Load() 校验 → _resolve_concurrency(meta)（默认 8、上限 32，超限直接 failed）→ 临时抬升 colony 的 max_concurrent_workers 到 max(原值, meta.concurrency)，跑完恢复 → 注入 hooks 执行 → 写 colony.db.playbook_runs。

工具作用
run_playbook启动；返回 run_id + name + path
get_playbook_status(run_id)查一次运行
stop_playbook杀收敛循环
list_playbook_runs(run_id?, limit=20)读运行日志
stop_playbook 为什么必须存在（代码原话）："A bare stop_worker only kills the workers that are live right now — it does not touch a playbook's convergence loop, which immediately re-dispatches fresh workers for any still-pending rows. So 'stop all workers' is a lie while a playbook is running."

3.4 怎么发现 —— 三条路都很弱，这就是最薄的一环

路径机制能看到什么 / 问题
运行日志（最可靠）list_playbook_runs 返回每行 name（playbook_runs.name 列）只看到跑过的；要 Queen 主动去查
踩空后看到playbook_name 未命中 → 报错附清单（现扫目录 glob("*.play.py")）反应式：事先不知道
回话历史上次返回的 name+path 还在上下文里压缩就可能丢

明确没有的：✗ 无 list_playbooks 工具（只有 list_playbook_runs）· ✗ 无注册表 / 索引文件（playbook_runs 是执行记录，不是册子）· ✗ 不主动注入提示词 · ✗ reminder 不列库（colony_parallel_nudge 只催"去写/去跑"）。

为什么没有册子是自洽的：playbook 自产自用，生产者 = 消费者。它和 runner 的设计声明同源——"owns no durable state: the tracker is the source of truth"；同理 目录才是真源。好处：永不失同步、cp 进去立刻可用、删文件即下线。代价见 §07。

3.5 怎么销毁 / 下架 —— 基本不存在

想要的现状
delete / retire 工具不存在（4 个工具只覆盖 run / status / stop / list-runs）
生命周期标记（deprecated / archived）无
引用检查（谁在用它）无
GC / 保留策略janitor 完全不管 playbook
运行记录清理playbook_runs 永不清
实际做法① terminal_exec 里 rm/mv；② write_file 覆盖成占位；③ 人工删文件
最关键的不对称：playbook_path 允许从任意路径执行。所以 playbooks/ 目录 ≠ "能执行的集合"，删掉文件 ≠ 不可执行。真正的"下架"只能靠不再给出路径——这是约定，不是强制边界。

3.6 迁移

通道是否带走 playbook
colony 打包 / 导入✅ 带走。导入解压只排除 sessions，playbooks/ 会一起解出来 → 唯一正规的分发通道
colony fork❌ 不带（只写 metadata.json + worker.json）
colony scaffold❌ 不预建目录（只建 skills/、runs/、triggers.json）
跨 colony 复用❌ 无 scope 机制，只能复制文件

04skill 专章

4.1 沉淀

write_skill(draft) → 写到 target_root/{draft.name}/，返回 (installed_path, error, replaced)。

  • 默认 replace_existing=True → 覆盖，并把 replaced 布尔回给调用方
  • replace_existing=False 且目录已存在 → 拒绝写入（非致命错误，调用方决定报 409 还是告警）
  • 失败时 installed_path=None，目标尽力保持原样

形制：SKILL.md = YAML frontmatter + markdown 正文，严格按 Agent Skills 标准解析（缺 description 才跳过，其余只告警）。

4.2 应用 —— 谁在什么时机看到新版本

消费者生效时机粒度
Queen每回合重读自己的 catalog（live_reload.py："A queen reads hers each turn, so she sees the change on her next one"）细：改完下一回合就看见
Workerspawn 时快照 SkillDirs粗：运行中的 worker 看不到新版本，下一批才可见 仓库文档
tool_gating工具在列表里 → 预激活对应 skill（browser_ → browser-automation）条件式
作用域framework / preset / project / user / external + per-queen skills_overrides.json分层遮蔽
这个不对称很重要：改 skill → Queen 立刻变强；已经在跑的那批 worker 不变。所以"改进"的传播边界是 spawn 边界，不是时间边界。

4.3 作用域与遮蔽

scope位置
frameworkskills/_default_skills
presetskills/_preset_skills
project（Hive）<project>/.hive/skills/
project（跨客户端）<project>/.agents/skills/ —— 与 Claude Code / Cursor 等共用
user（Hive）~/.hive/skills/
user（跨客户端）~/.agents/skills/
externalexternal_skills 路径（不存在时告警）
per-queen 覆盖~/.hive/agents/queens/{id}/skills_overrides.json —— 记录启用/禁用、provenance、参数微调。colony 没有自己的 store，继承其 owner queen 的

另有 trust 门禁：project 级 skill 来自被 clone 的仓库，可注入系统提示词，所以未受信仓库的 .hive/skills/ 需要显式信任。

4.4 消亡

janitor 明确保护 skills。 maintenance/retention.py 的 KEEP_ALWAYS 含 "skills"，注释写："Top-level HIVE_HOME entries the janitor must never touch, ever." —— 没有任何东西会被淘汰。

05两者关系：不需要"一起分发"

skillplaybook
位置6 个 scope 目录（见 §4.3）~/.hive/colonies/<c>/playbooks/
作用域跨 colony / 项目 / 客户端只属于某一个 colony
本质知识（方法 + 边界情况 + 如何记录结果）这个 colony 的具体流程（可重跑的调度程序）

唯一的关联是一根单向、字符串级的软引用：

worker(skill='name')  →  在任务文本后缀一行  Follow the 'name' skill.
                          （Python runner.py:226-230 / Go runner.go:310 逐字一致）
  • 没有存在性校验：技能不存在也不报错，worker 只是被提示"遵循一个它可能没有的技能"
  • 反向为零：skills 包里 grep playbook = 0 命中
  • 真正的可见性不来自 playbook，来自 worker 的 SkillDirs（colony 的 skills/ 自动进 catalog）——skill= 只是指针
它们什么时候确实"一起走"：只有打包整个 colony 目录时（两者都在树里）。那是打包的副作用，不是依赖。分发 skill = 装进某个 scope 目录；分发 playbook = 它天然绑在一个 colony 上。

06有没有进化

没有。而且这是仓库自己写下来的。 docs/key_concepts/improvement.md 开头："Note: earlier versions of Hive described improvement as 'evolution' — a coding agent that rewrote an agent's graph between generations. There is no graph in Hive today, and no cross-generation code rewriting. Improvement now happens through the mechanisms below."

按进化的四个必要条件逐条判

条件有没有证据
变异✅覆盖写：write_skill(replace_existing=True)、playbook 同名 write_text
遗传✅文件即基因：colony skills 进每个新 spawn 的 worker 的 catalog；scope 还能跨 colony / 项目 / 客户端
选择（差异生存）❌ 完全没有grep -rni "effectiveness\|success_rate\|usage_count\|hit_count\|score.*skill" = 0 命中。没有 A/B、没有回滚、没有淘汰
隔离 / 重组🟡 部分scope + overrides 给分层遮蔽，但没有合并/重组机制
有变异、有遗传、没有选择 = 漂变（drift），不是选择驱动的进化。进化的定义要求差异生存——这里没有任何东西影响"活下去"。

三条强化"没有选择"的证据

  1. janitor 明确保护 skills（KEEP_ALWAYS），playbook 目录也不在清理面 → 没有淘汰
  2. 没有 instinct / lessons 机制：全仓 grep 只命中一句注释里的英文单词，不是一个机制
  3. 没有"修订驱动"的提醒：唯一的 skill 相关 reminder 是①创建（"Factor it into a skill (write_skill)"）和②目录注入（<available_skills> 块）。没有一条提醒说"这个 skill 出错了/没用了，去改它"。修订完全靠 Queen 恰好想起来

那"改进"靠什么（仓库的说法）

时机机制本质
会话内Reflexion工具结果 + judge 反馈回灌 → 第二三次就对了
跨会话Scoped evolving memory反思写进 markdown 笔记，recall selector 后续调出
跨会话Learned skillspilot 成功 → write_skill 写下方法与边界情况
跨会话Systematization (playbook)pilot 成功 → 固化成可重跑的收敛流程
四个机制的共同点："记住并复用"（remember & reuse），不是"重写"（rewrite）。文档自己的收尾："This is improvement by remembering, not by rewriting."

这个设计的代价（照实说）

代价后果
只增不减没有淘汰压力 → 库持续膨胀、条目同质化。与「跨会话重复发明同一个 playbook」是同一现象的两面
质量无反馈写坏了的 skill 会被后续每个 worker 继承，而没有任何信号会告诉你它坏了
复制延迟不对称Queen 下一回合生效、worker 要等下一批 spawn → "改技能"救不了正在跑的批次
覆盖无痕replace_existing=True + 无备份 → 一次坏改能覆盖掉一个好版本，且没有回滚路径（overrides 只存"启用/关闭 + provenance + 参数微调"，不存历史版本）
修订无驱动没提醒、没评分、没失败归因 → 修订取决于 Queen 恰好想起来了

07三个具体缺口（带 ID）

L1 · fan-out 的"pilot 信号"已经过期 代码确认

colony_parallel_nudge 用工具名判定"她做过 pilot"：

_WORK_TOOL_PREFIX = "browser_"                        # 前缀
_WORK_TOOL_NAMES  = frozenset({"web_scrape"})          # 额外单列

但浏览器执行路径已经迁移：

core/framework/tools/browser_tools.py 的模块文档直说："The browser is driven from the terminal via the hive-browser CLI (which replaced the browser_* MCP tools). But the runtime can only observe tool NAMES, not opaque terminal_exec subprocess calls — so … this one in-process tool keeps the browser capability discoverable and gate-able: Its name starts with browser_, so tool_gating still pre-activates the foundational browser-automation skill."
事实后果
默认 39 个扁平工具里，browser_ 前缀只剩 browser_setup（且它只读、只用来读 CLI 用法）前缀从"我做了活"退化成"我读了活的手册"
真正的 pilot 活在 terminal_exec("hive-browser … --json")runtime 看不进子进程 → 假阴性
web_scrape 在 mcp_catalog 层（需先 search_tools 才可见）门槛又高了一层
两个信号（pilot + 刚写 tracker）不按任务关联假阳性：只读了 help + 任何无关 tracker 写入也会触发

同一个前缀承载了两个不同的问题，只有一个还成立：

消费者它想问的问题现在对吗
skills/tool_gating.py:35"浏览器能力是否存在" → 预激活 skill✅ 正确，且是刻意保留的
agentloop/colony_parallel_nudge.py"她是否真的做了一个单元"❌ 已不准

这不是 Go / Python 分叉——两边常量完全一致（workToolPrefix = "browser_" / workToolNames = {"web_scrape"}），是两个实现同样地过期了。

L2 · 没有发现机制 推断

✗ 无 list_playbooks 工具
✗ 无注册表 / 索引（playbook_runs 只是执行记录）
✗ 不主动注入提示词；reminder 不列库

推演出的后果：跨会话重复发明同一份 playbook。新会话上下文是空的，她不知道库里已有 instagram-dm-check，于是再写一个：同名 → 静默覆盖；不同名 → 库变成 foo、foo-2…只增不减。而唯一能让她看见"已有"的机制，是按名调用失败时的报错——她内联写的时候根本不触发。

关键缺口：nudge 让她"去写一个"，却从不告诉她"已经有一个"。_REMINDER_BODY 是固定字符串，没有任何库内插。

L3 · 无下架、无回滚 代码确认

  • 无 delete / retire 工具；无生命周期标记；无引用检查；janitor 不清理
  • playbook_path 可从任意路径执行 → 删文件 ≠ 不可执行
  • skill replace_existing=True 无备份；overrides 不存历史版本 → 没有回滚路径

08最小改法（不是"让代理自动重写自己"）

自动重写代理自己的知识风险极高，也不该是第一步。缺的是"选择压力"的最小闭环。
#加什么成本收益
1创建前告知已有：fan-out nudge 正文插入"本 colony 已有：…"（现扫目录即可，无需索引）小同时压住「重复发明」与「只增不减」。不引入任何新概念
2覆盖前留痕：写入前存一份旧版（或至少在 overrides 记 provenance）小给出回滚路径
3修 L1 的 pilot 信号：不再只看工具名（识别 terminal_exec 里的 hive-browser，或改用"tracker 新增完成行 + 工作量阈值"）中让"别继续手工做行了"这条提醒重新生效
4计数与归因：skill / playbook 被装载与使用的次数、关联到 run_id 的成功/死信率中让"有用/没用"第一次可观测——这是"选择"的前提

第 1 条性价比最高：它把已经能扫到的信息放进那条正在发出去的提醒里，不需要注册表、不需要评分、不破坏"文件即真源"。
