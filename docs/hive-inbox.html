Hive Inbox 协议与流程

Hive Inbox 是 Hive 云端后端（hive-backend）提供的第一方、账号绑定、双向通知通道——Sentinel 三个原生 channel 之一，默认开启。本页把协议（端点/字段/路由）与端到端流程可视化；它不是新的规范，唯一事实源仍是 docs/internal/hive-inbox-design.md（Draft，含实现状态 §14）。

00是什么（以及不是什么）

是
双向通道
colony 停泊提问 → 用户在 Inbox 回答 → colony 恢复。不是单向"通知中心"，是一条会话。
是
账号级收件箱
按账号（user_id + team_id）聚合所有 colony；桌面/网页/未来移动端都是同一通道的客户端。
不是
本地文件 / 自托管
消息存在 Hive 云端 Postgres；开源仓库只有协议与运行时客户端，后端实现是闭源的。
默认行为：没有 notifications.json 的 colony 解析为 channel="hive" + sentinel_enabled=true；有显式配置的按文件来；旧文件缺 channel 时解析为 hive。因此"登录状态下 Sentinel 默认开启"，Telegram/Slack 是 opt-in 的"also notify"。

01拓扑与传输

                    ┌─────────────────── hive-backend (hub，闭源) ──────────────┐
                    │  inbox_messages（user-scoped, team-visible）              │
                    │  inbox_message_reads（每人独立已读状态）                  │
                    │  runtime_connections（runtime_id → 活跃 SSE 连接）        │
                    │  Redis pub/sub 扇出                                       │
                    └───▲────────────▲───────────────────────┬─────────────────┘
   POST /v1/inbox/messages │            │ GET /v1/inbox/runtime/stream       │ GET /v1/inbox/stream (SSE)
   （升级上报）             │            │ （回复流，SSE，自注册 runtime_id）   │ + list/reply/read（POST）
              ┌────────────┴──┐   ┌─────┴────────┐        ┌──────▼──────────────┐
              │ runtime local │   │ runtime cloud│        │ clients             │
              │ colony A      │   │ colony B     │        │ desktop / web inbox │
              └───────────────┘   └──────────────┘        └─────────────────────┘
  • 传输：SSE 下行 + 普通 POST 上行。runtime 和客户端都是主动连出去（NAT 友好），后端不回调本地进程。
  • 路由键：消息上记录的 runtime_id（不是 colony→runtime 的映射，后者会漂移）。
  • runtime_id：云上 = e2b_sandbox_id；本地 = $HIVE_HOME/runtime_id 持久化的 uuid。环境契约：HIVE_RUNTIME_ID/HIVE_RUNTIME_KIND → E2B_SANDBOX_ID → 本地 uuid。
  • presence：runtime_connections 记录活跃连接；POST /v1/inbox/runtime/heartbeat 端点已存在，但 runtime 尚未调用，也没有过期清扫器（见 §07）。

02端点（/v1/inbox/*）

方法路径调用方用途
POST/v1/inbox/messagesruntime上报一条升级/报告（user_id/team_id 取自登录态）
GET/v1/inbox/messagesdevice列表（自己的 + 团队可见），支持 unread 过滤
GET/v1/inbox/streamdeviceSSE 推送新/更新消息（P1 桌面端实际用 15s 轮询，未消费此流）
POST/v1/inbox/messages/:id/replydevice用户答复；后端校验该消息属于当前用户/团队
POST/v1/inbox/resolveruntime跨渠道关闭（会话已在应用内/别处答复），按 session_id
POST/v1/inbox/messages/:id/readdevice标记单条已读
POST/v1/inbox/messages/mark-all-readdevice全部标记已读
GET/v1/inbox/messages/unread-countdevice角标未读数
GET/v1/inbox/runtime/streamruntimeSSE 回复流；连接即自注册 runtime_id
POST/v1/inbox/runtime/heartbeatruntimepresence 保活（端点存在，runtime 未调用）

上报字段（runtime → backend）

{
  "runtime_id": "…",        // 路由键：回复沿这条 id 回投
  "session_id": "…",         // 停泊待恢复的会话
  "colony_id": "…",          // 深链目标
  "kind": "blocker",         // blocker | heartbeat | progress | done
  "title": "…",
  "body": "…",
  "correlation_token": "…",  // 与 runtime 本地 escalation 记录对上
  "deep_link": null          // P1 未接线
}

认证：所有端点都要登录态；user_id/team_id 从登录凭据解析。runtime 用与 cloud_sync 相同的 Bearer 方式；desktop 用 Authorization: jwt …。回复会校验消息归属（owner 或 team-visible）。

03数据模型（后端 Postgres）

表 / 字段说明
inbox_messages一条消息一行；user-scoped, team-visible（owner 是主收件人，团队可读/可答作为兜底）
— id消息 id，也是返回给 runtime 的回复锚点
— user_id / team_id主收件人 / 团队可见范围（均来自登录态）
— runtime_id回复路由键：这条消息是哪个 runtime 发的
— session_id / colony_id待恢复会话 / 深链目标
— kindblocker · heartbeat · progress · done（kind 扩容迁移 035 已写未应用）
— title / body渲染内容
— correlation_token对回 runtime 本地 escalation 记录
— status / resolved_byopen|resolved；谁关的（user / superseded / 其他渠道）
— reply_text / deep_link / 时间戳存下的答复、深链、created/resolved/updated
inbox_message_reads每人独立已读状态；没有行 = 未读
runtime_connectionsruntime_id → 活跃 SSE 连接 + presence；只按 runtime_id 建键，绝不用 team_id 路由
为什么用 Postgres：要和 account_vm、runtime 注册表做事务读、关系型 ACL（team-visible）；不复用团队级 Mongo 的 honeycomb_notifications（生命周期不同）。

04端到端流程

4.1 报告（每次评估都发）

kind触发行为
blockerjudge 判定需人工 / 硬停停泊等回复，通知（loud）
heartbeat自动续跑到 max_nudges更响的检查点，停泊
progressjudge 判定继续只进 Inbox feed，不发 Telegram/Slack、不弹 toast；去重
doneclassifier 判定目标完成终态报告，通知（quiet）

发送：escalation_source._decide 选 kind → notifier.send("hive", …) → POST /v1/inbox/messages → 落 inbox_messages → Redis 扇出 → 客户端 SSE/轮询看到。
单会话单开项：新报告会 supersede 同一 session 之前的 open 报告（resolved_by='superseded'）；blocker 持有会话，等待回复期间不会被 supersede。首次评估前的空闲预算是 5 分钟（classify_after_seconds）。

4.2 回复 → 恢复

  1. 用户在客户端提交答复：POST /v1/inbox/messages/:id/reply。
  2. 后端按 id 读消息，取 runtime_id。
  3. 在 runtime_connections 里找到该 runtime 的活跃 SSE 连接。
  4. 把回复推到 GET /v1/inbox/runtime/stream（事件里带 correlation_token）。
  5. runtime 的 HiveInboxListener → manager.on_inbound("hive", …) → _resume() 把答复注入停泊的 queen。
  6. 后端把消息标记 resolved，把解决状态扇出给客户端。

4.3 跨渠道关闭 / 离线

  • 应用内答复：manager.on_local_resume 同时调 POST /v1/inbox/resolve（按 session_id），避免 Inbox 里留下过期条目。
  • 离线：路由依赖活跃 SSE 连接；runtime 不在线时回复返回 delivered:false（不排队）。"该 colony 离线"的提示与 heartbeat/sweeper 属于 P1.5。
  • 去重：连续相同的报告在 runtime 与后端两侧都去重。

NAT 约束：所有渠道（Telegram long-poll、Slack Socket Mode、Hive SSE）都是 outbound 连接。后端永远不能回调本地 runtime——这也是回复必须走 runtime 自注册 + SSE 的原因。

07实现状态（按设计文档 §14，分支 feature/hive-inbox）

已建
P1 主干
后端 migration 034（三张表）+ inbox 服务/控制器 + Redis 扇出；runtime 的 hive 通道/监听/身份/默认开启；桌面 InboxButton；Web Dashboard InboxBell（轮询）；跨渠道 resolve；report-everything。
有意偏差
4 项
设备端 15s 轮询（未消费 device SSE）；Sentinel 设置里 hive 呈现很少；deep_link 传 null；team-visible 只在刷新时可见（不实时推送）。
未建 / 债务
3 项
云 runtime_id ↔ account_vm 对账与终止清理；presence heartbeat/sweeper；spawner 环境契约（本地要 HIVE_RUNTIME_KIND=local，云要 HIVE_RUNTIME_ID=e2b_sandbox_id）。另有 migration 035 未应用（progress/done 会被旧 CHECK 拒绝）。
诚实口径：本页描述的是"协议 + 已建实现"。设计文档标 Draft，后端在独立闭源仓库；不要把"协议可见"当成"功能已在你本机可用"——本机没有配置 HIVE_CLOUD_BASE/登录态时，hive 通道发送会直接失败。

08开源边界（谁能看到/改什么）

部分可见性说明
设计文档 docs/internal/hive-inbox-design.md开源仓库内端点、数据模型、流程、实现状态、P1.5 债务全在；标 Draft，不是对外稳定规范

后端 hive-backend（Express/TS）闭源不在本仓库；GitHub 上 aden-hive/hive-backend 不可见（私有或不存在）
Inbox UI（桌面/网页）闭源开源前端无 /v1/inbox 调用；界面在闭源桌面/云 Dashboard

自建兼容：按本页端点 + 数据模型可以写一个兼容后端，但登录态/身份体系由 Hive 云签发，自建要自己造账号体系；HIVE_CLOUD_BASE 只能指向你自建的服务。成本明显高于直接用 Telegram/Slack，或把 Inbox 当 feed 再由外部转发。
