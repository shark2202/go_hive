00总览：六个机制，一根脊椎

Hive 的设计文档把它概括为"一个原语，多个设置"：全系统只有一个执行原语 AgentLoop；Queen 是它，Worker 是它的克隆。其余五个机制都是围绕这根脊椎的支撑：Colony 是部署单位（也是组织容器），Reminder 管注意力，Memory 管跨会话积累，Judge 管质量闸门。

01Queen：有身份的主管

设计（docs/key_concepts/queen.md）

  • 不是通用编排器，是身份：随包发行 13 个 Queen（各一部门主管），开箱默认启用 6 个；每个人都设是一份 YAML 画像（traits/background/behavior triggers），注入她的 system prompt。
  • 两阶段：Independent（她先自己做）→ Colony（当工作被证明是并行/周期/长时，她提议建 colony，用户在 Create Colony 对话框确认）。核心动作是 execute first, then systematize：先打样（pilot），再把路径固化成 skill + playbook。
  • 她拥有：对话（colony 唯一对外面）、计划（持久化任务表）、tracker（建 schema、用 SQL 验收）、以及"需要你拍板的问题"（park 等你回答；Sentinel 可在你离开时代为催办/升级）。

实现

  • queen_profiles.py 文件头：画像存 ~/.hive/agents/queens/{queen_id}/profile.yaml；本机 agents/queen/queen_defaults/ 实测 13 份 YAML（growth/technology/legal/finance_fundraising/talent/operations/product_strategy/sales/lead_gen/outbound/market_research/brand_design/content_creation）。
  • Queen 会话装载 12 个生命周期工具（core/framework/tools/queen_lifecycle_tools.py）：run_worker、stop_worker、write_skill、update_worker_profile、list_browser_profiles、get_worker_status、inject_message、list_worker_questions、reply_to_worker、set_trigger、remove_trigger、list_triggers；另有 queen mail 工具（queen_mail_tools.py）。
  • Queen 的记忆是 scoped 文件记忆 + 召回 + soul（见 §05）；worker 无记忆（每个 worker 都是新的）。
一个已发现的偏差：key_concepts/queen.md 写"自动 LLM 路由分类器已退役（猜错对象是错误设计），由用户自己选 Queen"；但代码里 select_queen（queen_profiles.py:779）仍被两条路径使用——session_manager.py:645（会话未带 queen 时兜底选择）和 routes_messages.py:21-37（POST /api/messages/classify，首页把提示词路由到某个 queen）。结论：文档说的是方向，代码里分类器仍在服役，两者需要对齐口径（见 §08）。

02Worker：专注、短命、失败要快

设计（docs/key_concepts/worker_agent.md）

  • Worker 不是另一种程序：是 Queen 那个 loop 的克隆 —— 同样的模型（除非配置独立 worker 模型）、一个 worker prompt、Queen 工具的子集、更紧的预算、注入一个任务。
  • 它"故意缺少"什么：无记忆、无人设、无 escalation（没有活人听众，绝不阻塞等答案）、不能派发自己的 worker（fan-out 属于 Queen）、失败要快（工具失败分类：瞬时→重试一次；结构性→修一次再试；不可修→停）。
  • 汇报：终止动作是 report_to_parent(status, summary, data)，三态 success / partial / failed；报告以 [WORKER_REPORT] 回合进入 Queen 的对话。为保证"总能汇报"，loop 有 grace iteration：即使预算耗尽，最后还有一个只放开 report_to_parent/task_update/tracker_upsert 的收尾回合。
  • Worker 之间不通信：协调完全靠共享基底 —— tracker.db（一行一个工作单元，Queen 直接用 SQL 读）、自己的 task list、colony 的 skills。
  • loop 配置对照（the_loop.md）：迭代 3 工作 + 1 grace；工具预算 30/回合（硬停 90）、生命周期 200。

实现

  • worker_definition.py 文件头把两件事钉在一起：运行时身份 + worker.json 序列化 ——"adding a field in one without the other is a silent contract break"；worker.json 由 routes_execution.fork_session_into_colony 写入，colony_runtime.spawn 读回。
  • host/worker.py 定义两种模式：ephemeral（默认）——跑一次、发 SUBAGENT_REPORT、终止；persistent——常驻，inject(message) 把用户聊天泵进已运行的 loop，用于 colony 的常驻 overseer。
  • 预算白名单/范围在 colony_runtime.py:64-121：可覆盖 max_iterations / grace_iterations / tool_call_budget / tool_call_lifetime_budget / max_context_tokens，其中 tool_call_budget ∈ (0,200]、tool_call_lifetime_budget ∈ (0,2000]，0 表示"不限制"。
  • worker 启动时会探测浏览器桥（_connected_browser_labels()，host/worker.py:29-45）：探不到就是"未知"，不能当成"没有连接"（避免瞬态误杀 worker）。

03Colony：一个目录，一台"多 loop 组织"

设计（docs/key_concepts/colony.md / coordination.md）

  • 为什么是 colony：真实业务流程是并行的、周期性的、长时的，且形状在开工前未知。Hive 的答案是"不预先定型"：Queen 先做，发现需要多少 worker 就在运行时开多少，没有图、没有边、没有节点要维护。
  • 磁盘形态：~/.hive/colonies/<name>/ 一个目录装下一切：Queen、worker 克隆、tracker/tracker.db（共享账本）、任务计划、skills/（打样后写下的方法，所有 worker 可加载）、triggers.json（定时唤醒）。
  • 四块轻基底（coordination.md）：tracker（结果，"什么做了、什么没做"的唯一真相，SQL 查询）、task plan（意图，持久任务表）、event bus（worker 报告与实时转录的"神经系统"）、reminder hub（注意力，§04）。
  • 绑定不可变：每个 worker 的 tracker 访问都带着 colony 的 binding（名字/目录/DB 路径）；没有 binding 的工具拒绝执行而不是猜路径 —— 防止两个 colony 写错账本。
  • 成长方式：execute-first-then-systematize；打样 → skill + playbook；playbook 自己不持状态，tracker 是真相，所以"重跑 = 断点续跑"（by construction）。
  • 人机回路：Queen 提问、loop park（落盘，可等几天）；Sentinel（按 colony 选择开关）在你离开时判定"催办 / 判定完成 / 升级到你"（Hive inbox / Telegram / Slack），你回复后 loop 恢复。

实现

  • colony_runtime.py 文件头（原文）："Each worker is an exact copy of the queen's AgentLoop — same tools, same prompt, same LLM … The ColonyRuntime replaces both AgentHost and ExecutionManager. There are no graphs, no edges, no nodes, no data buffers. Just: spawn N independent clones, let them run, collect results."
  • 配套实现：colony_binding.py（不可变绑定）、colony_db.py（colony 级库）、colony_metadata.py、tracker_db.py（ledger）、triggers.py + webhook_server.py（唤醒）、host/playbook/（playbook runner）。

04Reminder：系统的"注意力工程"

设计（reminders.py 文件头 + coordination.md）

一条 fan-out 几十个 worker 的长循环很容易忘事：忘了还有 worker 在跑、忘了压缩前落盘、忘了有哪些工具。ReminderHub 在已知时点注入"建议性上下文"（与配置式 hooks、错误纠正区分开）：

注入点类型 / 触发者含义
SESSION_STARTlifecycle（loop 内联触发）会话启动一次
USER_PROMPT_SUBMITlifecycle每次用户/外部消息到达
POST_TOOL_USElifecycle工具批次执行完（搭车在结果尾部）
TOOL_BUDGET_CHECKPOINTlifecycle每回合工具预算跨过新的软倍数（硬上限时合并进下一回合的 deferred advisory）
PRE_COMPACT / POST_COMPACTlifecycle压缩前 / 压缩后（把摘要丢掉的、模型看不见的东西重新播报：deferred 工具清单、skills catalog）
STOPlifecycle纯文本回合结束、agent 让出控制权时
IDLE_TICKtemporal（hub 自带的 ticker）周期轮询，park 中的 loop 也能被提醒
STREAM_STALLEDreactive（流一停滞就同步咨询）TTFT / 事件间静默看门狗触发时
  • 渲染与摆放：所有 body 统一包进 <system-reminder>…</system-reminder>，尾部固定一句（原文）："Only act on this if relevant to the current work. NEVER mention this reminder to the user."；安置点 Placement.USER_MESSAGE / TOOL_RESULT_TAIL。
  • energize（唤醒）：默认不唤醒 —— 大多数提醒是"下一回合读到的上下文"；只有"用户没法供给、不叫醒就会烂在那里"的提醒才 opt-in（例：CrmRevealReminderSource）。被 drain 的提醒会 energize 一个回合，保证被处理而不是躺在 park 的对话里。
  • 时序安全：temporal 点的提醒由 ticker collect() 暂存，loop 在迭代边界 take_pending() 取走 —— 对话写入永不与 loop 竞争。ticker 按所有 source 的最小间隔轮询。
  • 失败即跳过：任一 source 的 applies_to/render/observe_turn 抛异常 → 记 debug 日志并跳过，绝不传播（best-effort fan-out；过滤器坏了也 fail-open 保留 source）。
  • applies_to 是一次会话一次的"自我声明"：同一个 loop 服务多种角色（queen/worker/overseer），由 source 声明自己属于谁，而不是给 loop 按角色配置。

05Memory：纯文件的记忆与"自我叙事"

三层文件记忆（agents/queen/queen_memory_v2.py + key_concepts/queen.md）

  • 目录（~/.hive/memories/）：global/（所有 Queen/Colony 共享）、colonies/{name}/、agents/queens/{name}/ 与 agents/{worker}/。
  • 硬约束（代码常量）：MAX_FILES = 200 个文件/目录、MAX_FILE_SIZE_BYTES = 4096（4KB/文件）；全局记忆类别：profile / preference / environment / feedback。每个记忆是带 YAML frontmatter（name/type/description）的 .md。
  • 召回（recall_selector.py）：每回合前扫描目录 → 读 header（frontmatter + 前 30 行）→ 一次 LLM 结构化输出按 scope 选"明确有用"的 ≤5 条 → 注入 system prompt。只喂用户 query 字符串（省、快）；出错返回 []，绝不阻塞主对话。
  • past conversations：每条用户消息前，把最多 6 条相关历史会话的带日期摘录放到她眼前；所有历史可用 search_messages 搜；她被告知"先查记忆再问你"。
  • 时间线（timeline.py，需 memory_timeline 开关）：用 Queen 自己的 LLM 把用户消息抽取成 event / fact / plan 的带日期条目（相对日期按会话日期解析），写 <session>/timeline.jsonl + timeline_meta.json（抽取游标），单次抽取 ≤12,000 字符；由 search_timeline 工具提供。

Soul：Queen 的自我叙事（soul.py / soul_reflection.py）

  • 设计（soul.py 文件头）：profile 说"她该是谁"，memory 存"她知道的"，soul 是"她成为了什么"——她在想什么、与周围人状态如何、承诺过什么、为何如此、如何改变。第一人称、小（每节有字符上限）、永远在上下文里（紧随身份注入 system prompt），最多每天变一次。
  • 磁盘：queens/<id>/soul/ 下 soul.json（当前版本：version/updated_at/sections）、history/v<n>.json（每个曾生效的版本）、proposals/<id>.json（一次反思提出的修改及结局）、log.jsonl（每个新版本一行）、state.json（反思记账）。
  • 每日反思（soul_reflection.py 文件头）：每天在配置小时之后，她读自己聊天里"上次反思之后"的新消息（各会话 events.jsonl，标题按配置白/黑名单过滤），以工具形式用她自己的口吻提几条修改；代码按住提示词的规则：每条引用证据必须逐字出现在她读过的文本里、需要两条证据的节必须来自不同人或不同聊天、每次 ≤max_edits 条且不得超过节上限；超期条目自动掉落。
  • 模式：review 等用户逐条批准（soul.decide）；auto 立即生效。首版 bootstrap=True 还会读配置里的记忆文件、允许 bootstrap_edits 条修改。
  • 实现参数：_MAX_TURNS=8（bootstrap 16）、失败重试 1h 且每天 ≤3 次、state.json 按会话记录"已读到的时间"保证每段聊天只读一次。
  • Skills：Queen 打样后 write_skill 写下方法，落 colony skills/，进入之后每个 worker 的 skill catalog，按需加载（improvement.md 的"学到的技能"）。
  • LongMemEval：记忆质量的度量基准（docs/memory-benchmark.md、core/tests/e2e/longmemeval.py）。

06Judge：质量闸门（成功标准 + 说了没做）

设计（judge.py 文件头 + the_loop.md）

  • judge 是一个"槽"：configuration.json 的 judge 段声明 protocol / api_base / model / api_key / threshold，没有厂商被写死。当前唯一协议 typesafe：向 {api_base}/systemone 提一个 noul（概率）问题，返回 p(yes)。每次提问都重新读槽，改配置立即生效。
  • 语义：未配置 / 协议不支持 / 调用失败 → 返回 None（原因记日志）；超时 20s（"judge 卡住不能拖住问它的人"）。
  • agent 级 judge（reflexion）：声明了 success criteria 的 agent，每个完成的回合由 judge 管线检查——先便宜的"输出键检查"，再可选自定义 judge / LLM 质量检查；产出三态：ACCEPT（通过）/ RETRY（差一点，反馈作为消息注回对话，下一回合连批评一起看见）/ ESCALATE（根本卡住，停下上交）。Queen 跳过 judge——"你是她的 judge"；worker 以 report 结束。

Stall check（stall_check.py）："说了没做"的兜底

  • 问题：有些模型写"马上画"就结束回合、或只描述该改什么却不动手。开启 stall_check + judge 槽后，每个"结束时在等用户"的 queen 回合都会被送上 judge：用户消息、她最后的 reasoning 与回复、本回合调用的工具、以及她上一轮回复与工具（让 judge 能区分"对刚交付作品提出修正"与"空谈"）。
  • 判据是逐字提示词（_QUESTION + _CRITERIA true/false 长文），关键 false 口径：对话/回答问题/先问清需求/拒绝或反驳（即使承认错误、给了替代方案）/对用户质疑的回应/或本回合工具已做（即使结果不完美、回复里列了遗留缺陷）。
  • 判定 p ≥ threshold（默认 0.5）→ 注入一次提醒（原文见下方），此提醒是 <system-reminder>：告诉她要做的就现在调工具，不做就继续，不要提这条提醒。约束：每条用户消息至多一次判定/提醒（误判不会成环）；可见错误（gateway 把失败当回复）跳过；开关与槽都是回合结束时才读 → 运行中的会话立即生效。
  • 事件订阅：CLIENT_INPUT_RECEIVED / CLIENT_REASONING / CLIENT_OUTPUT_DELTA / TOOL_CALL_STARTED / CLIENT_INPUT_REQUESTED；只在 park_reason == "turn_done" 时判定；stream_id 必须是 queen。
  • 另一个使用点：channels（channels.py:123-125）——渠道层通过 ChannelHost.judge 向同一个槽提问（如"这条消息要不要升级"）。
REMINDER（stall_check.py 原文）：
<system-reminder>
Your last reply talked about work to do now (announced or promised it, or agreed to a change the user asked
for), but you ended the turn without calling any tool to do it, so nothing was done. If it should be done,
call the tools now. If not, carry on. Don't mention this reminder.
</system-reminder>

07停车与唤醒：park / idle nudge / Sentinel

长任务里真正难的不是"跑"，而是"等"：等人回答、等凭据、等外部事件、等定时器。Hive 用三条链路把"等待"变成可恢复、可提醒、可升级的状态机——三条都有代码与盘上证据。

① Park：停车即落盘（可等数天）

  • 停车有原因：每个 _await_user_input 调用点声明 ParkReason（TURN_DONE / ASK_USER / LLM_ERROR / USER_STOPPED / AWAITING_QUEEN / COLONY_SUGGESTION / UNKNOWN…），等待期间保留在 self._park_reason，供 idle nudge / Sentinel 区分"该等的"与"坏掉的"（agent_loop.py:3740-3790）。
  • 盘上结构（storage/session_store.py）：sessions/session_YYYYMMDD_HHMMSS_{uuid}/ 下——state.json（single source of truth，atomic write；含 status / checkpoint / active_triggers / pid / timestamps，schema v1.1）+ conversations/（EventLoop 状态，parts 带 phase_id）+ artifacts/（spillover）+ logs/（summary/details/tool_logs）。
  • 恢复路径：冷启动识别 _is_cold_resume（agent_loop.py:1437），cursor_persistence 的 checkpoint/resume 周期恢复对话与游标；session_manager 用 state.json 的 pid 做跨进程 stale 检测；worker 可用 resume_worker_ids 恢复。
  • 设计承诺（worker_agent.md）："a loop saves its position to disk whenever it waits, so a crash or restart resumes the session rather than starting over"。

② idle nudge：把"静默"变成一次提醒（in-memory）

IdleNudgeSource（temporal，IDLE_TICK）补 stream watchdog 的盲区——turn 之间、以及慢 TTFT 之下的静默。它按 park 子状态动作：

子状态行为
between_turns没有活跃 stream（judge/装配/真空闲）→ 按 cap 提醒
slow_ttft流已开但还没有首事件 → 提醒
parked_no_question无问题、无待办、原因 UNKNOWN → 只提醒一次找下一步；TURN_DONE 且无待办则完全不提醒
parked_open_tasks停车但 task list 还有未完成 → 点名任务；UNKNOWN 用满 cap，TURN_DONE 只一次
parked_broken失败后停车（LLM error / doom loop / 连续空回合）→ 短预算快速重启，防止 loop 搁浅
  • 外部等待（ask_user / colony suggestion / worker 等 queen）不打扰；正在出事件的流归 stream watchdog 管。
  • 计数按"用户回复周期"reset（loop 在用户消息时调用）→ in-memory，不落盘（advisory 状态；落盘的是 park 本身）。配置：session_idle_nudge_seconds=120、session_idle_nudge_max_per_session=3。

③ Sentinel：colony 无人值守时的"继续还是找人"

  • 决策：park 后 classify_after_seconds=300 开始评估；硬阻塞（broken park、auth/crash 错误）先判，模糊中间交一次廉价 LLM classifier（goal / open tasks / 最后回复 / 待答问题 / 最近工具错误）→ continue / needs_human / done。
  • 两种输出：返回 Reminder = 唤醒 loop 继续干（nudge）；发消息 + 返回 None = 保持 park 等人（escalate）。四种报告：blocker / heartbeat / done / progress（progress 只进 inbox feed，不发 telegram/slack）。
  • 落盘：~/.hive/colonies/<id>/escalations/<escalation_id>.json，字段含 escalation_id / colony_id / session_id / correlation_token / park_reason / question_text / channel / thread_ref / status / created_at / resolved_*；manager 启动时从 open records 重建 token 索引——"Disk is the source of truth"，重启后用户回复仍能路由回 parked queen。
  • 配置：全局 configuration.json 的 sentinel 块 + 每 colony notifications.json；默认 max_nudges_before_escalate=5、escalate_when_ui_attached=false、channel 默认 hive（内置 Inbox，无需 token；telegram/slack 需 token）。
  • 互斥：colony autopilot 时 Sentinel 独占 park 决策，IdleNudgeSource 自我跳过，避免双重 nudge；回复经 listeners（Telegram long-poll / Slack Socket Mode）→ inject_event 回 parked queen。
为什么重要：三条链路把"等待"从失控态变成状态机——park 保证等待不丢（盘上可恢复），idle nudge 保证静默不烂（回合间提醒），Sentinel 保证无人值守也能判断"继续/找人"（升级并落盘）。分工：stream stall 管流内静默，idle nudge 管回合间/停车，Sentinel 管停车后的决策与升级。

go_hive 对位：docs/reminders-coverage.md（13 source 注册矩阵，含 sentinel_escalation / idle_nudge / stream_stall）、docs/hive-inbox.html（Inbox 协议）、internal/sentinel；上游 Sentinel 的 escalation 记录是"盘上真相"，Go 侧实现与 E2E 需按此口径核对。
