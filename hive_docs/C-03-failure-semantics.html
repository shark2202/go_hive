失败语义分类学
五套独立分类 + 一条实际决策链

Hive 没有统一的 HiveError。失败被至少五套枚举分别描述：ParkReason、InterruptCause、JudgeVerdict、Sentinel verdict、Worker status；再叠加 LLM/工具的 transient 判定。本页把它们对齐成“信号 → 分类 → 动作 → 代码”的一张表。

0. 结论先行

真正决定“重试还是停”的不是异常类型，而是信号来源 + 分类器 + 预算：LLM 流错误走 transient/capacity；工具错误只标记 is_error，是否重试由模型/Worker 决定；死循环与文本停顿各有独立检测器；预算耗尽不是错误而是 grace；用户停止与崩溃恢复又是另外两条路径。缺少统一错误码，是排障时最大的摩擦。

2. 五套枚举

ParkReason（11）

  • 健康：ASK_USER、CREDENTIAL_FORM、COLONY_SUGGESTION、TURN_DONE、AWAITING_QUEEN、USER_STOPPED、COLD_INTERRUPTED
  • 故障：LLM_ERROR、EMPTY_RESPONSES、DOOM_LOOP
  • 未知：UNKNOWN
  • 视图：is_external_wait / is_silent_park / is_broken / activity

其它四套

  • InterruptCause：STREAM_STALL、CRASHED、STALE
  • JudgeVerdict：ACCEPT、RETRY、ESCALATE
  • Sentinel：continue、needs_human、done
  • Worker status：success、partial、failed、timeout、stopped

3. 实际决策树（简化）

收到信号
├─ 用户 Stop？ → USER_STOPPED，停止本 turn，不自动复活
├─ 进程崩溃/冷恢复？ → COLD_INTERRUPTED，读 cursor + parts 恢复
├─ LLM 调用失败？
│   ├─ capacity（429/529/overloaded）→ 持续重试到 600s
│   ├─ transient（网络/5xx/超时）→ 最多 5 次指数退避
│   └─ 其它 → ParkReason.LLM_ERROR
├─ 流卡住？
│   ├─ TTFT 600s → 取消流，重试/失败
│   └─ inter-event 120s → continue-nudge（≤3），否则错误
├─ 空回复累积 → EMPTY_RESPONSES
├─ 工具错误？
│   ├─ transient → 模型/Worker 决定是否重试一次
│   └─ structural → 不重试，记录/上报
├─ 同一工具调用 3 次 → DOOM_LOOP（警告/停泊）
├─ 文本回复 3 次相似 ≥0.85 → NODE_STALLED（提醒/停泊）
├─ 预算到硬上限 → grace 回合（只允许收尾工具）
├─ Judge RETRY → 注入 feedback 继续；耗尽 → ACCEPT/ESCALATE
└─ 停泊后 Sentinel → continue（nudge）/ needs_human（升级）/ done（收尾）

4. 缺口

结构性问题

  • 没有统一错误类型/错误码；同一失败在不同层有不同名字。
  • “transient”在 LLM 层自动重试，在工具层只是标签，语义不一致。
  • 重试预算分散在 LoopConfig、worker 提示、HTTP 客户端、CLI。
  • ParkReason 的 healthy/broken 视图是手工维护的集合，新增原因容易漏。
  • 没有“失败 → 用户可见文案”的映射表。

建议

  • 定义 FailureKind（transient/capacity/structural/permission/unknown）与统一错误码。
  • 把五套枚举映射到 FailureKind，集中决定 retry/fallback/park/escalate。
  • 为每个错误码补用户文案与可执行建议。
  • 用测试锁定 ParkReason 的视图集合与默认动作。
