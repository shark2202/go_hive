安全攻击面矩阵
11 个能力面，边界与缓解

Hive 的安全模型是“能力上限 = 运行它的用户权限”。本页把每个高危能力面、它能做什么、现有缓解与残余风险列成矩阵。它不是威胁建模的替代，而是把已知边界集中到一页。

0. 结论先行

最需要明确告知用户的三件事：① 终端/Playbook/MCP 就是任意代码执行；② 浏览器桥驱动的是用户已登录的 Chrome；③ 本机 HTTP API 默认没有强鉴权。Hive 的缓解是“分层 allowlist + 信任门禁 + 凭据加密”，不是沙箱。

2. 已知绕过/边界

Tracker

  • denylist 拦 ATTACH/PRAGMA/VACUUM/load_extension。
  • main._ 这种 schema-qualified 写可绕过 _ 前缀保护（19 章）。
  • Tracker 不是安全沙箱，只是“有护栏的 SQLite”。

HTTP / 本机

  • HIVE_DESKTOP_TOKEN 只在桌面模式强制。
  • hive serve 直接跑时无强鉴权。
  • CORS 只限制浏览器来源，不限制本机进程。
  • queen-mail 用一次性 token，但仍是本机。

3. 缺口与建议

缺口

  • 没有统一威胁模型/信任边界文档。
  • 高危能力没有默认关闭或显式授权。
  • 提示注入没有隔离/标记/出站审查。
  • 技能/MCP 安装无签名与来源验证。
  • 日志可能包含敏感上下文，脱敏不完整。

建议

  • 按“能力”做首次使用授权（terminal/browser/playbook/MCP）。
  • 为出站消息加人工确认或审计。
  • 给工具结果加“不可信内容”标记，提示模型不要执行其中的指令。
  • 把本页作为安全评审的基线，随能力增加更新。
