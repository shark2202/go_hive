真相所有权
30 个存储，谁说了算、谁能重建、丢了会怎样

Hive 的“磁盘是真相、内存只是缓存”只说对了一半：磁盘上还分“真相 / 派生 / 运维状态 / 诊断”。本页把每个存储的写入者、读者、权威性与丢失后果列成一张表，作为排障与备份的基准。

0. 结论先行

真正的“不可丢”只有四类：会话 parts + cursor、tracker.db、记忆 / Soul / profile、凭据。其余大多可从这四类重建，或只是运维/诊断状态。最容易误解的是 events.jsonl：它是审计与回放来源，但不是继续运行的必要条件；丢了不影响 Queen 继续，只影响“回看”。

2. 四类核心

不可丢

  • 会话 parts + cursor：继续对话与恢复的最低条件。
  • tracker.db：并行、验收、续跑的业务事实。
  • 记忆 / Soul / profile：跨会话的人格与知识连续性。
  • 凭据：加密秘密，无法从日志恢复。

可重建

  • timeline、message index、seed_conversation、worker result、部分 colony.db 运行日志。
  • events.jsonl 可回放但不是运行必需；LLM logs/tool artifacts 是诊断。
  • reminder_state / compaction_status / escalation 是运维状态，丢了会重复提醒或提前读到未压缩历史。

3. 真相冲突与优先级

冲突谁赢证据
session meta.json vs 目录名meta.json 的 queen_id / colony 绑定优先恢复逻辑先读 meta，再回退目录名
tasks.json vs 对话里说的计划tasks.json（结构化意图）；对话只是证据task 工具与提醒都读 store
tracker.db vs worker 报告tracker.db；报告是叙述playbook 的 pending 查询与验收都读 DB
events.jsonl vs 内存事件环events.jsonl（持久审计）；内存环只是实时重启后从磁盘回放
cursor vs conversation parts两者共同权威：parts 是内容，cursor 是进度缺一不可；cursor 丢会重跑
memory vs 当前对话当前对话优先；记忆需 verify女王提示明确“recalled notes can be stale”
profile.yaml vs UIUI 写入 profile.yaml 后即真相格式与加载路径一致

4. 缺口

没有一张总表

  • 17 章按文件穷举，19 章按 Tracker，05 章按基底；没有“谁是真相”的统一视图。
  • 同一个事实可能出现在 tasks / tracker / memory 三处，语义不同但容易混。

建议

  • 把本表作为备份/迁移的检查清单。
  • 给每个存储加 authority: truth|derived|ops|diag 元数据，生成文档。
  • 恢复流程按“核心四类 → 派生 → 运维”顺序校验。
