并发、锁与原子性
20 个锁/并发资源，谁保护什么、哪里会卡

Hive 的主循环是单线程 asyncio，但并发来自：多个 session、多个 worker、线程池、SQLite、子进程、文件锁。本页把锁与并发资源列成清单，并标出“串行化点”与“可能的等待源”。

0. 结论先行

Hive 不是“无锁并发”：它靠单事件循环 + 局部锁 + SQLite WAL + 文件锁组合。最容易卡住的是 Colony._scheduler_lock（spawn 串行）、EventBus 的 handler 信号量、Tracker 的写锁（busy 5s），以及工具线程池（64）。跨进程协调只有 SQLite 与文件锁，没有分布式锁。

2. 四类并发模型

事件循环内

  • 同一 session 的 AgentLoop 串行执行回合。
  • spawn/queue/admit 由 scheduler lock 串行。
  • handler 并发受 EventBus 信号量限制。

线程池

  • 工具执行 64 线程；HTTP 请求 32 线程。
  • 同步阻塞工具不会卡事件循环，但会占线程。
  • 线程池耗尽会让工具排队。

SQLite

  • WAL：多读单写；busy_timeout 5s。
  • 长事务会阻塞其他写者。
  • UI 读走只读快照，不抢原库。

跨进程

  • server.lock / janitor.lock 防双启动/并发清理。
  • MCP 子进程有自己的连接管理。
  • 没有跨主机锁；网络文件系统上 Tracker 不安全。

3. 非原子写与竞态窗口

已知窗口

  • conversation parts 按 seq 写；cursor 单独写——崩溃时可能“内容已写、进度未写”。
  • compaction_status 与 parts 替换是两步。
  • Tracker 触发器写 change log 与业务写在同一事务内（相对安全）。
  • fork 复制会话与后台压缩之间有窗口，靠 marker 等待。

建议

  • 为写路径标注“原子/可重放/需幂等”等级。
  • cursor 与最后一条 part 合并提交，或写前先记 intent。
  • 给锁加等待/持有时间指标，定位卡顿。
  • 明确“不支持网络文件系统”的部署约束。
