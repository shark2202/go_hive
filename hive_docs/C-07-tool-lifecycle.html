工具调用生命周期
从模型产出到结果回到上下文，15 个阶段

工具调用不是“执行一下”。它经过参数修复、grace/预算门、重放检测、并行分区、超时、截断/落盘、视觉回退、事件发布、微压缩与尾部提醒。本页把这条链路拆开，标出每一步的代码与失败语义。

0. 结论先行

工具调用层最容易被低估的是结果后处理：30k 截断 + 落盘、图片 caption、微压缩占位、尾部 reminder。这些都会改变模型下一轮看到的内容。另一个常见误解是“工具失败会自动重试”——工具层只标记 is_error，是否重试由模型或 Worker 决定。

2. 时序图

LLM response
  └─ tool_calls[]
       ├─ coerce input
       ├─ grace gate ──非收尾──▶ skip + placeholder
       ├─ per-turn hard gate ──超限──▶ defer + placeholder
       ├─ lifetime gate ──超限──▶ defer + grace next iter
       ├─ replay/doom fingerprint ──命中──▶ warn/escalate
       ├─ partition
       │    ├─ framework tool → inline
       │    └─ real tool → parallel (≤10)
       ├─ TOOL_CALL_STARTED
       ├─ execute(timeout)
       ├─ truncate/spill (>30k)
       ├─ vision fallback (image)
       ├─ TOOL_CALL_COMPLETED
       ├─ conversation.add_tool_result
       ├─ microcompact(old results)
       ├─ POST_TOOL_USE reminders (tail)
       └─ judge → next turn

3. 失败与边界

失败

  • 超时：工具结果 is_error，由模型决定下一步。
  • transient：只打标签，不自动重试。
  • 永久：同样标记，Worker 应 fail-fast。
  • 死循环：检测器介入，不依赖工具本身。

边界

  • 并行只读上限 10；写工具默认串行。
  • 结果 >30k 落盘，模型只看到预览。
  • 图片在纯文本模型下被 caption。
  • 旧结果会被微压缩成占位符。
  • 没有工具结果 schema 校验。

4. 缺口

结构性问题

  • 生命周期逻辑集中在 7.5k 行循环里，没有独立状态机。
  • “工具错误”没有结构化错误码。
  • 结果截断/落盘/微压缩三套机制叠加，排障需看多处。
  • 工具重试策略在提示词里，不在代码里。

建议

  • 抽出 ToolCallPipeline 状态机，阶段可观测。
  • 给工具结果加 error_kind 与 retryable。
  • 统一“截断/落盘/微压缩”的结果生命周期。
  • 为每个阶段发结构化事件，UI 可追踪。
