权限与能力模型
没有中央 capability token，只有 11 层局部检查

Hive 的授权是“层层过滤”而不是“统一主体 + 能力表”：工具表、阶段列表、MCP allowlist、eager/searchable、queen-only 剥离、技能信任、凭据过滤、CRM principal、HTTP token、OS 权限各自为政。本页把这些层拼成一张矩阵，并标出哪些只是声明、没有执行。

0. 结论先行

最危险的三个误解：① AgentSpec.tool_access_policy 在 live AgentLoop 里不生效；② 技能 frontmatter 的 allowed-tools 只被解析/校验，运行时不会按它过滤；③ 没有通用 principal/能力令牌，principal 只在可选 CRM 包里使用。真正可靠的边界只有：工具表本身、Queen-only 剥离、MCP allowlist、技能信任门禁，以及“能力上限 = 宿主用户权限”。

3. Queen-only 剥离的精确集合

20 个被剥离

get_playbook_status, get_worker_health_summary, get_worker_status, inject_message, list_playbook_runs, list_queens, list_triggers, message_queen, remove_trigger, run_playbook, run_worker, search_tools, set_trigger, stop_playbook, stop_worker, suggest_colony, switch_to_independent, tracker_register_writable, tracker_sql, write_skill

6 个被继承

task_create, task_get, task_list, task_update, tracker_query, tracker_upsert

  • Worker 仍可读写自己被分配的 tracker 行。
  • tracker_sql / tracker_register_writable 是 queen-only，防止 worker 改 schema。
  • write_skill 是 queen-only，worker 只能使用已存在技能。

4. 技能信任与 allowed-tools

信任门禁

  • 直接放行：framework、preset、user、queen_ui、colony_ui。
  • project scope：按 git remote 分类；未信任仓库在 headless 下直接跳过。
  • HIVE_TRUST_PROJECT_SKILLS=1 可在 CI 中跳过询问。
  • 结论：信任是“整仓级”，不是“单技能级”。

allowed-tools

  • 解析到 ParsedSkill.allowed_tools。
  • validator 会检查它是否是字符串列表。
  • 运行时没有消费点：没有按它裁剪工具表或拦截调用。
  • 因此它目前是文档性声明，不是安全边界。

5. 缺口与建议

缺口

  • 没有统一 Principal（谁、在哪个会话、代表谁）。
  • 没有 per-call 授权：凭据过滤只发生在 spawn。
  • tool_access_policy 与技能 allowed-tools 声明不执行。
  • HTTP 无 per-route auth，远程部署需自建反代。
  • 终端/Playbook/浏览器无沙箱，等于宿主用户。

建议

  • 定义统一 capability 表：subject × action × resource × context。
  • 让 AgentLoop 执行 tool_access_policy，并让技能 allowed-tools 参与过滤。
  • 把凭据检查从 spawn 前移到 per-call，失败返回可恢复错误。
  • 为 HTTP 增加可选 bearer auth，而不是只靠 localhost。
  • 把“无沙箱”写进产品边界，而不是隐含假设。
