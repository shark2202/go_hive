03

测试基础设施

最值得看的是隔离、mock 与标记机制：它们决定了测试能否在开发者机器、CI 和真实模型之间安全切换。

导入前隔离 HIVE_HOME

关键设计

core/conftest.py 在任何 Hive 模块导入之前，把 HIVE_HOME 指向一个临时目录，并在进程退出时删除。注释记录了一次真实事故：测试曾覆盖用户真实 ~/.hive 的凭证密钥，因为 litellm 导入时调用了 load_dotenv()，把仓库 .env 里的真实 HIVE_HOME 带了进来。

  • 隔离发生在 import 阶段，因此所有「导入时计算路径」的模块都落在一次性目录
  • atexit 清理，避免临时目录堆积
  • 这是测试工程里少见的「把事故写进注释」的做法，可审计、可追溯

每测试隔离与 Live 反转

autouse

父级 conftest 为每个测试准备独立的 Hive home；core/tests/live/conftest.py 则通过 monkeypatch.undo() 主动撤销隔离，让 Live 测试读取开发者真实的 configuration.json、凭证与模型，与桌面应用完全一致。

确定性 Mock 模型

单元

MockLLMProvider 根据期望的 JSON 结构生成占位响应，用于无 API key 的结构校验与循环测试；AgentLoader.load(..., mock_mode=True) 走同一能力。注意：代码里没有 MOCK_MODE=1 这个环境变量，旧文档的写法已过时。

live 标记

默认关闭

core 与 tools 的 pytest 配置都写了 addopts = "-m 'not live'"，并注册了 live 标记。除非显式 -m live 或清空 addopts，否则真实 API 测试不会运行。

异步与并行

pytest-asyncio

core 使用 pytest-asyncio>=0.23；tools 设置 asyncio_mode = "auto"。两边都声明 pytest-xdist，CI 本身不加 -n，但 LongMemEval 文档示例使用 -n 4 并行跑题。

框架内的「目标驱动测试」子系统

产品能力

core/framework/testing/ 不是 pytest 辅助包，而是一套面向 Agent 的测试框架：根据 success_criteria 与约束生成测试，用 pytest 子进程 + xdist 执行，做错误分类，并提供 LLMJudge 语义评判、人工审批 CLI 与 MCP 工具。

  • 组成：Test / TestResult / TestStorage / ErrorCategorizer / LLMJudge / approval_cli / debug_tool
  • CLI：python -m framework test-run | test-debug | test-list
  • 因为模块名是 test_*.py，它被 CI 的 --ignore=framework/testing 排除，避免把库代码当测试收集

Queen E2E 是「规格驱动」的

spec-driven

测试本身只有 20 行：对 SPECS 里的每个场景做参数化，运行 Queen 的多轮对话，断言回合数并调用 spec.check(run)。真正的场景、夹具与断言在 specs.py、synthetic.py、conftest.py 里，因此加场景不需要改测试函数。

Live 夹具刻意「不用测试替身」

真实组件

core/tests/live/conftest.py 明确说明：使用与桌面应用相同的 AgentLoop、NodeContext、NodeConversation、LiteLLMProvider、EventBus、FileConversationStore，唯一差别是用户回合来自 Python 列表、工作目录是 tmp_path。

LongMemEval 可恢复、可换判官

基准

环境变量控制题量（HIVE_LME_QUESTIONS）、断点续跑（HIVE_LME_RESUME）、时间线开关（HIVE_LME_TIMELINE）、判官模型与 API（HIVE_LME_JUDGE_MODEL 等）。失败但已产生的回答会保留并标记为未评分，便于之后 rejudge。

为什么都不在 CI

按设计

两边 pytest 配置默认 -m 'not live'，CI 没有注入真实 API key 的步骤，也没有 nightly 工作流。好处是 CI 稳定、无外部依赖；代价是这两条最有价值的端到端链路只能靠维护者手动跑。

覆盖率

未采集

仓库内没有 coverage / pytest-cov 配置，CI 也不生成报告。测试很多，但「哪些路径没被覆盖」不可见，无法用趋势判断新增代码的质量。

08

评价：强项、缺口与风险

总体判断：测试工程是這個仓库的强项，尤其是隔离设计、真实链路测试与打包验证； 主要短板集中在「已有的测试没有全部进 CI」和「缺少覆盖率与 Python 类型检查」。

强项

体量与分层都真实

强

三大套件 113k 行、5,888 个函数，与 135k 行的生产代码同量级；跨模块集成、同目录单测、工具 mock 测试分层清楚，定位测试的成本低。

隔离设计有事故记忆

强

HIVE_HOME 在 import 前重定向，并有真实事故注释。对一个会写凭证、Sentinel 密钥和运行时 ID 的系统，这比多写几百个断言更有价值。

Live 测试用真实组件

强

明确拒绝 test-only 子类与上下文捷径，使用与桌面应用相同的 AgentLoop、Provider、EventBus。这让 Live 结果更可信，也更容易解释「测试通过但线上失败」的差异。

端到端记忆评测

少见

LongMemEval 不只是检索组件测试，而是通过真实存储、真实 Queen 回答、官方 judge 评分，并主动披露「读完整历史更高」「偏好类最弱」等失败模式。

工具测试覆盖广

广

106 个按工具拆分的测试文件，覆盖 104 个集成目录中的大部分；浏览器桥、终端、凭证、图表、健康检查都有独立测试。

双平台 + 安装后验证

扎实

Linux 与 Windows 同时跑 core 与 tools；打包 job 在干净 venv 里安装 wheel 并运行检查脚本，能抓到「workspace 能跑、装出来不能跑」的问题。

改进建议与统计复现

建议按「成本低、收益快」排序，前三条基本是配置级改动。

#建议具体做法预期收益
1 把前端测试接进 CI 在 package job 的 npm run build 前加 npm test；或新增一个轻量 test-frontend job 复用 npm 缓存 立即让 218 个已有用例生效，成本几乎为零
2 先让覆盖率「可见」 pytest-cov 生成 XML/HTML 上传为 artifact；前端用 vitest --coverage。先不设门槛，观察趋势 找到空白路径，为后续重构提供客观依据
3 启用 ty 或移除它 从 framework/llm、framework/storage、hive 等边界清晰的模块开始，先 report-only；或在确认不用后删掉 dev 依赖 避免「声明了类型检查器但从不运行」的误导
4 加一条 nightly Live/E2E 用 repository secrets 提供模型 key，跑一个小规模 -m live 子集与 Queen E2E；失败只通知、不阻塞 PR 让整链路测试真正持续执行，而不是靠记忆
5 修复测试收集范围 把 tools/src/**/tests 移入 tools/tests，或在 testpaths 中加入；同时让 make test 不再忽略 tests/tools 消除「测试存在但从不运行」的盲区
6 删除死忽略 去掉 --ignore=tests/dummy_agents，或恢复该目录并说明用途 减少读者误解
7 加工具描述快照测试 对工具名、首行描述、类别与 eager/searchable 分层生成快照；变更需显式更新 把「prompt 影响」纳入 CI，防止无意改动改变模型行为
8 拆分巨型测试文件 随 agent_loop.py 的拆分同步拆 test_event_loop_node.py，按 TurnRunner、ToolExecutor、CompactionController 对齐 降低定位与并行成本，减少重构冲突
9 补浏览器冒烟 用 Playwright 跑「创建会话 → 发消息 → 收到回复 → 建 Colony」一条链路 覆盖前后端契约，补上前端 E2E 空白
10 对 mock 密集区做行为化改造 优先把断言从「内部调用次数/具体文案」转向「输入输出与可观察状态」 降低重构时的大面积误报
